# 회의록 정리

STT 전사본은 길고, 노이즈가 많고, 결론이 흩어져 있다. 이 스킬의 목적은 그걸 **다음 행동을 정할 수 있는 문서**로 바꾸는 것이다.

## 결과물

- 저장 위치 기본값: `01_Raw/정권호/Jira/`
- 파일명: `YYYY년 M월 D일 <회의 성격>.md` (예: `2026년 7월 27일 Sprint Planning.md`)
- 다른 위치를 원하는 낌새가 있으면 물어보되, 없으면 기본값으로 조용히 진행한다.

## 절차

### 1. 인코딩부터 확인한다

STT 도구가 뱉는 파일은 UTF-16인 경우가 많다. 그냥 읽으면 `\355\231\230` 같은 깨진 문자만 나오고, 그 상태로 요약하면 통째로 헛것을 지어내게 된다.

```bash
file "<경로>"                                   # 인코딩 확인
iconv -f UTF-16 -t UTF-8 "<경로>" > <스크래치패드>/meeting.txt
```

변환본은 스크래치패드에 두고 볼트를 어지럽히지 않는다. 원본 파일은 건드리지 않는다.

### 2. 전문을 다 읽는다

앞부분만 읽고 요약하지 않는다. 회의는 같은 주제로 몇 번씩 되돌아오고, **최종 결론이 처음 언급보다 뒤에 나온다.** 초반에 "A로 하자"고 했다가 한 시간 뒤에 뒤집는 일이 흔하다.

2000줄 단위로 끊어 읽되, 마지막 20~30분은 잡담 비중이 높으니 그 부분은 요약에서 덜어내도 된다(다만 읽기는 읽는다 — 잡담 중에 결정이 튀어나온다).

### 3. STT 오인식을 감안해 읽는다

한국어 STT는 영어 약어와 고유명사를 심하게 뭉갠다. 실제로 관측된 것들:

| 전사된 것 | 실제 |
|---|---|
| MBT1, MBP, MVBN2 | MVP1, MVP, MVP2 |
| 오어스, 오버스, 호스 | OAuth |
| JPI, EPI, APN, PY, FPI | API |
| 에피, 에필 | 에픽(Epic) |
| 지라적, 지라고 | 지라(Jira) |
| 클로드안, 그랬더니 | 클로드(Claude) |

문맥으로 복원하되, **확신이 안 서면 지어내지 말고** `> [!question] 확인 필요` 로 남긴다. 숫자(날짜·개수·금액)는 특히 잘 틀리니 앞뒤에서 교차 확인한다.

### 4. 발화자를 추정하되 추정임을 밝힌다

전사본은 `발화자 1/2/3`으로만 나온다. 본문 중 호명("태환 씨", "권호 씨")이나 역할 발언("에픽은 제가 만들어 놨거든요")으로 매핑할 수 있다.

mz2az 팀 구성: **정권호 = 백엔드, 김태환 = 데이터/AI, 정승길 = 프론트·팀장**

매핑했으면 문서 상단에 추정임을 반드시 명시한다. 담당자 배정이 이 추정 위에 얹히기 때문에, 틀렸을 때 조용히 틀리면 피해가 크다.

### 5. 확정 / 시도 / 미결을 갈라낸다

**이게 이 작업에서 가장 중요하고, 가장 자주 틀리는 지점이다.**

팀은 회의 중에 이 세 가지를 말로 명확히 구분한다. 그대로 받아 적어야 한다:

- **확정** — "이건 확실한 확정인데", "이걸로 가죠", "확정입니다"
- **시도** — "일단 해 보고", "이건 시도예요", "이건 확장이고"
- **미결** — 논의만 하고 결론 없이 넘어간 것. 다음 회의로 미룬 것.

같은 대화 덩어리 안에 확정과 시도가 섞여 나오므로, **어느 쪽이 어디에 붙는지 발화 시점으로 확인한다.** 중요한 확정·시도에는 타임스탬프와 원문 인용을 남긴다:

```markdown
> 원문: *"이건 확실한 확정인데 … 유명한 것들은 수작업으로"* (02:24:18)
```

인용을 남기면 나중에 뒤집혔을 때 근거를 되짚을 수 있다. 실제로 이 구분을 반대로 적어서 지라 티켓까지 잘못 만든 적이 있다.

### 6. 회의록이 항상 기준이다

**"무엇이 결정됐는가"는 오로지 전사본에서 판단한다.** 다른 문서를 근거로 전사본의 내용을 뒤집지 않는다. 팀원이 같은 회의를 정리해 둔 노트가 볼트에 있을 수 있지만, 최신본이 아닐 수 있고 개인 메모라 맥락이 빠져 있다.

다른 자료는 **참고용으로만** 쓴다. 이런 용도는 괜찮다:

- 발화자 추정 (누가 어느 파트인지)
- 사람·제품·멘토 이름의 정확한 표기
- 프로젝트 용어 확인 — `01_Raw/정승길/SceneTrip.md` 등
- 지라 에픽 이름·구조 확인 (Atlassian MCP 연결되어 있음. `searchJiraIssuesUsingJql`로 `project = MZ2AZ AND issuetype = 에픽`)

즉 **표기와 맥락은 밖에서 빌려오되, 사실관계는 전사본에서만 가져온다.**

### 7. 회의록에 없는 내용은 쓰지 않는다

빈 칸을 그럴듯하게 메우지 않는다. 완료 조건이 전사본에 없으면 만들어 넣지 말고, 담당자가 정해지지 않았으면 배정하지 말고, 기한이 안 나왔으면 추정하지 않는다.

애매한 곳이 나오면 두 가지 중 하나를 한다:

- 문서 안에 `> [!question] 확인 필요` 로 남긴다
- 판단이 문서 전체 구조를 좌우할 만큼 중요하면 **작업을 멈추고 사용자에게 묻는다**

사용자는 회의에 있었다. 5초면 답해줄 것을 지어내서 틀리는 게 훨씬 비싸다.

## 문서 구조

```markdown
# YYYY-MM-DD <회의명>

> [!info] 문서 정보
> - **원본**: <파일명> (STT 전사, 약 N시간 N분, 인코딩)
> - **참석**: ...
> - 관련 노트: ...

> [!warning] 발화자 매핑은 추정입니다
> ...

## 1. 회의 개요
표로: 기간 / 목표 / 범위 등 한눈에 볼 것

## 2. 해야 할 일 (Action Items)
### 2-1. <묶음 이름> — <담당>
- 무엇을, 왜, 언제까지
- **완료 조건**을 반드시 적는다

## 3. 결정된 것 (Decisions)
### 3-1. 일정
### 3-2. 범위
### 3-3. ...
확정과 시도를 callout으로 갈라서 표시

## 4. 결정해야 할 일 (Open Issues)
| # | 항목 | 상태 / 메모 |

## 5. 기타 기록
```

## 서술 원칙

- **완료 조건이 회의에서 나왔으면 적는다.** "데이터 수집"보다 "병합된 CSV 1본이 나오고 빈 칸이 채워져 있다"가 낫다. 다만 **없는 걸 지어내지는 않는다** — 회의에서 안 정했으면 안 정한 대로 둔다.
- **근거를 남긴다.** 결정에는 이유가 붙어 있다. "성지 100개 × 3개면 충분하니까" 같은 근거를 같이 적어야 나중에 그 결정을 재평가할 수 있다.
- **범위 밖으로 밀린 것도 적는다.** "이번 MVP에서는 안 한다"는 것도 결정이다. 안 적으면 다음 회의에서 같은 논의를 반복한다.
- **추측하지 않는다.** 모르면 `> [!question] 확인 필요`.
- **속도보다 정확도.** 전문을 다 읽고 교차 확인하느라 오래 걸려도 괜찮다. 이 스킬의 목적은 긴 프롬프트 없이 명령 한 줄로 부르는 것이지, 빨리 끝내는 게 아니다.

## 볼트 규약

- `**단어**` 뒤에 한국어 조사가 바로 붙으면 렌더링이 깨진다. 한 칸 띄운다: `**단어** 가` (`**단어**가` 아님)
- Obsidian callout(`> [!info]`, `> [!check]`, `> [!warning]`, `> [!question]`)을 적극 쓴다. 확정/시도 구분에 특히 유용하다.
- `01_Raw`는 원자료 보관 폴더다. 정리본을 여기 두더라도 **원본 파일 경로를 반드시 문서에 남겨** 검증 경로를 유지한다.

## 마무리

정리가 끝나면 사용자에게 이렇게 알린다:
1. 저장 위치
2. 핵심 3~5줄 (이번 스프린트에 뭘 해야 하는지)
3. **확인이 필요한 항목** — 추정한 것, 애매했던 것, `[!question]`으로 남긴 것

3번을 빠뜨리지 않는 게 중요하다. 사용자는 회의에 있었으므로, 틀린 부분을 즉시 잡아줄 수 있는 유일한 사람이다.
