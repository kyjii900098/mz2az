# 지라 백로그 생성

회의에서 나온 일을 지라로 옮기는 작업이다. 핵심은 **회의가 스스로 그은 범위를 지키는 것** 과 **만들기 전에 검사받는 것** 두 가지다.

## 접속 정보

변하지 않는 것만 적어 둔다. 나머지(에픽 목록, 기존 티켓, 커스텀 필드)는 **매번 MCP로 조회한다** — 낡은 값을 문서에 박아두면 조회를 건너뛰고 틀린 키를 쓰게 된다.

| 항목 | 값 |
|---|---|
| 사이트 | `mz2az.atlassian.net` |
| cloudId | `1e4d59af-da0b-44f4-9ac7-02107f0795bc` |
| 프로젝트 키 | `MZ2AZ` (team-managed) |
| 계층 | 에픽 → 스토리 / 작업 → Subtask |
| 이슈 타입명 | `에픽`, `스토리`, `작업`, `Subtask` |

이슈 타입명은 **한글 그대로** 넘긴다. `Story`, `Task` 같은 영어로 보내면 실패한다.

## 절차

### 1. 지라 실물을 먼저 읽는다

MCP 인증이 끊겨 있으면 `mcp__atlassian__authenticate`로 URL을 받아 사용자에게 전달한다.

```
searchJiraIssuesUsingJql  → project = MZ2AZ AND issuetype = 에픽    (에픽 목록·키)
searchJiraIssuesUsingJql  → project = MZ2AZ ORDER BY created DESC  (기존 티켓)
```

**에픽 키를 기억에 의존해 쓰지 않는다.** 매번 조회해서 나온 키만 쓴다. 에픽은 추가·개명될 수 있고, 과거에 회의록 텍스트만 보고 에픽 개수를 7개로 넘겨짚었다가 틀린 적이 있다 (`계정`과 `인프라`는 한 에픽이다).

**같은 회의록으로 이미 만든 티켓이 없는지 반드시 확인한다.** 회의록 경로가 description에 남아 있으니 그걸로 찾는다. 이미 있으면 새로 만들지 말고 **차이(delta)만** 제안한다 — 그냥 만들면 수십 개 중복이 생기는데 MCP로는 지울 수 없다.

### 2. 회의록에서 티켓 후보를 뽑는다

입력은 `01_Raw/정권호/Jira/` 의 정리본이다. 다음 매핑을 쓴다:

| 회의록 | 지라 |
|---|---|
| 해야 할 일 (묶음) | **스토리** |
| 그 아래 개별 작업 | **Subtask** |
| 확정된 방침 | 일반 스토리 |
| "시도" 로 표시된 것 | 스파이크 스토리 (`spike` 라벨, 제목에 `[Spike]`) |
| 결정해야 할 일 | 이번 주 범위에 걸린 것만 티켓화, 나머지는 두지 않음 |

### 3. 회의록에 없는 내용은 만들지 않는다

**티켓 내용은 전부 회의록에서 나와야 한다.** 완료 조건이 회의록에 있으면 옮기고, 없으면 비워 둔다. 그럴듯한 문장을 지어 채우지 않는다. 기한·우선순위도 회의에서 나온 것만 넣는다.

애매해서 판단이 필요하면 **5단계 계획에 질문으로 올린다.** 임의로 정하고 넘어가지 않는다.

### 4. 회의가 그은 범위를 지킨다

회의록에 "이번 스프린트는 딱 두 가지만" 같은 문장이 있으면 그게 제약이다. 관련돼 보인다고 티켓을 늘리지 않는다. 범위를 부풀리는 건 팀의 결정을 조용히 뒤집는 일이다.

범위 밖이지만 잊으면 안 되는 것은 `backlog` 라벨을 달아 구분해 둔다.

### 5. 계획을 먼저 보여주고 승인받는다

**티켓을 하나라도 만들기 전에 멈춘다.** 지라 생성은 되돌리기 어렵다 — MCP에 삭제 기능이 없어서, 잘못 만들면 사용자가 UI에서 손으로 지워야 한다.

보여줄 것:
- 에픽별로 묶은 스토리 목록과 각 서브태스크
- 회의가 이번 주 범위로 잡은 것 / 그 밖의 것(`backlog` 라벨) 분리
- 기한, 우선순위
- **티켓으로 만들지 않기로 한 것과 그 이유**
- 확인이 필요한 판단 (담당자 배정, 실물과 회의록의 불일치 등)

승인이 나기 전에는 읽기 전용 조회만 한다.

### 6. 생성한다

```
createJiraIssue(
  cloudId, projectKey="MZ2AZ", issueTypeName="스토리",
  summary, description,
  additional_fields={
    "parent": {"key": "<에픽 키>"},
    "labels": [...], "priority": {"name": "Highest"}, "duedate": "YYYY-MM-DD"
  })
```

- 스토리는 `additional_fields.parent` 로 에픽에 붙인다.
- Subtask는 최상위 `parent` 파라미터에 **스토리 키**를 넣는다.
- 스토리를 먼저 다 만들어 키를 확보한 뒤 서브태스크를 만든다.
- 각 description 끝에 출처를 남긴다: `` 출처: `01_Raw/정권호/Jira/<파일>.md` ``

**호출이 300초 타임아웃으로 실패했다는 알림이 와도 실제로는 생성됐을 수 있다.** 재시도하기 전에 반드시 조회해서 확인한다. 그냥 다시 만들면 중복이 생긴다.

### 7. 검증하고 보고한다

전량을 다시 조회해 부모·라벨·기한이 맞는지 확인한다. 결과가 크면 파일로 떨어지니 스크립트로 요약한다:

```bash
python3 -c "
import json; d=json.load(open('<결과파일>')); ...
print(f\"{key} {type} parent={parent} due={due} {labels} {summary}\")"
```

보고에는 **사용자가 손으로 해야 하는 일**을 반드시 포함한다.

## 스프린트는 건드리지 않는다

**스프린트 운영은 사용자가 직접 한다.** 이 스킬이 할 일은 **백로그에 티켓을 만드는 것까지** 다.

- `customfield_10020`(스프린트)에 값을 넣지 않는다.
- 이슈를 스프린트에 넣거나 빼지 않는다.
- "스프린트를 만드세요" 같은 안내도 하지 않는다. 사용자가 알아서 한다.

기존 스프린트 상태는 **중복 확인 목적으로만** 조회한다(`sprint IN openSprints()` — `sprint IS NOT EMPTY` 는 이슈가 배정된 스프린트만 잡아내므로 빈 스프린트를 놓친다).

## 알려진 제약

**이슈를 삭제할 수 없다.** MCP에 삭제 기능이 없다. 잘못 만들었으면 제목에 `[삭제 예정 / 잘못 생성됨]` 을 달고 사유를 본문에 적은 뒤, 브라우즈 링크(`https://mz2az.atlassian.net/browse/<키>`)를 주고 UI에서 지우게 한다. 이래서 5단계 승인이 중요하다.

**담당자는 비워 둔다.** 회의록의 발화자 매핑은 추정이라 확실하지 않다. 사용자가 명시적으로 지정하지 않으면 미지정으로 만들고, 필요하면 제목에 이름을 넣는 선에서 그친다(`담당분 데이터 수집 — 김태환`).

## 티켓 작성 원칙

- **왜 이렇게 하기로 했는지를 본문에 남긴다.** 근거가 있어야 나중에 재평가할 수 있다. "성지 100개 × 3개면 충분하다고 판단" 같은 것.
- **확정과 시도를 제목에서 구분한다.** 스파이크는 `[Spike]`, 확정은 그냥 서술형. 티켓만 보고도 "이건 해보고 판단하는 거구나"를 알 수 있어야 한다.
- **범위 밖이라는 사실도 본문에 적는다.** "전수 DB 방식은 이번 MVP에서 하지 않는다" 같은 문장이 있으면 다음에 같은 논의를 반복하지 않는다.
- 회의가 이번 주 목표로 못 박은 것은 `Highest`, 지원 작업은 `High`, 나머지는 `Medium`. 회의에서 우선순위를 논하지 않았으면 기본값(`Medium`)으로 둔다.

## 기존 티켓을 고칠 때

회의록이 정정되면 이미 만든 티켓도 따라가야 한다. `editJiraIssue`로 `summary`, `description`, `labels`, `priority`를 바꾼다.

내용이 뒤집히는 정정이면 본문에 정정 사실을 적을지 판단한다 — 팀이 볼 티켓이라 "왜 바뀌었나"가 필요할 때가 있다. 다만 정정 근거가 나중에 또 뒤집힐 수 있는 것(예: 누군가의 개인 노트)이라면, 근거를 적지 말고 최종 상태만 깔끔하게 남긴다.
