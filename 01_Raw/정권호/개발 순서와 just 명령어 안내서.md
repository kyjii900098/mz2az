## 먼저 — AI에게 일을 시킬 때는 이 프롬프트를 쓴다

거창하게 쓸 것 없다. 이 세 줄이면 된다.

```
MZ2AZ-<번호> 작업해줘.

기획 레퍼런스는 ~/mz2az 다. 이 폴더와 JiraDocs/ 를 참고해서 진행해라.
애매하거나 정해지지 않은 건 추측하지 말고 나한테 물어봐.
```

저장소 규칙(`AGENTS.md`, `CLAUDE.md`)과 개발 순서는 AI가 알아서 읽는다.
프롬프트에 옮겨 적지 않는다.

셋째 줄이 제일 중요하다. 그게 빠지면 AI는 **정해지지 않은 것을 그럴듯하게 채워 넣는다.**
이유와 예외는 [[#6. AI에게 일을 시킬 때 지켜야 할 규칙|6장]] 에 있다.

## 0. 먼저, 큰 그림 한 장

우리 저장소에는 프로그램을 조립하는 기계가 하나 있다. 이름은 **Bazel** 이다.
이 기계는 성능은 좋은데 조작 방법이 복잡하다. 버튼이 수십 개고, 옵션 하나 빠뜨리면
엉뚱한 결과가 나온다.

그래서 그 앞에 **주문표** 를 하나 붙여놨다. 그게 **just** 다.

```
   사람 / AI
      │
      │  "just build"  ← 이렇게만 말한다
      ▼
 ┌──────────┐
 │   just   │   주문표. 어떤 버튼을 눌러야 하는지 알고 있다.
 └────┬─────┘
      │  bazel build //... --옵션 --옵션 --옵션
      ▼
 ┌──────────┐
 │  Bazel   │   실제 조립 기계
 └──────────┘
```

**중요한 원칙 하나:** 이 저장소에서는 `bazel` 을 직접 치지 않는다. 문서에도, 스크립트에도,
사람이 손으로도 안 친다. **항상 `just` 를 통해서만 부른다.**

왜냐면 — 주문표를 거치면 모든 사람이 **똑같은 옵션으로** 명령을 실행하게 된다.
누구는 옵션 빼먹고 누구는 넣고 하면, "내 컴퓨터에선 되는데요?" 가 시작된다.
주문표는 그 사고를 원천 차단한다.

### 용어 몇 개 미리 풀기

- **저장소(repository)** — 코드가 들어있는 창고. 우리 창고 이름은 `arapaima`.
- **모노레포(monorepo)** — 창고 하나에 백엔드·앱·AI를 전부 넣는 방식. 우리가 이 방식이다.
- **빌드(build)** — 사람이 쓴 코드를 컴퓨터가 실행할 수 있는 형태로 **조립** 하는 일.
- **타깃(target)** — 조립할 물건 하나하나에 붙인 **이름표**. `//services/scene-api:bin` 처럼 생겼다.
  앞의 `//` 는 "창고 맨 위에서부터" 라는 뜻이고, `:` 뒤가 물건 이름이다.
- **레시피(recipe)** — just 명령 하나하나. `just build` 의 `build` 가 레시피 이름.

## 1. 딱 세 개만 기억한다면

나머지는 다 잊어도 이 셋은 남겨두자.

**`just`**
아무것도 안 붙이고 그냥 치면 **쓸 수 있는 명령 전부** 를 그룹별로 보여준다.
설명이 안 떠오르면 이걸 치는 게 이 문서를 찾는 것보다 빠르다.

**`just doctor`**
"내 노트북에 필요한 도구가 다 깔려 있나?" 를 검사한다. 뭔가 안 될 때 **가장 먼저** 칠 명령.
병원 가면 일단 체온 재는 것과 같다.

**`just check`**
**작업을 끝내고 남에게 넘기기 전에 반드시 통과시켜야 하는 검문소.**
줄맞춤 검사 → 잔소리 검사 → 조립 → 테스트를 한 번에 돌린다.
초록불이 안 뜨면 아직 끝난 게 아니다.

## 2. 상황별 처방전

### 상황 A — 저장소를 방금 클론했다. 뭐부터?

```bash
just setup     # 필요한 도구 설치. 여러 번 실행해도 안전하다.
just doctor    # 제대로 깔렸는지 확인
just versions  # 지금 쓰는 도구들 버전 확인
```

`setup` 은 **멱등(idempotent)** 하다 — 어려운 말인데, **"몇 번을 실행해도 결과가 같다"** 는 뜻이다.
엘리베이터 버튼을 열 번 눌러도 한 번 누른 것과 같은 것처럼. 그러니 불안하면 그냥 또 돌려도 된다.

> 참고: 지금 이 저장소는 **뼈대만 있고 실제 모듈은 0개** 다.
> 그래서 `just build` 나 `just test` 를 돌리면 "할 일이 없다" 는 식으로 조용히 끝난다.
> 고장 난 게 아니라 **아직 조립할 물건이 없는 것** 이다.

---

### 상황 B — 코드를 고치는 중이다. 잘 돌아가는지 보고 싶다

```bash
just build                             # 창고 전체 조립
just build-module services/scene-api   # 내가 만진 모듈만 조립 (훨씬 빠름)
just test                              # 빠른 테스트만 실행
just test-module services/scene-api    # 내 모듈 테스트만
```

**전체를 조립하지 말고 내 모듈만 조립하자.** 창고가 커질수록 차이가 커진다.
집 전체를 청소할 필요 없이 내 방만 치우면 되는 것과 같다.

프로그램을 실제로 실행해 보고 싶으면:

```bash
just run //services/scene-api:bin -- --port=8080
```

`--` 뒤에 붙는 건 just 한테 하는 말이 아니라 **그 프로그램한테 그대로 전달되는 말** 이다.

---

### 상황 C — 작업을 끝냈다. 넘기기 전에 뭘 해야 하나

```bash
just fmt      # 줄맞춤을 자동으로 고쳐준다
just check    # 검문소 통과 시도
```

- **포맷(format)** = 들여쓰기, 띄어쓰기, 줄바꿈을 **정해진 모양으로 맞추는** 일.
  내용은 안 바뀌고 생김새만 바뀐다. 사람마다 스타일이 다르면 나중에 "누가 뭘 고쳤는지"
  알아보기가 어려워지기 때문에 기계가 통일해 준다.
- **린트(lint)** = 코드에 대한 **잔소리 검사**. 문법은 맞는데 위험하거나 헷갈리는 표현을 잡아낸다.
  맞춤법 검사기가 아니라 **문장이 애매하다고 지적하는 편집자** 에 가깝다.

`just check` 가 빨간불이면 **거기서 멈춘다.** 빨간 걸 초록으로 만드는 게 작업의 일부다.
테스트를 지우거나 검사를 꺼서 초록으로 만드는 건 절대 안 된다 — 그건 체온계를 부수는 것이다.

CI 서버에서 뭐가 터졌는지 로컬에서 똑같이 재현하고 싶으면:

```bash
just ci    # CI가 하는 일 전부를, CI와 같은 순서로
```

- **CI(Continuous Integration, 지속적 통합)** = 내가 코드를 올릴 때마다 **서버가 대신 검사해 주는 것**.
  집에 들어오기 전 현관에서 검사받는 것과 비슷하다. `just ci` 는 그 검사를 미리 집 안에서 해보는 것.

### 상황 D — 새로 뭔가를 만들려고 한다

**절대 손으로 폴더를 만들지 않는다.** 반드시 아래 명령으로 만든다.

```bash
just new-service scene-api        # 백엔드 서비스 (Java / Spring Boot)
just new-app-ios trip-ios         # iOS 앱 (Swift)
just new-app-android trip-android # Android 앱 (Kotlin)
just new-agent trip-planner       # AI 에이전트 (Python)
just new-lib java telemetry       # 여러 곳에서 같이 쓰는 공용 코드
just new-contract proto scene/v1  # 모듈 간 약속 문서
```

왜 손으로 만들면 안 되냐면 — 이 명령들은 **뼈대(scaffold)** 를 찍어낸다.
설정 파일, README, 테스트 자리, 이름표까지 **모든 모듈이 똑같은 모양으로** 시작한다.
붕어빵 틀과 같다. 틀을 안 쓰고 손으로 빚으면 모양이 제각각이 되고,
나중에 자동화 도구도 사람도 그 모듈을 못 찾는다.

지금 뭐가 있는지 보려면:

```bash
just modules
```

**계약(contract)** 이라는 말이 낯설 텐데 — 모듈끼리 주고받는 **데이터 형식 약속** 이다.
"나는 이런 모양으로 보낼 테니 너는 이런 모양으로 받아라" 를 문서로 못 박아 둔 것.
백엔드와 앱이 서로 코드를 들여다보지 않고도 맞물릴 수 있는 이유가 이것이다.

약속을 바꿨으면 반드시:

```bash
just gen    # 약속 문서를 보고 각 언어용 코드를 새로 찍어낸다
```

- **생성(generate)** = 약속 문서 하나에서 Java용·Swift용·Kotlin용·Python용 코드를
  **기계가 자동으로 만들어 주는** 것. 사람이 네 벌 손으로 쓰면 반드시 어긋난다.

### 상황 E — 테스트가 이상하다

먼저 알아둘 것: 테스트는 **네 개의 라인(lane)** 으로 나뉜다. 공항 검색대가 여러 줄인 것과 같다.

**`just test` — 빠른 줄 (단위 테스트)**
함수 하나, 클래스 하나만 따로 떼서 검사. 몇 초 만에 끝난다. **항상 초록이어야 한다.**

**`just test-integration` — 통합 테스트**
데이터베이스나 다른 프로그램을 실제로 띄워놓고 검사. 느리다.

**`just test-e2e` — 끝에서 끝까지(end-to-end)**
앱에서 버튼 누르면 서버 거쳐 DB까지 갔다 오는 전 과정을 한 번에 검사. 제일 느리고 제일 현실적이다.

**`just test-contract` — 계약 테스트**
보내는 쪽과 받는 쪽이 **약속을 정말 지키고 있는지** 검사. iOS와 Android가 따로 만들어져도
같은 서버와 맞물리는 걸 이게 보장한다.

문제 상황별 처방:

```bash
just test-fresh //some:target      # 결과가 의심스러울 때: 기억(캐시) 무시하고 다시
just test-flaky //some:target 20   # 됐다 안 됐다 할 때: 20번 돌려서 확인
just test-log //some:target        # 마지막 실행 기록 보기
just coverage                      # 테스트가 코드를 얼마나 훑었는지 비율로 보기
```

- **캐시(cache)** = **"이거 아까 해봤는데 결과 이거였어"** 하고 기계가 기억해 두는 것.
  그래서 두 번째부터는 순식간에 끝난다. 그런데 가끔 그 기억이 낡아서 틀릴 때가 있고,
  그때 `test-fresh` 로 **기억을 무시하고** 처음부터 다시 시킨다.
- **플래키(flaky) 테스트** = **변덕스러운 테스트.** 코드를 안 고쳤는데 어떤 날은 통과하고
  어떤 날은 실패한다. 제일 골치 아픈 종류다. `test-flaky` 로 여러 번 돌려서 정말 변덕인지 확인한다.

### 상황 F — 뭐가 뭐랑 연결돼 있는지 모르겠다

이건 **모노레포에서 제일 자주 쓰게 되는 종류** 의 명령이다.
"이거 고치면 어디가 깨지지?" 를 추측하지 말고 물어보자.

```bash
just targets                    # 이 창고에 있는 물건 목록 전부
just test-targets               # 테스트 목록 전부
just rdeps //libs/java/util:lib # 이걸 쓰고 있는 게 누구누구인가 (= 고치면 영향받는 범위)
just why //apps/x:app //libs:y  # x가 왜 y에 의존하게 됐는지 경로 추적
just deps-graph                 # 외부에서 가져다 쓰는 라이브러리 관계도
```

`rdeps` 가 특히 유용하다. **"내가 이 공용 코드를 건드리면 누가 다치나?"** 에 대한 답을
추측이 아니라 사실로 알려준다.

### 상황 G — 외부 라이브러리를 추가하고 싶다

```bash
# 1. MODULE.bazel 파일을 직접 열어서 편집한다 (여기가 유일한 창구)
# 2. 그다음:
just deps-update
# 3. 바뀐 MODULE.bazel.lock 파일을 같은 커밋에 함께 넣는다
```

- **잠금 파일(lock file)** = 가져다 쓰는 라이브러리의 **정확한 버전을 못 박아 둔 명세서**.
  이게 없으면 사람마다 다른 버전을 받아서 "제 컴퓨터에선 되는데요" 가 발생한다.
  그래서 이 파일은 **반드시 코드와 같이 커밋** 한다.

무거운 라이브러리를 새로 넣는 건 되돌리기 어려우니 **넣기 전에 팀에 먼저 물어본다.**

### 상황 H — 문서를 고쳤다

```bash
just docs-lint          # 문서 검사 — 스타일, 죽은 링크, 목록에서 빠진 문서
just docs-fmt           # 자동으로 고칠 수 있는 건 고쳐준다
just docs-check-index   # 모든 폴더에 README 목차가 있는지 확인
just docs-serve         # 문서 사이트를 노트북에서 띄워 보기
just adr-new "제목"      # 새 결정 기록 만들기
just adr-list           # 지금까지의 결정 목록
```

- **ADR(Architecture Decision Record, 아키텍처 결정 기록)** =
  **"우리가 왜 이렇게 하기로 했는지" 를 남기는 회의록.**
  중요한 성질이 하나 있는데, **한 번 쓴 ADR은 고치지 않는다.** 생각이 바뀌면
  새 ADR을 써서 "이건 3번 결정을 대체한다" 라고 적는다.
  일기를 고쳐 쓰지 않고 새 날짜에 새로 쓰는 것과 같다. 그래야 **결정이 바뀌어 온 흐름** 이 남는다.

### 상황 I — AI 에이전트를 만진다

```bash
just agent-run trip-planner -- --input=fixtures/a.json  # 로컬에서 실행
just agent-eval trip-planner        # 평가 실행 (실제 AI 모델을 부르지 않음 — 공짜, 빠름)
just agent-eval-all                 # 모든 에이전트 평가
just agent-lint-prompts             # 프롬프트 파일 검사
just agent-check-tools              # 도구 명세와 실제 구현이 맞는지 확인
just agent-eval-diff trip-planner <기준>  # 바꾸기 전후 비교 — 정말 나아졌나?
```

- **평가(evaluation, eval)** = AI가 내놓는 답의 품질을 재는 시험.
  일반 테스트가 "맞다/틀리다" 라면, 평가는 **"얼마나 잘했나"** 를 점수로 매긴다.
- **픽스처(fixture)** = AI 모델의 응답을 **미리 녹화해 둔 것**.
  시험 볼 때마다 진짜 모델을 부르면 돈이 나가고, 매번 답이 조금씩 달라져서
  시험 자체를 믿을 수 없게 된다. 그래서 녹화본을 틀어놓고 시험한다.

**돈이 나가는 명령 두 개** (실행 전에 물어본다):

```bash
just agent-eval-live trip-planner   # 진짜 모델을 불러서 평가 — 과금됨
just agent-record trip-planner      # 진짜 모델을 불러 녹화본 새로 만들기 — 과금됨
```

### 상황 J — 내 노트북에서 서버를 실제로 띄워 보고 싶다

여기서 개념 두 개를 먼저 풀자.

**컨테이너 이미지(container image)** = **도시락** 이다.
프로그램뿐 아니라 그게 돌아가는 데 필요한 것(라이브러리, 설정, 실행 환경)까지
**한 통에 다 싸 놓은 것**. 그래서 어느 컴퓨터에 갖다 놔도 똑같이 돌아간다.

**쿠버네티스(Kubernetes, 줄여서 k8s)** = **급식실** 이다.
도시락을 몇 개 데울지, 하나가 상하면 언제 새로 데울지, 어느 창구로 배식할지를 관리한다.

**kind** = 노트북 안에 만든 **연습용 급식실**. 진짜 급식실은 클라우드에 있고,
kind는 내 컴퓨터 안에서 똑같은 구조를 흉내 낸다.

```bash
just up               # 연습용 급식실을 짓고 계기판까지 설치 (여러 번 해도 안전)
just cluster-doctor   # 도구·급식실·계기판 상태를 한 화면에
just cluster-status   # 지금 뭐가 돌고 있나
just cluster-test-drive  # 급식실이 진짜 되는지 시험 배식 한 번 해보기
```

배포 흐름은 이렇다:

```bash
just image scene-api       # 도시락을 싸서 급식실 안까지 들여놓기
just deploy scene-api      # 배식 시작하고 다 나올 때까지 기다리기
just logs scene-api        # 그 프로그램이 뭐라고 떠드는지 실시간으로 보기
just health                # 살아 있나 / 손님 받을 준비 됐나 확인
just update scene-api      # 코드 고친 뒤: 다시 싸서 → 들여놓고 → 갈아끼우기
just pod-shell scene-api   # 돌고 있는 통 안에 직접 들어가 보기
```

> ⚠️ **가장 흔한 사고 하나만 짚고 간다.**
> 도시락을 새로 쌌는데 **급식실 안에 들여놓는 단계를 빠뜨리면**,
> 오류가 나지 않고 **옛날 도시락이 조용히 계속 배식된다.**
> "코드 고쳤는데 왜 그대로지?" 의 90%가 이것이다.
> `just image` 와 `just update` 는 이 단계를 안에 포함하고 있으니 이 명령을 쓰면 안전하다.

정리할 때:

```bash
just undeploy scene-api   # 그 프로그램만 내리기 (급식실은 그대로)
just cluster-down         # 급식실 통째로 철거 — 쌓인 기록도 같이 사라진다
```

### 상황 K — 서버가 왜 느린지, 어디서 터졌는지 보고 싶다

**텔레메트리(telemetry)** = 프로그램이 돌면서 **스스로 내보내는 계기판 데이터**.
자동차의 속도계·연료계·경고등이라고 보면 된다. 로그(무슨 일이 있었나),
트레이스(요청 하나가 어디를 거쳐 갔나), 메트릭(숫자 지표) 세 종류가 있다.

**SigNoz** = 그 계기판을 모아서 보여주는 **대시보드**.

```bash
just signoz          # 접속 주소와 사용법 안내
just signoz-open     # 브라우저에서 바로 열기
just signoz-status   # 계기판 자체가 잘 돌고 있나
just signoz-verify   # 데이터가 실제로 쌓이고 있는지 직접 조회해서 확인
just signoz-watch    # 쌓이는 양을 주기적으로 출력 (Ctrl+C로 중지)
```

노트북이 무거우면:

```bash
just signoz-pause    # 잠시 재우기 — 데이터는 그대로 보존된다
just signoz-resume   # 다시 깨우기
```

노트북에서 직접 돌리는 앱의 계기판 데이터를 보내고 싶으면:

```bash
just signoz-forward  # 통로를 열어둔다. 터미널을 붙잡고 있으니 창을 하나 더 띄우자.
```

공부용 자료도 있다:

```bash
just slides    # 쿠버네티스·관측성 강의 슬라이드
just guides    # 설치 가이드 목록
```

### 상황 L — 진짜 클라우드를 건드린다 (조심)

여기부터는 **되돌리기 어려운 영역** 이다. 내 노트북이 아니라 **모두가 쓰는 것** 을 바꾼다.

읽기만 하는 안전한 명령:

```bash
just tf-check dev    # 인프라 설정 파일 문법 검사
just tf-plan dev     # "적용하면 뭐가 바뀔지" 미리보기 — 실제로 바꾸진 않는다
just k8s-render dev  # 설정 파일만 만들어 보기
just k8s-diff dev    # 지금 돌고 있는 것과 뭐가 다른지 비교
```

- **Terraform** = 클라우드 인프라(서버, 네트워크, 데이터베이스)를 **설정 파일로 관리하는 도구**.
  콘솔에서 마우스로 클릭해서 만들면 나중에 누가 뭘 왜 만들었는지 아무도 모른다.
  파일로 적어두면 코드처럼 리뷰하고 되돌릴 수 있다.
- **plan(계획)** 과 **apply(적용)** 의 차이가 핵심이다.
  `plan` 은 **견적서** 고 `apply` 는 **공사 시작** 이다. 항상 견적서를 먼저 본다.

실제로 바꾸는 명령 — **반드시 확인 질문을 거친다**:

```bash
just tf-apply dev            # 인프라 실제 변경
just image-push scene-api    # 도시락을 공용 창고에 올리기
just rollback scene-api      # 이전 버전으로 되돌리기
just ci-release v1.2.0       # 릴리스 배포
```

"Bazel이 도저히 말을 안 들을 때" 만 쓴다. 확인 질문이 뜬다.

## 3. 확인 질문이 뜨는 명령들

아래 명령은 **실행 전에 "정말 할까요?" 를 물어본다.** 되돌리기 어렵거나,
남들이 같이 쓰는 것을 건드리거나, 돈이 나가기 때문이다.

물어본다고 겁먹을 필요는 없다. 다만 **질문에 뜬 대상이 내가 의도한 게 맞는지**
한 번 읽고 답하자. 특히 환경 이름(`dev` / `staging` / `prod`)을 확인한다.

- `just clean-all` — 조립 기억 전부 삭제
- `just cluster-down` — 연습용 급식실 철거 (쌓인 기록 소멸)
- `just signoz-uninstall` — 계기판과 저장된 모든 기록 삭제
- `just rollback` — 돌고 있는 배포를 이전 버전으로
- `just image-push` — 공용 창고에 올리기
- `just tf-apply` — 클라우드 인프라 실제 변경
- `just ci-release` — 릴리스 배포
- `just agent-eval-live`, `just agent-record` — 실제 AI 모델 호출 (과금)

---

## 4. 필요한 명령이 없을 때

**직접 `bazel` 이나 `kubectl` 을 치지 않는다.** 대신 **레시피를 새로 만든다.**

1. `tools/just/` 안에서 성격이 맞는 파일을 고른다
   (조립은 `bazel.just`, 테스트는 `test.just`, 쿠버네티스는 `k8s.just` … )
2. 레시피를 추가하고 `[group('...')]` 표시와 **설명 주석** 을 단다
3. 남들이 같이 쓰는 걸 바꾸는 명령이면 `[confirm]` 을 붙인다

설명 주석에 주의할 점이 하나 있다. just는 **레시피 바로 윗줄의 마지막 주석 한 줄** 만
설명으로 읽는다. 그러니 여러 줄을 쓸 거면 **요약 문장을 맨 아래에** 둔다.

```
# 배경 설명 여러 줄...
# 이러저러한 이유로 이 명령이 필요하다.
#
# 모듈 이미지를 빌드해 kind 노드에 적재    ← 이 줄이 목록에 표시된다
[group('k8s')]
image module tag="dev":
    ...
```

**"레시피를 추가하는 것까지가 그 작업의 일부다."**
명령을 한 번 손으로 치고 넘어가면, 다음 사람은 그 명령이 존재했다는 것조차 모른다.

## 5. 이 저장소는 어떤 순서로 개발되는가

### 지금 우리가 서 있는 지점

이 저장소에는 **규칙과 명령만 있고 실제 코드는 아직 0줄** 이다.
`services/`, `apps/`, `agents/` 폴더를 열어 보면 README 하나씩만 들어 있다.

즉 지금은 **집을 짓기 전에 설계 규칙과 공구를 먼저 갖춰 둔 상태** 다.
이제부터가 실제 공사다.

### 전체 5단계

```
 0단계   규칙과 공구 갖추기          ← 지금 여기
         AGENTS.md, justfile, 폴더 구조
              │
 1단계   약속(계약) 정하기            contracts/ 를 먼저 쓴다
         "서버는 이런 모양으로 준다, 앱은 이런 모양으로 받는다"
              │
 2단계   뼈대 찍어내기                just new-service / new-app-ios / new-agent
              │
 3단계   각자 개발 (동시에!)          백엔드 · 앱 · AI 가 서로 안 기다린다
              │
 4단계   맞물리는지 검사              just test-contract → just test-e2e
              │
 5단계   띄우고 지켜보기              just deploy → just logs → SigNoz
```

### 왜 하필 "약속"이 맨 앞인가

이게 이 저장소 구조 전체에서 **가장 중요한 한 가지** 다. 여기만 이해하면 나머지는 따라온다.

우리 팀은 백엔드·앱·AI 세 갈래로 나뉘어 일한다. 만약 약속을 먼저 정하지 않으면
이렇게 된다.

```
 약속 없이 일하면 — 줄줄이 기다린다

 백엔드  ████████
 앱                ████████          ← 서버 나올 때까지 손 놓고 대기
 AI                          ████████
                                      전체 3배
```

앱 담당자는 서버가 나올 때까지 할 게 없다. AI 담당자는 그 둘이 끝날 때까지 또 기다린다.
셋이 일해도 한 사람 속도밖에 안 나온다.

약속을 먼저 못 박으면 이렇게 바뀐다.

```
 약속을 먼저 정하면 — 동시에 간다

 약속    ██
 백엔드    ████████
 앱        ████████                  ← 서버가 없어도 개발할 수 있다
 AI        ████████
                                      전체 1배 + 약속 정하는 시간
```

앱 담당자는 **"서버가 이런 모양으로 준다"는 종이 한 장** 만 있으면 화면을 다 만들 수 있다.
서버가 실제로 완성됐는지는 나중 문제다. 이게 `contracts/` 폴더가 존재하는 이유 전부다.

### 약속은 어디에 어떻게 적나

`contracts/` 안에 종류별로 나뉘어 있다.

- `contracts/openapi/` — 앱이 서버를 부를 때 쓰는 **REST API 명세**
- `contracts/proto/` — 서버끼리 부를 때 쓰는 **gRPC 명세**
- `contracts/asyncapi/` — 실시간 이벤트·알림 명세
- `contracts/schemas/` — **AI 에이전트가 쓰는 도구의 입출력 명세**

여기 적힌 것만이 정답이다. 그리고 반드시:

```bash
just gen    # 약속 → 각 언어용 코드를 기계가 찍어낸다
```

> ⚠️ **생성된 코드를 손으로 고치지 않는다.**
> `just gen` 이 만들어 준 파일을 직접 수정하면, 다음에 누가 `just gen` 을 돌리는 순간
> 그 수정은 흔적도 없이 사라진다. 고칠 게 있으면 **약속 파일을 고치고 다시 생성** 한다.
> 원본 문서가 아니라 복사본에 밑줄을 긋는 것과 같다.

### 약속을 바꿔야 할 때

혼자 바꾸지 않는다. 약속은 **최소 두 사람 사이의 합의** 라서, 한쪽이 조용히 바꾸면
반대쪽이 조용히 깨진다.

```
1. 바꿔야 할 이유를 상대 담당자에게 말한다
2. contracts/ 를 고친다
3. just gen
4. 양쪽 다 just check 가 초록인지 확인
5. just test-contract 로 실제로 맞물리는지 확인
```

## 6. AI에게 일을 시킬 때 지켜야 할 규칙

이 저장소는 사람과 AI가 같이 개발하는 것을 전제로 만들어졌다.
`AGENTS.md` 와 `CLAUDE.md` 가 있는 이유가 그것이다. 그래서 AI를 쓸 때의 규칙도
개발 규칙의 일부다.

### 6-1. 규칙 1 — 정해지지 않은 것은 AI가 정하지 않는다

> **정해지지 않은 부분이 나오면, AI는 추측해서 만들지 말고 반드시 담당 개발자에게
> 물어서 확인을 받는다.**

AI는 모르는 게 나와도 멈추지 않고 **가장 그럴듯한 것을 채워 넣는다.** 그리고 그 결과물은
그럴듯해서 리뷰에서도 잘 안 걸린다. 아무도 정한 적 없는 값이 정해진 것처럼 코드에 박힌다.
그래서 프롬프트에 적어야 한다. 안 적으면 AI는 알아서 채운다.

지킬 것은 세 가지다.

- **묻는 시점은 구현 전이다.** 다 만든 뒤에 물으면 이미 추측 위에 전부 쌓아 올린 뒤다.
- **"만들지 마라"는 빈칸을 넣으라는 뜻이 아니다.** 그 부분을 아예 손대지 않는다.
  임시값을 넣으면 반드시 살아남아 결정으로 굳는다.
- **멈춰도 된다.** 그 답에 매달린 일밖에 없으면 멈추는 게 맞다.
  멈춘 AI는 5분이면 다시 출발하지만, 잘못 쌓인 코드는 되돌리는 데 하루가 든다.

### 6-2. 규칙 2 — 레퍼런스로 mz2az 볼트를 준다

> **개발자는 AI에게 `mz2az` 폴더(옵시디언 볼트)를 레퍼런스로 지정해서,
> 기획·조사 내용을 직접 찾아보고 근거로 삼을 수 있게 프롬프트를 작성한다.**

`mz2az` 볼트에는 SceneTrip의 **기획서, 사용자 조사, 페르소나, 회의 기록, 지라 산출물** 이
전부 들어 있다. 코드 저장소에는 "어떻게 만드는가"가 있고, 볼트에는 **"왜 이렇게 만드는가"** 가 있다.
AI에게 볼트를 안 주면, AI는 "왜"를 모르는 채로 "어떻게"만 하게 된다.

볼트는 이런 구조다. 순서가 중요하다.

```
  03_MOC/index.md      ← 입구. 여기서 시작한다
        │
        │  관련 개념을 찾아 들어가면
        ▼
  02_Wiki/             ← 개념 하나당 노트 하나. 요약과 정리가 들어 있다
        │
        │  "이거 진짜 맞아?" 를 확인하려면
        ▼
  01_Raw/              ← 원본 그대로. 기획서, 설문 결과, 회의 녹취
                          ★ 사실 확인은 반드시 여기서 한다
```

- `01_Raw/` — **원본 그대로** 다. 요약도 해석도 없다. 사실인지 아닌지는 여기서만 확인된다.
- `02_Wiki/` — 개념을 하나씩 정리한 노트. 반드시 `01_Raw` 에 근거를 두고 쓴다.
- `03_MOC/index.md` — 전체 목차. 어디서 시작할지 모를 때 여는 문.

AI에게 이 순서를 알려줘야 하는 이유는, 안 알려주면 **볼트 전체를 뒤지느라 시간을 쓰거나,
02_Wiki 의 요약만 보고 그걸 사실로 믿기** 때문이다. 요약은 요약일 뿐이고,
근거는 `01_Raw` 에만 있다.

### 그리고 `JiraDocs/` — 티켓 번호로 들어가는 문

앞의 길이 **개념으로** 찾아가는 길이라면, `JiraDocs/` 는 **티켓 번호로** 찾아가는 문이다.
일을 시작할 때 손에 쥔 건 보통 티켓 번호이므로, 실제로는 여기를 제일 먼저 연다.

`MZ2AZ-{번호} {스토리명}.md` 형식으로, 그 티켓에서 **실제로 만들어진 것** 이 들어 있다.

```
  MZ2AZ-90   설문 조사
  MZ2AZ-91   브랜드 네이밍
  MZ2AZ-111  SceneTrip DB 스키마       ← 데이터 구조가 이미 설계돼 있다
  MZ2AZ-113  촬영지 데이터 수집
  MZ2AZ-114  외부 데이터 소스 확보 및 검토
  MZ2AZ-116  작품검색 목업 기능 명세    ← 화면 명세가 이미 있다
  MZ2AZ-140  촬영지 데이터 보완
  MZ2AZ-141  성지 필터링 작업기록
```

안 읽고 시작하면 **이미 있는 걸 또 만든다.** 스키마가 111에, 화면 명세가 116에 있는데
AI가 새로 지어낸다. 그럴듯하게 나오니 리뷰에서도 안 걸린다.

문서 안의 `> [!question] 확인 필요` 는 **아직 아무도 정하지 않았다** 는 표시다.
6-1의 규칙이 정확히 거기 걸린다.

작업이 끝나면 반대로 갱신한다. AI에게 **"MZ2AZ-NNN JiraDocs 갱신해줘"** 라고 하면
`JiraDocs/JiraDocs.md` 의 형식을 읽고 맞춰 쓴다.

### 6-3. 무엇을 물어야 하고 무엇은 안 물어도 되나

규칙 1을 잘못 적용하면 AI가 사소한 것까지 다 물어보느라 진도가 안 나간다.
경계는 이렇게 잡는다.

**반드시 물어야 하는 것 — "사람이 정하는 것"**

- 화면에 무엇이 어떤 순서로 보여야 하는가
- 데이터에 어떤 항목이 들어가고, 그중 뭐가 필수인가
- 오류가 났을 때 사용자에게 뭐라고 보여줄 것인가
- 숫자로 정해야 하는 정책 — 목록 개수, 유효 기간, 재시도 횟수
- 외부 서비스를 새로 붙이는 결정 (지도, 결제, 로그인)
- 개인정보를 어디에 얼마나 저장할 것인가
- 무거운 라이브러리를 새로 추가하는 결정

이것들의 공통점은 **코드를 봐도 답이 안 나온다** 는 것이다. 사람이 결정해야만 존재하는 값이다.

**물어보지 않아도 되는 것 — "이미 문서에 적혀 있는 것"**

- 파일을 어디에 둘지 → `AGENTS.md` 의 배치표에 있다
- 어떤 명령을 쓸지 → `just --list` 에 있다
- 커밋 메시지 형식 → `AGENTS.md` §7 에 있다
- 이름 짓는 규칙, 들여쓰기 → `AGENTS.md` §10 에 있다
- 테스트를 어느 레인에 넣을지 → 규칙이 정해져 있다

이건 물어보면 안 된다. **이미 정해진 것을 다시 묻는 것은 문서를 안 읽었다는 뜻** 이다.

**답을 기다리는 동안 계속 가도 되나 — 질문을 두 종류로 나눈다**

"물어보라"고만 해두면 다음 질문이 바로 따라온다. **답이 올 때까지 손 놓고 있어야 하나?**
그건 질문이 어떤 종류인지에 달렸다. 기준은 하나다 — **다른 일이 그 답에 매달려 있는가.**

**곁가지 질문** — 그 부분 하나만 비면 되는 것

> 버튼에 뭐라고 쓸지, 목록을 12개 보여줄지 20개 보여줄지, 빈 화면에 띄울 안내 문구

이런 건 답이 바뀌어도 **다른 코드를 다시 짤 일이 없다.** 물어놓고, 그 부분만 손대지 않은 채
나머지를 진행하면 된다.

**뼈대 질문** — 다른 일이 그 위에 얹히는 것

> 이 데이터에 어떤 항목이 들어가는가, 로그인이 필요한 기능인가,
> 이 목록의 정렬 기준이 무엇인가, 오프라인에서도 동작해야 하는가

이건 다르다. 답이 바뀌면 **약속(`contracts/`)이 바뀌고, 약속이 바뀌면 백엔드·앱·AI가
모두 다시 짠다.** 이 답을 모른 채로 "일단 진행"하면 진행할수록 손해가 커진다.
**여기서는 멈추는 것이 맞다.**

멈추는 걸 실패로 여기지 말자. 5분 멈춘 AI는 답을 받으면 바로 출발한다.
잘못된 뼈대 위에 하루치를 쌓은 AI는 하루를 버린다.

**답을 못 받았을 때 어떻게 하나**

그 부분은 **구현하지 않는다.** 이게 제일 중요하다.
"일단 이렇게 해두고 나중에 고치죠" 가 가장 비싼 선택지다. 임시로 넣은 값은 반드시 남고,
남은 뒤에는 그게 임시였다는 사실을 아무도 기억하지 못한다.

질문은 지라 티켓이나 PR 설명에 적는다. 코드 안에 `TODO` 로 숨기지 않는다 —
`AGENTS.md` 는 **추적 링크 없는 TODO를 금지** 하고 있다.

### 6-4. AI 결과물 검수 체크리스트

AI가 작업을 끝냈다고 하면, 합치기 전에 이것만 확인한다.

```
[ ] just check 를 실제로 돌렸는가? 출력을 보여줬는가?
    → "통과할 겁니다" 는 통과가 아니다. 돌린 결과를 봐야 한다.

[ ] 파일을 추가했다면 BUILD.bazel 도 같이 고쳤는가?
    → 이걸 빠뜨리는 게 이 저장소에서 가장 흔한 실수다.

[ ] 주고받는 데이터 모양이 바뀌었는데 contracts/ 를 안 고치지 않았는가?

[ ] 생성된 코드(just gen 산출물)를 손으로 고치지 않았는가?

[ ] 아무도 정한 적 없는 값이 슬쩍 들어가 있지 않은가?
    → 숫자, 화면 문구, 기본값을 특히 본다. 여기가 AI가 지어내는 자리다.

[ ] 비밀값(API 키, 토큰, 비밀번호)이 들어가지 않았는가? 테스트와 문서까지 본다.

[ ] 못 한 부분이 있으면 솔직히 말했는가?
    → 다 했다는 보고보다, 어디까지 했고 뭐가 막혔는지가 훨씬 쓸모 있다.
```

## 7. 한눈에 보는 요약

```
 프로젝트 전체 순서
 ───────────────────────────────────────────────

 약속 정하기        contracts/ 를 먼저 쓴다 → just gen
       │            ★ 여기서만 셋이 모인다
       │
 뼈대 만들기        just new-service / new-app-ios / new-app-android / new-agent
       │
 각자 개발          백엔드 · 앱 · AI 가 동시에, 서로 안 기다리고
       │
 맞물림 검사        just test-contract → just test-e2e
       │            ★ 여기서 다시 모인다
       │
 띄우고 지켜보기     just deploy → just logs → SigNoz
```

```
 하루의 흐름
 ───────────────────────────────────────────────

 아침에 켜고        just doctor
                        │
 뭘 만들 때         just new-service / new-app-ios / new-agent
                        │
 고치는 중          just build-module <모듈>
                    just test-module  <모듈>
                        │
 헷갈릴 때          just rdeps <타깃>      ← 누가 영향받나
                    just targets           ← 뭐가 있나
                        │
 넘기기 전          just fmt
                    just check      ★ 반드시 초록
                        │
 CI가 빨간불        just ci         ← 로컬에서 똑같이 재현
                        │
 실제로 띄워볼 때    just up → just image → just deploy → just logs
                        │
 안 될 때           just doctor → just clean → just clean-all
```

그리고 **막히면 그냥 `just`** 를 쳐 보자. 목록이 다 나온다.
AI에게 시킬 때는 맨 위의 세 줄짜리 프롬프트를 쓰면 된다.
