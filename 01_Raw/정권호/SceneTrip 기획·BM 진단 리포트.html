초판에서 정정된 것

무엇이 틀렸었나

초판 집계에 파싱 오류 두 건이 있었다. csv.DictReader가 중복 헤더를 병합해 분기 문항 한쪽(20명)이 통째로 사라졌고 — 그 20명이 방한 경험자 15명 + 예약 확정자 3명, 즉 이 문서가 타겟이라 부른 집단 전체였다. 또 복수응답 구분자를 ,로 잘못 써서(실제는 ;) 조합 응답이 쪼개지지 않았다.

  • 뒤집힘"탐색 고통이 약하다"는 반대였다. 실제로는 70.3%가 불편을 겪었고 언어 장벽이 42.2%로 1위다. 기획서 문제인식 3번을 교체하라는 초판 권고는 철회한다.
  • 반증됨"12.5%가 레퍼럴 고객"은 틀렸다. 그 8명 중 6명이 같은 설문에서 "아무것도 돈 낸 적 없음", 가이드 투어 지출자 0명, 7명이 계획 없음이다.
  • 보류"10달러 정정" 권고는 성급했다. 김상규 인용(7/13 Reddit)과 이 CSV(7/22 surveyswap)는 별개 설문일 가능성이 높다.
  • 교체"첫 상품 하나를 고른다"는 틀 자체를 버린다. eSIM 우선 권고는 철회하고, 화면 ↔ 상품 대응표로 대체한다. 화면마다 자연스러운 상품이 다르고, 클릭률은 여러 상품을 걸어야 배울 수 있다.
  • 불가초판 assignment는 실행 불가. 이메일 남긴 8명 중 예약·계획 확정자는 0명이다.

정정 후 결론

다섯 문장 요약

  • 01기획서의 언어 장벽 판단이 데이터로 가장 강하게 지지된다. 겪은 불편 1위가 언어 장벽(42.2%)이다. 다국어를 전제 조건으로 승격한 것은 옳았다.
  • 028/29 MVP1은 현재 범위로 불가능하다. 실가용 14 영업일에 3명. 커뮤니티를 넣으면 스토어 심사와 직렬로 묶인다.
  • 03레퍼럴 BM의 방향은 맞다. Trazy가 이미 작품 단위 투어를 팔고 있어 "전환 맥락이 명확하다"가 실행 가능함이 확인됐다. 상품은 하나로 고르지 말고 화면 ↔ 상품 대응표대로 붙인다.
  • 04이 단계 목표는 매출이 아니라 전환율이다. 3개월 안에 레퍼럴 매출은 사용자 1,000명당 $78 수준이다.
  • 05도달이 유일한 미해결 문제다. 69명 중 예약·계획 확정자는 3명뿐이고, 그 3명은 $11 이상 지불 의사 0명에 이메일도 남기지 않았다.

01_Raw/정권호/K-Content Travel — 90-Second Fan Survey (Anonymous).csv · 69건 · 27컬럼 · 2지 분기 구조

볼트 3곳(02_Wiki/Reddit 설문과 10달러 지불 의사.md, 02_Wiki/설문대행 이용.md, 04_Story/4막)이 "원본이 어디에도 없다"고 기록하고 있으나 사실이 아니다. 갱신이 필요하다.

3. 확정한 정체성과 전제

"우리 어플은 성지순례 여행 계획을 잡기 쉽도록 도와주는 서비스가 맞는 것 같아. 우리가 교통까지 제공해주게 되면 범위가 너무 커져."

여행 계획을 세우는 순간이 곧 투어·패스가 예약되는 순간이므로, 계획 도구로 범위를 확정하면 타겟과 수익 지점이 같은 자리에 놓인다. 다만 이것이 도달 문제를 푸는 것은 아니다 — 계획 중인 방한 확정자를 어떻게 만나느냐는 여전히 미해결이다.

  1. 여행 계획 도구다. 여행 중 기능은 MVP2 이후이거나 하지 않는다.
  2. MVP1 주력은 검색·지도와 코스다.
  3. 수익은 레퍼럴, 대상은 "계획 중인 방한 확정자". 앱 자체 유료화는 하지 않는다.
  4. 교통·영업시간은 자체 보유하지 않고 네이버 지도로 연결한다.
전제 4의 대가

방한 경험자가 꼽은 1위 불편이 대중교통 혼란(15명 중 7명)인데 이를 네이버에 위임한다. 지도 API 약관과 일정을 고려하면 옳은 판단이지만, SceneTrip의 가치가 "찾아주는 것"이지 "데려다주는 것"이 아니라는 점을 팀이 합의하고 있어야 한다.

레퍼럴로 걸 상품을 만들 필요가 없고, 기획서가 주장한 "우리는 어디에 어떤 순서로 가는지 알기에 전환 맥락이 명확하다"가 실행 가능함이 확인됐다. 눈물의 여왕 촬영지를 보는 사용자에게 눈물의 여왕 투어를 거는 것이 실제로 가능하다.

동시에 경쟁 신호다. Klook은 이미 Fandom Tour와 K-드라마 촬영지 블로그를 운영 중이다. 기획서 시장분석의 경쟁자 목록에 Klook·Trazy를 추가해야 한다 — K-Spot·DUCPIC·트리플보다 이쪽이 실질적 경쟁자다.

레퍼럴이 실제로 어떻게 돈이 되나

용어 혼선을 막기 위해 한 장면으로 적는다. 프랑스 거주 사용자가 Queen of Tears를 검색해 더현대 서울(극중 퀸즈 백화점) 상세 화면에 들어간다. 그 화면 맨 아래에 줄 하나가 붙는다.

누르면 Trazy 예약 페이지가 브라우저로 열린다. SceneTrip 안에서 결제하지 않으므로 자체 결제 모듈이 필요 없다. 링크 주소에 SceneTrip 식별 코드가 붙어 있어 Trazy가 유입 출처를 안다. 30일 안에 예약이 일어나면 Trazy가 SceneTrip에 약 4%(₩3,500)를 지급한다. 사용자 부담은 없다 — 파트너가 원래 마케팅비로 쓰는 예산에서 나간다.

화면 ↔ 상품 대응표

상품을 하나로 정하지 않는다. 화면마다 자연스러운 것이 다르므로 대응표를 미리 정해두고 그대로 붙인다. 즉흥으로 붙이면 광고판이 된다.

  3. 파트너는 둘까지. Klook 하나로 투어·패스·입장권·액티비티가 커버되고, Trazy는 작품 단위 투어 때문에 추가한다. 어필리에이트는 회사마다 가입·승인·링크 형식·대시보드가 따로라 늘릴수록 3명에게 부담이다

이 방식은 기획서의 원래 원칙과 일치한다 — "광고성 무차별 노출이 아니라 해당 작품·동선과 연관된 상품만 큐레이션하여 신뢰도 유지".

초판 수정 — "측정을 위해 하나로 집중"은 약한 논리였다

클릭 → 예약 전환율은 상품을 하나로 몰아도 이 트래픽 규모에서 유의미한 숫자가 나오지 않는다. 반면 노출 → 클릭률은 훨씬 적은 표본으로 측정 가능하고, 화면 종류별로 배우려면 오히려 여러 상품을 걸어야 한다. 대응표 방식이 배움의 양에서 더 낫다.

중간발표에 들고 갈 숫자는 화면 종류별 클릭률로 잡는다.

초판 철회

eSIM 우선 권고를 거둔다

초판은 "첫 레퍼럴 상품은 투어가 아니라 eSIM(수수료 20%, 구매율 거의 전원)"을 최대 발견으로 제시했다. 세 가지 문제가 있다.

  • 구매율 "거의 전원"은 설문에 문항이 없는 추정이다. 투어 쪽 22%는 실측치인데 한쪽만 가정을 썼고, 투어에는 전환율 2%를 곱하면서 eSIM에는 아무것도 곱하지 않았다.
  • 귀속이 어렵다. eSIM은 대개 항공권 예약 직후 Klook·Airalo에서 직접, 혹은 공항에서 산다. 쿠키 30일 안에 SceneTrip을 거칠 이유가 없다.
  • 이 기획의 방어논리를 무효화한다. "어디에 어떤 순서로 가는지 안다"는 우위가 eSIM에는 아무 값도 갖지 못한다. 눈물의 여왕 촬영지를 보는 사용자에게 유심칩을 들이미는 것은 여행 블로그도 똑같이 할 수 있다.

영영 배제하는 것은 아니다. 위 대응표에 "여행 준비 체크리스트" 같은 화면이 생기면 그때 붙인다. 우선순위가 낮을 뿐이다.

5. 이 단계 목표는 매출이 아니다

수수료 6.5%, 투어 객단가 $60, 노출 대비 예약 전환 2%(여행 어필리에이트로는 낙관적)를 가정하면 사용자 1,000명당 약 $78. MVP1에 사용자 1,000명을 모으는 것 자체가 도전인데, 모아도 10만 원 남짓이다.

3개월 안에 의미 있는 매출은 나지 않으며, 목표를 매출로 잡으면 반드시 실패한다. 목표는 전환율이라는 숫자를 실측하는 것이어야 한다. 정문창 멘토가 요구한 바와 같다.

패스·단품 가격과 구매 전환율(%) 목표를 숫자로 제시하고 조기 실측할 것
범위 변경으로 기록할 것

기획서 부록 A는 "MVP1에서는 상품 노출 영역만 UI에 확보하고, 실제 제휴 링크 연동은 MVP2에서 붙인다"로 정해 두었다. 링크와 이벤트 추적을 MVP1으로 당기려면 "기존 방침 그대로"가 아니라 명시적 범위 변경으로 기록해야 한다. 파트너 승인, 이벤트 수집, 노출 UI 정책(부록 C #15 미결)이 딸려 온다.

6. 8/29 MVP1은 현재 범위로 불가능하다

실제 가용 평일은 14 영업일이다. 8/4~8/8(5) + 8/11~8/14(4, 광복절 제외) + 8/24~8/28(5). 8/17~21은 AWS 교육 주간. "3주"는 과대 표기다.

이 14일에 들어가야 하는 것: 촬영지 데이터셋 구축 + 별칭·로마자 검색 + 지도 뷰포트 탐색 + 편집 가능 코스 + 커뮤니티 + OAuth + 마이페이지 + 3개국어 + Flutter 크로스 플랫폼. 학생 3명 기준, 각 대형 기능에 1인당 5영업일 미만이 배정되는 셈이다.

놓친 선행 조건 둘
  • 부록 C #0 "초기 수집 대상 작품 목록 확정" 미결. 성공지표 1("쿼리셋 100개에서 90% 정답 반환")은 정답이 존재해야 측정 가능한데, 촬영지 DB가 없으면 정답이 없다.
  • 부록 C #4 "작품 별칭 저장 방식" 보류. 최소 진입점으로 고른 "별칭·배우명·로마자 검색"이 이 보류 항목에 물려 있다.
직렬 연결 위험

앱스토어·구글플레이 심사가 커뮤니티 구현 이후 단계에 배치돼 있다(기획서 210행). 커뮤니티를 MVP1에 넣으면 8/29 마감이 스토어 심사와 직렬로 묶인다.

제안

8/29 MVP1을 검색 + 지도 + 코스 조회·편집 + 익명 사용으로 자르고, 로그인·마이페이지·커뮤니티·어필리에이트를 9월 버퍼(8/31~9/12)로 미룬다. 이미 "주력은 검색·지도와 코스"라고 판정했으므로 판정과 범위를 일치시키는 것뿐이다.

8. 한 장으로

바꾸지 않아도 되는 것

레퍼럴 BM의 방향은 맞다. MVP1이 검색·지도를 주력으로 잡은 것도, 다국어를 전제 조건으로 올린 것도 데이터와 일치한다. 설문도 잘 만들었다.

바꿔야 하는 것

딱 하나다 — MVP1 범위. 14 영업일에 6개 기능은 성립하지 않고, 커뮤니티가 스토어 심사를 마감에 물고 온다.

이 문서를 어떻게 쓰나

  • 팀 회의 — 6번(실현 가능성)을 띄워놓고 무엇을 9월로 미룰지 정한다
  • 멘토 미팅 — 정문창 멘토에게는 5번(전환율이 목표), 김상규 멘토에게는 2번의 언어 장벽 표
  • 중간발표 — 언어 장벽 42.2%를 문제인식의 축으로 쓴다. 데이터가 가장 강하게 받치는 지점이다
숫자를 인용할 때 반드시 지킬 것

CSV는 27컬럼, 분기 문항 5쌍이 중복 헤더다. csv.DictReader로 읽으면 중복 키가 병합돼 한쪽 분기가 통째로 사라진다 — 이 문서 초판이 그렇게 틀렸다. csv.reader로 인덱스를 직접 다룰 것. 복수응답 구분자는 ;다.

문항별 응답 수가 다르다(n=15 / 20 / 44 / 55 / 56 / 64 / 69). 분모를 항상 함께 밝힐 것. 표본은 자기선택된 온라인 팬 집단이며, n=69에서 60.9%의 95% 신뢰구간은 대략 ±12pp, n=15에서 46.7%는 ±25pp다. 소수점 표기가 데이터에 없는 정밀도를 암시한다.

응답자 구성: 여성 72%(41/57), 18–24세 24/57, 거주지 유럽 23·북미 14·동남아 14. 동아시아는 3명 — 다국어 계획의 일본어 근거는 이 데이터에 없다.
