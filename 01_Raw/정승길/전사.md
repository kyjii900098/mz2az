# 전사 — 원본에서 위키까지 작업 계획

> [!important] 이 문서의 상태
> **계획 단계다. 전사도 아토믹화도 아직 실행하지 않았다.**
> 이 문서는 무엇을·어떤 순서로·어떤 규칙으로 할지 먼저 확정하기 위한 설계도이며, 승인 후 실행한다.

- 작성: 2026-07-29 (정승길)
- 대상: mz2az 볼트 `01_Raw` 전체 + `정승길/history` 아카이브
- 최종 목표: 팀 세 사람이 흩어놓은 기록을 하나의 검증 가능한 지식망으로 만들고, 그 위에 SceneTrip이 어떻게 여기까지 왔는지 서사를 얹는다.

## 0. 볼트 루트 `CLAUDE.md` 와의 관계

볼트 루트에 이미 `CLAUDE.md` 가 있지만, 그건 **멘토가 다른 볼트에서 쓰던 규칙을 그대로 가져온 것** 이다. 일반적인 PKM 파이프라인으로는 맞지만 우리 자료의 실제 모양과 어긋나는 부분이 있다. 이 문서가 mz2az 실정에 맞춘 실행 규칙이고, 충돌하면 **이 문서를 우선** 한다.

| 항목 | 루트 CLAUDE.md | 이 계획 |
| --- | --- | --- |
| 단계 | `01_Raw` → `02_Wiki` → `03_MOC` (3단계) | `01_Raw` → **전사** → `02_Wiki` → `04_Story` (4단계) |
| 전사 위치 | 원본과 같은 폴더 | **`정승길/전사/`** 로 분리, 원본 폴더 무오염 |
| 3단계 성격 | MOC (링크 목록 색인) | **Story** (5막 전 과정 기록 + 다중 인덱스) |
| 노트 길이 | "300~500자 내외" 고정 | 개념에 필요한 만큼. 한 노트 = 한 개념이 기준이지 글자 수가 기준이 아니다 |
| `status` | 예시가 `stable` 로 되어 있음 | LLM이 만든 노트는 **예외 없이 `draft`**, 사람이 검증해야 `stable` |
| 작성자 추적 | 없음 | `author` 속성 필수 — 누가 쓴 기록인지가 중복 판별의 핵심이다 |
| 날짜 | 없음 | `date` 속성 필수 — 04_Story가 시간순이라 없으면 서사를 못 만든다 |

세 번째 줄이 특히 중요하다. 우리가 만들려는 3단계는 "노트 목록"이 아니라 **"애니 성지순례에서 어떻게 SceneTrip이 됐는가"를 읽을 수 있는 글** 이다. 그래서 MOC가 아니라 Story다.

## 1. 파이프라인

```
01_Raw/                   원본. 절대 수정하지 않는다.
  ├ 김태환/               (pdf·docx·hwp·md 등 원래 포맷 그대로)
  ├ 정권호/
  ├ 정승길/history/       ← 시간순 정리 완료. 동결(freeze).
  └ Project/
        │
        │  ① 전사 — 무손실. 해석 금지. 포맷만 .md로.
        ▼
정승길/전사/               위키화의 유일한 입력원.
  ├ 김태환/
  ├ 정권호/
  ├ 정승길/
  └ Project/
        │
        │  ② 아토믹화 — 개념 단위로 쪼개고 중복 병합.
        ▼
02_Wiki/                   플랫 구조. 폴더 만들지 않는다.
        │
        │  ③ 서사화 — 시간순으로 엮고 의사결정 계보를 밝힌다.
        ▼
04_Story/
```

**각 단계의 불변 규칙**

- ① 전사는 **내용을 바꾸지 않는다.** 요약·정정·재배열 금지. 오탈자도 그대로 둔다. 판단이 들어가는 순간 원본 대조가 불가능해진다.
- ② 아토믹화는 **전사본에 있는 사실만** 쓴다. 없는 내용을 채우지 않는다. 추론은 반드시 `해석`으로 표시한다.
- ③ 서사화는 **위키 노트를 링크로 엮어서** 쓴다. Story에서 새로운 사실을 만들지 않는다.

## 2. 전사 폴더 구조

```
정승길/전사/
  ├ 00_입력원 목록.md      전사본 전체 색인 (원본 경로·작성자·날짜·전사 방식)
  ├ 김태환/
  ├ 정권호/
  ├ 정승길/
  └ Project/               팀 공동 산출물·외부 문서(사무국·멘토)
```

팀원 이름으로 나누는 이유는 정리 편의가 아니라 **중복을 눈으로 보기 위해서** 다. 같은 회의를 세 사람이 각자 적은 기록이 나란히 있어야, 아토믹화할 때 무엇이 합쳐지고 무엇이 그 사람만 적어둔 고유 정보인지 판별할 수 있다.

> [!check] 결정됨 — history는 전사 폴더로 **복사한다**
> `정승길/history/` 의 md 61개를 번호를 유지한 채 `전사/정승길/` 로 복사한다. 두 폴더의 역할이 이렇게 갈린다.
>
> - `history/` = **손대지 않는 금고.** 시간순 아카이브. 이후 수정 금지(freeze)
> - `전사/정승길/` = **작업대.** frontmatter 정규화·판본 표시 등 가공은 여기서만 한다
>
> 이렇게 해야 위키화가 `전사/` 한 폴더만 보면 되고, 작업 중 실수가 나도 금고에서 되살릴 수 있다.

## 5. 전사 규칙

### frontmatter 양식

```yaml
---
source: "[[원본 파일명]]"
source_path: "01_Raw/Project/피보팅/평가의견.pdf"
author: 정승길 | 김태환 | 정권호 | 팀공동 | 외부-사무국 | 외부-멘토
date: 2026-07-13          # 자료가 만들어진 날짜. 추정이면 date_est 로 쓴다
type: raw-transcription
method: vision-transcription | text-extraction | ocr | stt | native-md
visual_review: pending | complete | n-a
---
```

`author` 와 `date` 는 루트 CLAUDE.md에 없는 항목이고, 이 두 개가 없으면 중복 판별(§6)과 Story 작성이 불가능하다. **반드시 채운다.**

### method 표기 — 실제보다 좋게 쓰지 않는다

| 값 | 언제 쓰나 |
| --- | --- |
| `vision-transcription` | 페이지 **이미지를 실제로 보고** 표·수식·도식까지 전사했을 때만 |
| `text-extraction` | pdf/docx 텍스트 레이어만 뽑았을 때. 표가 깨져 있을 수 있다 |
| `ocr` | 이미지 pdf를 광학 인식했을 때 |
| `stt` | 음성을 받아썼을 때 |
| `native-md` | 원래 마크다운이라 변환하지 않았을 때 |

텍스트 추출만 한 문서는 `visual_review: pending` 으로 둔다. 표·도식을 원본과 대조한 뒤에만 `complete` 로 올린다. **pending인 전사본의 표를 근거로 위키 노트를 쓰지 않는다** — 원본을 열어 확인한다.

### 본문 규칙

- 페이지·슬라이드가 바뀌면 `## p{번호}` 로 구분한다
- 표·글머리·각주 구조를 최대한 마크다운으로 살린다
- 이미지는 `![이미지: 제목, 축, 범례, 도형 관계, 판독 가능한 텍스트]` 로 **무엇이 그려져 있는지** 적는다. 파일명만 적지 않는다
- 판독이 불확실하면 확정해 쓰지 말고 `> [!question] 판독 불확실` 로 남긴다
- 강조 뒤에 조사가 오면 `**단어** 다` 처럼 한 칸 띄운다 (렌더링 깨짐 방지)

## 6. 중복과 판본 충돌 — 이미 발생해 있다

조사해보니 같은 원본을 두 사람이 각각 전사해둔 게 이미 있다.

| 원본 | 판본 1 | 판본 2 | 실제 차이 |
| --- | --- | --- | --- |
| 기획서(mz2az).pdf | `Project/피보팅/` · `text-extraction` · 24,923B | `history/41_` · `vision-transcription` · 28,985B | vision 판본이 4KB 더 많다. 표를 살렸기 때문 |
| (김상규)멘토 의견서.pdf | `Project/피보팅/` · `text-extraction` | `history/41_` · `vision-transcription` | text 판본은 표가 2열로 뭉개졌고, vision 판본은 원본대로 4열 |
| 평가의견.pdf | `Project/피보팅/` · 8,511B | `history/31_` · 8,486B | 서식 차이 |

### 정본 선택 규칙

1. **`vision-transcription` 이 `text-extraction` 을 이긴다.** 표 손실 여부가 갈린다.
2. 같은 method면 **나중 것 또는 더 긴 것** 을 정본으로 하되, 짧은 쪽에만 있는 내용이 없는지 diff로 확인한다.
3. 정본이 아닌 판본은 **지우지 않는다.** 전사본 frontmatter에 `superseded_by: "[[정본 파일명]]"` 을 달아 관계만 기록한다.
4. 위키 노트는 **정본만 출처로 인용** 한다.

### 내용 중복 (다른 종류)

같은 회의를 세 사람이 각자 적은 것, 같은 문서가 노션 워크스페이스 두 곳에 남은 것(`03_(06.02)아이디어 모아모아` ↔ `02_(06.02)아이디어 취합 및 투표`, `19_아이디어 설명서` ↔ `20_아이디어 설명서 사본`)이 있다. 이건 판본 충돌이 아니라 **관점 차이** 다. 전사 단계에서는 **합치지 않고 그대로 둔다.** 병합은 ②에서 개념 단위로 판단할 일이다. 셋 다 같은 말을 하면 노트 하나가 되고, 한 사람만 적어둔 게 있으면 그게 오히려 귀한 정보다.

## 7. ② 02_Wiki — 아토믹화 (아직 실행 안 함)

- 플랫 구조. 폴더를 만들지 않는다. 분류는 링크와 속성이 한다
- 노트 제목은 자료명이 아니라 **다시 찾을 개념명** 으로 짓는다. `(06.13) 박정두 멘토님` 이 아니라 `저작권 회피형 미디어 배치 전략` 처럼
- 한 개념이 여러 자료에 나오면 노트 하나에 출처를 여러 개 단다. **이게 중복이 사라지는 지점이다**
- `status: draft` 로 시작. 사람이 원본 대조를 마쳐야 `stable`

### 위키 노트 frontmatter

§9의 다중 인덱스를 **손으로 나열하지 않고 쿼리로 자동 생성** 하려면 속성이 있어야 한다. 아래 속성이 인덱스의 재료다.

```yaml
---
title: "저작권 회피형 미디어 배치 전략"
type: concept | decision | feedback | artifact
status: draft
date: 2026-06-13              # 이 내용이 나온 시점
act: 2                        # 1~5막 (§8)
mentor: ["박정두", "박병선"]    # 피드백/멘토링에서 나온 내용이면 발화자 전원
topic: ["저작권", "데이터확보"]
adopted: yes | partial | no | pending
adopted_note: "공식 링크·임베드 방식으로 부분 반영. 사용자 업로드 검수 플로우는 미착수"
source: ["[[전사본 파일명]]"]
related: []
---
```

- `mentor` — 멘토별 인덱스의 근거. 한 회의에서 여러 명이 말했으면 전원 기재
- `adopted` — **이번 정리의 핵심 동기.** 좋은 피드백을 받고도 반영 못 한 게 많으니, 무엇을 왜 못 했는지가 남아야 한다. `no`·`partial`이면 `adopted_note` 필수
- `act` — Story 5막 중 어디에 속하는지

예상 노트 축: 아이디어 후보와 투표 / 성지순례→K-콘텐츠 전환 / 저작권 대응 / 데이터 확보 전략 / 타겟 정의 / AI 기술 축 / BM / MVP 범위 / 피벗 경위 / 설문 설계와 결과 / IA 전환(지도-first→콘텐츠-first) / 스프린트 운영

## 8. ③ 04_Story — 전 과정 기록

### 성격: 요약이 아니라 완전 기록

Story는 **줄이는 글이 아니다.** 주제를 정하던 날부터 오늘 데이터 수집까지, 거쳐온 것을 하나도 빠뜨리지 않고 남기는 게 목적이다. 후보로 올랐다가 탈락한 아이디어도, 반영하지 못한 피드백도 전부 들어간다. 나중에 "그때 왜 그렇게 했지"를 되짚을 수 있어야 한다.

### 서술 원칙

- **사실은 위키에, 서사는 Story에.** Story 본문은 흐름과 인과를 쓰고, 사실 데이터는 위키 노트로 링크한다
- **중복 게재보다 링크.** 같은 내용을 여러 막에 반복하지 않는다. 시간순으로 쌓아 올리려면 각 사실이 한 군데에만 있어야 나중에 고칠 때 어긋나지 않는다. 다만 그 막을 읽는 데 꼭 필요한 수치·결론 한두 줄은 인용해도 된다
- **Story에서 새 사실을 만들지 않는다.** 위키에 없는 내용이 Story에 나오면 근거를 잃는다
- **연결은 양방향으로.** 관련된 막·노트끼리 서로 링크를 걸어 어느 쪽에서 들어와도 읽힌다

### 설문 결과 자리

설문 결과 데이터는 아직 정리되지 않았다. 4막에 **자리를 미리 비워두고**, 결과가 나오면 이렇게 넣는다.

1. 순수 결과 데이터는 `02_Wiki/설문조사 결과.md` 노트로 만든다 (문항·응답 수·주요 수치)
2. 4막 본문에서는 **링크로 참조** 하고, 서사에 필요한 핵심 수치 한두 줄만 인용한다
3. 결과가 늦게 도착해도 **4막에 넣는다.** 실제 시점이 데이터 수집보다 앞서므로 시간순 위치는 4막이 맞다
4. 결과가 기획에 영향을 줬다면 그 판단은 5막 이후에 링크로 잇는다
