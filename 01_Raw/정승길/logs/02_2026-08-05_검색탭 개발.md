## 1. 작업 기기 이전 — 맥북프로 → 맥북에어

맥북프로에서 만들던 Flutter 프로젝트를 맥북에어로 옮겼다. Dropbox 동기화를 운반 수단으로만 썼고, 옮긴 뒤에는 Dropbox 밖으로 빼냈다.

맥북에어에 처음부터 깐 것은 다음과 같다.

| 항목 | 버전 | 비고 |
| --- | --- | --- |
| Xcode | 26.6 | App Store 설치. iOS 시뮬레이터는 별도 다운로드다 |
| iOS 시뮬레이터 런타임 | 26.5 (8.52GB) | `xcodebuild -downloadPlatform iOS` |
| Flutter SDK | 3.44.8 (Dart 3.12.2) | `brew install --cask flutter` |
| CocoaPods | 1.17.0 | `brew install cocoapods` |

Xcode를 설치한 직후에는 터미널이 아직 Xcode를 보지 못한다. `xcode-select` 가 예전 Command Line Tools를 가리키고 있어서 `xcodebuild` 와 `simctl` 이 전부 실패한다. 아래 한 줄로 전환해야 한다.

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
sudo xcodebuild -license accept
sudo xcodebuild -runFirstLaunch
```

## 2. Dropbox 안에서는 iOS 빌드가 안 된다

Dropbox 폴더에 둔 채로 빌드하니 코드 서명 단계에서 죽었다.

```
Flutter.framework/Flutter: resource fork, Finder information, or similar detritus not allowed
Failed to codesign .../Flutter.framework/Flutter with identity -.
```

원인은 Dropbox의 CloudStorage 파일 프로바이더(macOS가 클라우드 폴더를 다루는 시스템 구성 요소)가 파일에 `com.apple.provenance` 라는 확장 속성을 붙이는 것이다. `codesign` 은 이런 속성이 붙은 바이너리를 거부한다. `xattr -c` 로 지워도 다시 붙어서 지워지지 않는다. Flutter도 빌드 중에 스스로 지우려 시도하지만 똑같이 실패한다.

**해결: 프로젝트를 `/Users/gil/workspace/mobile` 로 옮겼다.** Dropbox 밖으로 나오자 기본 설정 그대로 빌드가 통과했다.

> [!warning] 이 프로젝트를 Dropbox·iCloud 같은 동기화 폴더 안에 두지 말 것
> 맥 사이를 옮길 때는 git이나 일회성 복사를 쓴다. 1주차 로그에서 저장소를 Dropbox에서 workspace로 옮긴 것과 같은 이유이며, 그때는 git 충돌이 이유였고 이번에는 코드 서명이 이유다.

굳이 동기화 폴더에서 빌드해야 한다면 `flutter config --build-dir=<Dropbox 밖으로 나가는 상대경로>` 로 산출물만 빼내는 우회가 있다. 다만 이 설정은 전역이고 상대경로만 받아서 다른 프로젝트를 깨뜨리므로 권하지 않는다.

## 4. 배우로 검색되게 만들었다

기존 검색은 작품 제목과 별칭만 봤다. 그래서 "김수현"을 쳐도 아무것도 나오지 않았다. 매칭 대상을 **출연·감독·주소** 까지 넓혔다.

배우를 검색하면 이제 세 곳이 함께 반응한다.

- 작품 탭에는 그 배우가 나온 작품이 나온다.
- 장소 탭에는 그 작품들의 촬영지가 전부 나온다.
- 시트 맨 위에 `김수현 · 배우 · 작품 2 · 촬영지 140` 같은 요약 줄이 뜬다.

자동완성에는 **인물** 섹션이 따로 생겼다. 배우로 걸린 작품은 제목으로 걸린 작품과 구분해야 읽기 편해서 `출연 김수현` 배지를 달았다.

`cast` 컬럼은 `"김수현, 김지원"` 처럼 한 칸에 여러 이름이 들어 있다. 이것을 사람 단위로 뒤집어 `Person` 으로 만들었다. V6 164행에서 배우 14명이 나온다.

## 5. 연관 검색어 — 별칭 컬럼에 몰아넣지 않았다

네이버 검색창처럼 연관 검색어를 띄우려면 검색 가능한 낱말 목록이 필요하다. 이것을 `title_aliases` 에 전부 밀어넣는 방법을 먼저 검토했고, **쓰지 않기로 했다.**

별칭 컬럼은 "그 작품의 다른 표기"라는 뜻이 분명한 자리다. 여기에 배우·지역·장르까지 넣으면 두 가지 문제가 생긴다. 첫째, 컬럼의 의미가 뭉개져서 나중에 별칭만 따로 쓸 수 없다. 둘째, 배우 한 명이 작품 10편에 나오면 이름이 10번 중복 저장되고, 그 배우 정보가 바뀌면 10군데를 고쳐야 한다.

**대신 이미 있는 컬럼에서 검색어를 파생시킨다.** 앱이 데이터를 읽는 시점에 아래를 한 번 훑어 검색어 사전을 만든다.

| 갈래 | 출처 컬럼 |
| --- | --- |
| 작품 | `title`, `title_aliases` |
| 인물 | `title_cast`, `title_director` |
| 장소 | `place_name` |
| 지역 | `place_address` 앞 두 토막 (예: `서울`, `마포구`) |
| 장르·채널 | `title_genre`, `title_network` |

별칭 컬럼은 지금 형태를 그대로 유지하면 된다. 케데헌의 `KPop Demon Hunters;K-Pop Demon Hunters;케데헌;KPDH;KDH` 처럼 작품의 다른 표기만 담는다.

화면에서는 검색창을 탭하면 추천 검색어가 먼저 깔리고, 글자를 치면 작품 → 인물 → 장소 → 연관 검색어 순으로 나온다. 칩을 누르면 그 낱말로 다시 검색된다.

> [!important] 정정 (8/5 저녁) — 서버는 이미 이렇게 만들고 있었다
> 처음에 "작품만 주는 자동완성 API 로는 이 화면을 못 채운다"고 적었는데 **틀렸다.** 근거로 삼은 것이 [[01_MVP1 프론트 테크 스펙 (초안)]] §5 의 내 요청 목록이었고, 권호가 실제로 만든 계약(`contracts/openapi/scene-api-v1.yaml`)을 안 봤다.
>
> 실제 계약은 이 화면이 필요로 하는 것을 거의 다 갖고 있다. `GET /search/suggestions` 는 장소·작품·**인물**을 `type` 으로 구분해 함께 돌려주고, `GET /contents?q=` 는 인물 이름에 걸리며, `GET /contents?personId=` 로 인물을 정확히 지목할 수도 있다. 랭킹 규칙(앞글자 우선, 인기도순)까지 내가 프론트에서 정한 것과 같다. 서버 스키마의 `search_term` 도 다섯 곳을 합친 MATERIALIZED VIEW 라, §5 에서 내가 "데이터에서 파생시킨다"고 한 것과 같은 구조다.
>
> **진짜 빈 곳은 하나뿐이다** — `GET /places` 에 인물 조건이 없다. 파라미터가 `q`·`contentId`·`bbox`·좌표·`sort` 뿐이고 `q` 는 인물 이름에 걸리지 않는다. 그래서 배우를 검색하면 작품 탭은 채워지지만 **장소 탭이 빈다.** `GET /places` 에 `personId` 를 더하자고 권호와 합의해야 한다. 상세는 저장소의 [계획서 §4](https://github.com/mz2az/SceneTrip/blob/main/docs/project/plans/mobile-ios-search-tab.md) 에 적었다.

## 6. 검색 결과를 지도에 반영

검색 결과가 시트 목록에만 반영되고 지도 핀은 첫 화면의 인기 촬영지 그대로였다. 목록과 지도가 서로 다른 것을 보여주고 있었다. 검색이 확정되면 핀을 결과 촬영지로 갈고 그 범위에 맞춰 카메라를 움직이게 했다.

판단이 갈릴 만한 두 가지는 이렇게 정했다.

- **글자를 칠 때마다 갱신하지 않는다.** 핀 아이콘을 위젯에서 이미지로 굽는 구조라(`NOverlayImage.fromWidget`) 타이핑마다 수십 개를 다시 그리면 화면이 버벅인다. 추천어를 고르거나 엔터를 친 시점에만 갱신한다.
- **카테고리 칩은 목록만 좁히고 지도는 건드리지 않는다.** 칩을 눌렀을 때 지도에서 핀이 사라지면 오히려 혼란스럽다고 봤다. 팀 의견이 다르면 바꾼다.

## 7. 최근 검색어

검색한 낱말을 최대 10개까지 남긴다. 같은 낱말을 다시 검색하면 중복 없이 맨 위로 올라오고, 칩마다 붙은 ×로 하나씩 지우거나 '전체 삭제'로 비울 수 있다.

`shared_preferences`(기기에 간단한 값을 저장하는 Flutter 패키지)를 붙여 **앱을 껐다 켜도 남게** 했다. 저장은 화면을 막지 않도록 백그라운드로 던지고, 저장소 읽기나 쓰기가 실패해도 목록은 메모리 기준으로 그대로 동작한다.

장바구니는 여전히 메모리에만 있다. 최근 검색어는 로그인 없이도 개인 기기에 남는 것이 자연스러워 먼저 영속화했고, 장바구니는 로그인·서버 이관 때 `saved_place` 로 함께 처리하는 편이 낫다고 봤다.

## 10. 모노레포에 넣으려다 발견한 것 — Flutter 는 이 저장소에 못 들어간다

작업 폴더를 모노레포 `SceneTrip/apps/mobile` 로 옮기려고 저장소 규칙을 읽다가 막혔다.

**`docs/architecture/adr/0002-product-stack-spring-python-native-mobile.md`** 는 `status: accepted` 이고, 본문에 이렇게 적혀 있다.

> 크로스 플랫폼 프레임워크(Flutter · React Native)를 쓰지 않는다. iOS 앱과 Android 앱은 코드를 공유하지 않는 별개의 모듈이며, 두 앱이 공유하는 것은 `contracts/` 의 정의다.

검토한 대안 표에 "Flutter 로 iOS·Android 를 한 번에"가 명시적으로 기각돼 있다. 기각 사유는 유지보수되는 Bazel 규칙이 없어서 저장소 제1법칙("Bazel 이 모든 것을 빌드한다")과 정면 충돌한다는 것이다.

이 ADR 은 **권호(`jkh1447`)가 8/4 에 MZ2AZ-157 작업 중 커밋 `64cb637` 로 넣었다.** 팀이 8/3 스프린트 회의에서 Flutter 로 정한 바로 다음 날이다. 저장소 도구도 이 결정을 따라 바뀌어 있어서, 1주차에 썼던 `just new-app mobile dart` 는 지금 없고 `just new-app-ios` 와 `just new-app-android` 만 있다. `MODULE.bazel`·`justfile`·CI 어디에도 Flutter 나 Dart 문자열이 하나도 없다.

**결정: ADR 0002 를 따른다.** Flutter 로 만든 것은 프로토타입으로 남기고, 같은 화면을 iOS 네이티브(Swift)로 다시 만들어 모노레포에 넣는다.

- Flutter 프로젝트는 `~/workspace/mobile` 에 그대로 둔다. 모노레포 밖이라 git 이 서로 얽히지 않는다.
- 넘어가는 것은 코드가 아니라 **화면 설계·데이터 모델·검색 규칙** 이다. Flutter 를 Swift 로 바꿔주는 변환기는 없다. 이 문서 §4~8 이 그 명세 역할을 한다.

Swift 로 가면서 새로 드는 비용은 이렇다.

| 항목 | 내용 |
| --- | --- |
| Bazel Apple 규칙 활성화 | `MODULE.bazel` 에서 `apple_support`·`rules_swift`·`rules_apple` 이 전부 주석 처리돼 있다. 첫 iOS 모듈을 만드는 사람이 푼다 |
| 팀원 장비 | ADR 경고 — `apple_support` 를 선언만 해도 **정식 Xcode 가 없는 맥에서는 `bazel build //...` 전체가 크래시한다.** 빌드에 참여하는 모든 맥에 Xcode 설치가 필요하다 |
| CI | 지금 CI 는 `ubuntu-latest` 에서만 돈다. iOS 빌드는 macOS 러너가 있어야 한다 (ADR 0002 의 후속 작업에도 적혀 있다) |
| 안드로이드 | Flutter 는 두 플랫폼을 한 번에 줬지만 네이티브는 Kotlin 앱을 따로 만든다. ADR 도 "모바일 기능을 두 번 만든다"를 감수 비용으로 명시했다 |
| 폴더 이름 | `MODULE.bazel` 주석의 규칙은 `apps/<name>-ios/` 다. `apps/mobile` 이 아니다 |

> [!question] 확인 필요 — 지라 티켓을 언제 닫을지
> Flutter 로 동작한다고 티켓을 닫으면 보드는 완료인데 `main` 에는 아무것도 없는 상태가 된다. 그 티켓들의 산출물이 Swift 앱이라면 **Swift 구현이 머지된 뒤에 닫는 것이 맞다.** 팀이 프로토타입 단계를 별도 티켓으로 인정하는지 확인이 필요하다.

## 11. 저장소 git 규칙 (`docs/engineering/onboarding.md` §12)

GitHub Flow 에 JIRA 를 붙인 방식이다. 앞으로 이걸 지켜서 올린다.

- `main` 에 직접 커밋하지 않는다. 브랜치를 파고 **PR 로만** 머지한다.
- 브랜치 이름은 JIRA 티켓 키에 짧은 설명을 붙인다 — `MZ2AZ-91-브랜드-네이밍`.
- 커밋 메시지는 `<type>: <명령형 요약> (<JIRA-KEY>)` 형식이다. type 은 `feat` `fix` `docs` `refactor` `test` `chore`. 예: `feat: 지도 SDK 적용 (MZ2AZ-10)`.
- PR 제목은 `[<JIRA-KEY>] <type>: <요약>` 이다.
- 커밋 전에 `just check` 가 초록이어야 한다.

브랜치 안에서는 커밋을 얼마나 자주 찍든 상관없다. "커밋 하나에 논리적 변경 하나"는 `main` 에 남는 이력 기준이므로, 되돌릴 지점을 원하는 만큼 만들어 두고 PR 올릴 때 정리하면 된다.
