## 1. 전제부터 고쳐야 한다

**"제공이 안 된다"가 아니라 "저장이 안 된다"이다.** 이 둘은 완전히 다르고,
구분하는 순간 설계가 풀린다.

Google Places API 정책 기준:

| 항목 | 저장(캐싱) | 화면 표시 |
|---|---|---|
| `place_id` | ✅ 무기한 | ✅ |
| 좌표 | 🔶 최대 30일 | ✅ |
| **리뷰 · 사진 · 메뉴 · 평점 · 전화번호** | ❌ 금지 | ✅ **라이브 호출 + 어트리뷰션 표시 시 허용** |

카카오·네이버가 막은 것도 정확히 같은 지점이다. 7/27 회의에서 "1시간 캐싱조차 반려된
사례가 있다"고 공유된 건 **전수 저장**을 전제했기 때문이다. 화면에 띄우는 것 자체는
원래 막지 않는다 — 그게 API의 존재 이유다.

## 2. 데이터 3계층

| 계층 | 소스 | 저장 | 쓰임 |
|---|---|---|---|
| **1 · 우리 자산** | 직접 수집한 촬영지 | ✅ 영구 | 핀, 장바구니, 루트(핀 순서), 찜, 자체 리뷰 |
| **2 · 공공데이터** | **TourAPI**(한국관광공사), 소상공인시장진흥공단 | ✅ 영구 | 맛집·카페 후보 풀. **상호·좌표·주소·전화·영업시간·휴무일·대표메뉴·주차·이미지·소개문** 까지 전부 여기서 나온다 |
| **3 · 라이브 호출** | Google Places, ODsay, 카카오 | ❌ `place_id`만 | **리뷰·평점**, 경로 |

> [!important] 7/28 조사로 바뀐 것 — 3계층의 역할이 줄었다
> 초안에서는 **리뷰·사진·메뉴** 를 묶어 3계층(Google Places)에 뒀는데, 실제로 확인해보니
> **사진·메뉴·영업시간까지 TourAPI가 준다.** Google Places가 반드시 필요한 것은
> **리뷰·평점뿐** 이다 (TourAPI는 공공기관 작성 데이터라 UGC가 애초에 없다).
> → 유료 라이브 호출 범위가 좁아지므로 **§6 리스크 2(비용)가 상당히 완화** 된다.

### 2계층이 핵심이다 — TourAPI

아직 검토 안 된 소스인데 이 프로젝트에 거의 맞춤이다:

- 관광 데이터 15종 약 26만 건, **음식점 포함** (개요·이미지·대표메뉴)
- **다국어 제공 (국·영·일·중)** ← 외국인 대상 + 다국어 확정이라 결정적
- 공공데이터라 **저장·재배포 자유** (공공누리)
- `data.go.kr`에서 인증키 발급 — 국문 서비스는 `15101578`, 영문은 `15101753`. 개발계정 **1,000회/일**

#### 음식점·카페를 어떻게 꺼내는가 (2026-07-28 확인)

음식점은 **별도 API가 아니다.** 관광지·숙박·음식점이 전부 같은 엔드포인트를 쓰고
**`contentTypeId` 파라미터로만 구분** 된다. 국문(KorService2) 기준:

| ID | 타입 | ID | 타입 |
|---|---|---|---|
| 12 | 관광지 | 28 | 레포츠 |
| 14 | 문화시설 | 32 | 숙박 |
| 15 | 축제·공연·행사 | 38 | 쇼핑 |
| 25 | 여행코스 | **39** | **음식점** |

**카페 전용 코드는 없다.** 39 안의 서비스분류코드 3단계로 들어간다:

```
cat1 = A05          음식
cat2 = A0502        음식점
cat3 = A05020900    카페 / 전통찻집     ← 카페만 뽑을 때
                    (A05020100 한식 / A05020200 서양식 / A05020300 일식 / A05020400 중식 …)
```

우리가 쓸 호출은 **촬영지 좌표 주변 검색** 이므로 `locationBasedList2`가 정확히 맞는다:

```
http://apis.data.go.kr/B551011/KorService2/locationBasedList2
  ?serviceKey={키}&MobileOS=ETC&MobileApp=SceneTrip&_type=json
  &mapX=129.1586&mapY=35.1587    ← 촬영지 좌표
  &radius=1000                    ← 반경(m)
  &contentTypeId=39               ← 음식점
```

⚠️ TourAPI **4.0은 오퍼레이션 접미사가 `2`**, 구버전 3.0은 `1`(`locationBasedList1`)이다.
블로그 예제 대부분이 3.0 기준이라 그대로 복붙하면 안 된다.

#### 어디까지 주는가 — 이름·좌표만이 아니다

오퍼레이션 3개를 이어 붙이면 상세 화면이 거의 채워진다:

| 오퍼레이션 | 얻는 것 |
|---|---|
| `detailCommon2` | 상호, 주소, 좌표, 전화, 대표이미지, 홈페이지, **소개문(overview)**, 분류코드 |
| **`detailIntro2`** (39 전용) | **영업시간**(`opentimefood`, 브레이크·라스트오더 포함), **휴무일**(`restdatefood`), **대표메뉴**(`firstmenu`), 취급메뉴(`treatmenu`), 주차(`parkingfood`), 포장(`packing`), 예약(`reservationfood`), 좌석·규모(`seat`/`scalefood`), 금연·카드 여부 |
| `detailImage2` | 추가 이미지 목록 |

실물 확인(대구 산채식당, `contentId=1845322`): 상호·주소·전화 + `11:00~21:00 / 브레이크 16–17시 /
라스트오더 19:30` + 월요일 휴무 + 무료주차 + 대표메뉴 산채비빔밥 + 취급메뉴(버섯전골·오리·닭)
+ 인허가번호 + 개업연도(1995) + 재료 수급 방식 설명문까지 나온다.

#### 없는 것 — 리뷰와 평점

**후기·별점은 없다.** 공공기관이 작성·검수한 소개 데이터라 사용자 생성 콘텐츠가 존재하지 않는다.
7/27 회의 미결 **#7(평점·리뷰 수급)은 TourAPI로 해결되지 않는다** — §7 참조.

### 3계층은 저장하지 않는다

루트에 저장하는 것은 **`place_id` + 상호명 + 좌표**뿐이다.
사용자가 핀을 탭하면 그때 Google Places를 라이브 호출해 **리뷰·평점** 을 붙인다.
(사진·메뉴·영업시간은 2계층에서 이미 확보되므로 라이브 호출 대상이 아니다.)
합법이고, 업데이트 부담도 사라진다.

## 3. 라우팅 API

| API | 대중교통 | 자동차 | 도보 | 비고 |
|---|---|---|---|---|
| **ODsay LIVE** | ✅ | — | — | **국내 대중교통 경로는 사실상 여기뿐** |
| 카카오모빌리티 | ❌ | ✅ | ✅ | **대중교통 경로 없음** |
| TAGO (국토부) | 🔶 | — | — | 정류소·노선·도착정보만. **경로탐색 없음** |

방한민 멘토가 제안한 **오디세이 + 카카오** 조합이 맞다.
대중교통은 ODsay, 도보·자동차는 카카오모빌리티.

### ODsay 운영정책 (직접 확인)

- 무료(Basic) **1,000회/일** — 개인·학생·5인 이하 스타트업, 앱 등록 후 6개월
- Standard **100,000회/일** (유료, 가격 문의)
- 유료 앱 서비스 자체는 **허용**. 단 광고 결합은 제한
- 결과 데이터 저장은 "**회사의 사전 동의 없이**" 금지 → 협의 여지 있음
- **타사 지도 표출 제약은 명시 없음.** ODsay 표기 의무만 있음

### 경로는 애초에 저장할 필요가 없다

루트에 저장할 것은 **핀의 순서**뿐이고, 경로선은 열 때마다 계산한다.
저장 금지 조항을 우회가 아니라 정면으로 피해간다.

```
Route = [ {place_id, type: spot|food, order}, ... ]   ← 우리 DB에 저장
경로선  = 열 때마다 ODsay / 카카오모빌리티 호출          ← 저장 안 함
```

⚠️ **무료 1,000회/일은 9월 중간발표 데모에서 터질 수 있다.**
루트 하나 열 때마다 구간 수만큼 호출된다. 유료 문의를 미리 해둘 것.

## 4. 지도 SDK — 오해 정리

> "다른 앱들은 구글맵이나 카카오맵을 새로 열게 한다. 우리는 앱 하나로 하고 싶다"

**"카카오맵 앱을 여는 것"과 "카카오맵 SDK를 우리 앱에 임베드하는 것"은 전혀 다르다.**
후자는 정상적인 사용법이고, "앱 하나로 끝난다"는 요건을 그대로 만족한다.
지도 타일을 직접 만들 필요는 없다 — 그건 불가능하다.

다만 확인이 필요하다: 한국은 정밀지도 국외 반출 규제 때문에 **Google Maps가 한국 내
상세 길찾기(특히 자동차)를 제대로 못 한다.** 외국인 사용자는 Google Maps에 익숙한데
정작 한국에선 안 되는 상황이라 **이게 오히려 우리 앱의 존재 이유가 된다.**
대신 카카오맵 SDK의 영문·일문 지원 수준은 직접 확인해야 한다.

## 5. 실시간 루트 수정 (MVP2)

루트가 배열이므로 수정은 원소 삽입이다.

```
기존:  A → B → C
삽입:  A → 맛집 → B → C     (배열에 끼워넣고 경로 재계산)
```

챗봇 동작 순서:

1. 현재 위치 반경으로 **2계층(TourAPI + 소상공인)**에서 후보를 검색 — 저장된 데이터라 빠르고 무료
   (`locationBasedList2` + `contentTypeId=39`. 카페만이면 `cat3=A05020900`)
2. 후보 카드에 **사진·대표메뉴·영업시간·휴무일을 바로 표시** — 2계층 데이터라 호출 비용 0
3. 사용자가 고르면 **3계층(Google Places)** 라이브 호출로 **리뷰·평점만** 붙임
4. 루트 배열에 삽입 → **ODsay/카카오모빌리티** 재호출로 경로선 갱신

7/27 회의에서 **MVP1 = 여행 전 / MVP2 = 여행 중**으로 나눈 것이 정확했다.
8/29 MVP1까지는 **핀 → 장바구니 → 루트 순서 → 경로 표시**까지만 해도 벅차다.

## 6. 리스크 (정직하게)

1. **직접 하면 정확도 책임이 우리에게 온다.** 다른 앱이 카카오맵으로 던지는 건
   게을러서가 아니라 그 책임을 안 지려는 것이다. 환승 정보가 틀리면 클레임은 우리가 받는다.
2. ~~**Google Places는 호출당 과금**이고 리뷰·사진 필드는 특히 비싸다.~~
   **[7/28 완화]** 사진·메뉴·영업시간을 TourAPI가 대신하므로 라이브 호출은 **리뷰·평점 전용** 으로 좁혀진다.
   여전히 **사용자가 핀을 탭할 때만** 호출한다는 원칙은 유지.
3. **TourAPI 음식점 커버리지·최신성은 직접 확인 필요.** ← **가장 큰 미검증 리스크**
   26만 건이 전부 음식점은 아니고, 관광지 위주라 로컬 맛집은 얇을 수 있다.
   필드는 충분한 것이 확인됐으므로 **남은 문제는 "그 식당이 등재돼 있는가" 하나** 다. 검증 방법은 §9.
4. ODsay 무료 한도 → 유료 전환 시점과 비용이 미확인.
5. **[추가] 다국어 서비스의 `contentTypeId` 체계가 국문과 다를 수 있다.**
   영문 TourAPI 예제에서 음식점이 **`82`** 로 쓰이는 사례가 확인된다(76 관광지 / 80 숙박 계열).
   4.0에서 국문과 통합됐는지 문서로 확정하지 못했다. **TourAPI를 채택한 근거 자체가 다국어이므로
   여기가 깨지면 §2 전체가 흔들린다** — 최우선 확인 대상.
6. **[추가] 영문·일문 DB 건수는 국문보다 훨씬 적다.**
   "26만 건"은 국문 전체(15종) 기준이지 음식점만도, 다국어도 아니다. 실제 다국어 커버리지는 별도 측정 필요.

## 7. 회의 미결 항목에 대한 답

| 미결 | 답 |
|---|---|
| **#3 음식점/카페 전략** | 전수 저장 대신 **2계층(공공, 저장) + 3계층(라이브, 미저장)** 조합. 꺼내는 방법은 `contentTypeId=39`(+카페는 `cat3=A05020900`) — §2 확인 완료. **단, 커버리지 검증 결과에 따라 7/27 확정안(수동 큐레이션)으로 되돌아갈 수 있다** (§9) |
| **#6 경로 API 선택** | ODsay(대중교통) + 카카오모빌리티(도보·자동차). 멘토 제안이 맞음 |
| **#7 평점·리뷰 수급** | **우리가 저장하지 않는다.** Google Places를 라이브로 띄우고, 우리 DB에는 **외국인 자체 리뷰**만 쌓는다 — "외국인 리뷰 DB가 해자"라는 회의 인식과 같은 방향.<br>**[7/28 보강]** TourAPI에는 리뷰·평점이 아예 없음을 확인했으므로, 이 미결은 **공공데이터로 우회할 수 없고** 위 구조가 사실상 유일한 답이다 |
| **#8 AI를 어디에 쓸 것인가** | 챗봇 맛집 추천(MVP2) + 루트 자동 생성(고도화). 수집 단계 AI는 이미 사용 중 |

### 덤으로 다시 논의할 것 — 영업시간

7/27 회의는 **영업시간을 넣지 않기로 확정** 했다. 근거는 *"책임져야 할 부분이 너무 많아진다"* 였지
**저장 금지 때문이 아니었다.**

그런데 TourAPI 영업시간(`opentimefood`)은 **공공데이터라 저장이 합법이고, 출처가 한국관광공사** 다.
`modifiedtime`과 함께 **"한국관광공사 제공 · N월 기준"** 으로 표기하면 정확도 책임이 우리에게 오지 않는다.
기획서에서 영업시간을 뺀 대가로 "네이버 지도로 나가야 함"을 감수하고 있는데,
**외국인이 한국어 네이버 지도로 튕겨나가는 것** 이 이 서비스에서 더 큰 손실일 수 있다.

→ **8/1(토) 스프린트 리뷰 안건으로 재론 제안.** 결정을 뒤집자는 게 아니라, 전제가 달라졌으므로
   같은 결론이 유지되는지 한 번 확인하자는 것.

## 8. 멘토링 질문 후보 (방한민 멘토)

1. **ODsay 유료 전환 시점과 비용** — 무료 1,000회/일로 데모가 가능한가
2. **외국인 대상인데 카카오맵 SDK 다국어가 충분한가** — 아니면 네이버 지도 SDK인가
3. **TourAPI로 맛집 커버리지가 나오는가** — 필드는 충분함을 확인했으므로(§2), 질문은
   **"촬영지 주변 로컬 맛집이 실제로 등재돼 있는가"** 로 좁혀졌다. 등재율이 낮으면
   ① 소상공인 상권 DB로 보완할지 ② 7/27 확정안대로 수동 큐레이션으로 갈지
4. **[추가] TourAPI 다국어 서비스의 실제 데이터 밀도** — 영문·일문 DB가 국문 대비 얼마나 얇은가.
   멘토가 공공데이터 실무 경험이 있다면 바로 답이 나올 수 있는 부분
