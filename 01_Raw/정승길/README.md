# 정승길 작업 폴더 — 무엇을 어디에 두는가

이 폴더의 배치 규칙이다. 새 파일을 만들기 전에 여기를 보고 자리를 고른다.
`worklog` 스킬이 이 문서를 정본으로 삼는다.

## 두 갈래로 나눈다

기록을 **스프린트 산출물** 과 **작업 로그** 로 나눈다. 기준은 "다음 주에도 읽을
것인가" 다.

| | `N주차_주제/` | `logs/` |
| --- | --- | --- |
| 무엇 | 그 주 스프린트의 **산출물과 결론** | 날마다 **한 일과 배운 것** |
| 수명 | 그 주가 끝나도 참조된다 | 그날의 기록. 나중엔 경위를 찾을 때만 본다 |
| 단위 | 주 | 하루 |
| 예 | 테크 스펙, 데이터 결과물, 설계 결정 | "오늘 pull 이 막혔고 원인은 이것이었다" |
| 갱신 | 결론이 바뀌면 **고친다** | 원문은 두고 **정정 블록을 덧붙인다** |

같은 사실이 둘 다에 들어갈 수 있다. 스프린트 문서에는 **결론만**, 로그에는
**어떻게 거기 도달했는지** 를 쓴다. 로그가 없으면 결론의 근거를 다시 찾지 못하고,
스프린트 문서가 없으면 결론이 로그 더미에 묻힌다.

## 폴더

```
01_Raw/정승길/
├── README.md              ← 이 파일 (배치 규칙 정본)
├── logs/                  ← 날마다 쌓는 작업 로그
├── 1주차_data/            ← 스프린트 산출물 (주차별)
├── 2주차_검색탭개발/
├── 3주차_.../             ← 새 주가 시작되면 만든다
├── history/               ← 프로젝트 착수 이전 기록. 아카이브, 새로 쓰지 않는다
├── 전사/                  ← 원본 문서의 무손실 전사본
└── 이미지/
```

팀 공용 회의록은 **이 폴더가 아니라** `00_기록/` 에 있다 — Daily(태환작성),
Sprint(권호작성), SSoma(승길작성). 내 개인 기록만 여기 둔다.

## 이름 규칙

### 주차 폴더 — `N주차_주제`

```
1주차_data
2주차_검색탭개발
3주차_...
```

숫자 뒤에 **그 주가 무엇에 관한 주였는지** 를 붙인다. 나중에 목록만 보고 "몇 주차에
뭘 했나" 를 알 수 있게 하려는 것이다. 주제는 스프린트 회의에서 정해진 그 주의
주제를 쓴다.

주차 폴더 안의 문서는 `NN_제목.md` 로 앞에 두 자리 번호를 붙인다 — 읽는 순서를
고정하기 위해서다.

### 로그 — `NN_YYYY-MM-DD_제목.md`

```
01_2026-08-03_세팅.md
02_2026-08-05_검색탭 개발.md
03_2026-08-06_지라 정리와 네이티브 전환.md
```

- `NN` 은 **연속 번호** 다. 날짜가 아니라 이 번호가 순서를 정한다. 하루에 로그가
  둘이면 번호만 늘린다.
- 날짜는 **작업한 날** 이다. 다음 날 새벽까지 이어졌으면 시작한 날로 적는다.
- 제목은 그날 무엇을 했는지 한 덩어리로 — "세팅", "검색탭 개발" 처럼 짧게.

번호를 쓰는 이유는 대화에서 "2번 로그" 로 부를 수 있어서다. 파일을 새로 끼워 넣기
위해 기존 번호를 다시 매기지 않는다 — 위키링크가 전부 깨진다.

> [!warning] 1주차 로그는 예외로 `1주차_data/logs/` 에 있다
> 날짜 우선 이름(`2026-07-30-1600-...`)을 쓰고 위치도 다르다. 옮기지 않는 이유는
> `전사/정승길/1주차_data/logs/` 에 그 파일들의 전사 미러가 있고 `source_path:` 로
> 경로가 박혀 있어서다. 옮기면 그 연결이 끊긴다. **2주차부터의 규칙이 위의 것이고,
> 1주차 로그는 그 자리에 그대로 둔다.**

## 로그 문서의 골격

프런트매터를 쓰지 않는다. 첫 줄이 제목이고 그 아래 인용 블록이 머리말이다.

```markdown
# 03. 2026-08-06 — 지라 정리와 네이티브 전환

> 한 일을 한두 문장으로.
> 작업자: 정승길 (Claude Code 보조)
> 관련 문서: [[…]], [[…]]

## 1. 첫 번째 덩어리

## 2. 두 번째 덩어리

...

## 다음에 할 일

| # | 항목 |

## 미결 사항

| # | 항목 | 상태 |
```

절 번호를 매기는 이유는 다른 문서에서 `§4` 로 가리키기 위해서다. 실제로 스프린트
문서와 지라 티켓이 로그의 절 번호를 참조한다.

### 로그에 반드시 남기는 것

1. **막혔던 것과 그 원인.** 에러 메시지를 그대로 붙인다. 같은 에러를 다시 만났을 때
   검색으로 찾을 수 있어야 한다.
2. **판단이 갈렸던 지점과 고른 이유.** "A 로 했다" 가 아니라 "B 는 …라서 A 로 했다".
3. **틀렸던 것.** 잘못 안 것을 지우지 말고 정정 블록으로 덧붙인다. 왜 틀렸는지가
   다음에 같은 실수를 막는다.
4. **버전·명령어·경로.** 나중에 재현할 수 있게 그대로 적는다.

### 이전 로그가 뒤집혔을 때

**원문을 고치지 않는다.** 그 자리에 콜아웃을 덧붙이고 새 로그를 가리킨다.

```markdown
> [!important] 이 판단을 뒤집었다 (8/6)
> 무엇이 바뀌었는지, 왜 바뀌었는지.
> 상세는 [[03_2026-08-06_지라 정리와 네이티브 전환]] §7 참고.
```

콜아웃 종류는 뜻에 맞춰 고른다 — `[!done]` 해결됨, `[!important]` 판단 뒤집힘,
`[!warning]` 내가 틀렸음, `[!note]` 보충.

미결 사항 표는 지우지 말고 **"8/6 이후" 열을 덧붙여** 무엇이 어떻게 됐는지 적는다.
이렇게 하면 그날의 판단과 그 뒤의 결과를 한 표에서 볼 수 있다.

## 글쓰기 규칙

볼트 루트 `CLAUDE.md` 의 "Writing for the reader" 를 따른다. 특히 자주 걸리는 것 셋:

- **주어를 적는다.** "저장 후 검증한다" → "서버가 저장한 뒤 클라이언트가 응답을 검증한다".
- **처음 나오는 용어는 풀어 준다.** "MCP(AI 도구가 외부 서비스에 붙는 표준 규약)".
- **표로 끝내지 않는다.** 표 앞뒤에 그 표가 무엇을 뜻하는지 문장으로 적는다.

굵은 글씨 뒤에 조사가 붙으면 사이에 공백을 넣는다 — `**단어** 다` (`**단어**다` 아님).
