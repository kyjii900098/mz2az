## 2. "149 브랜치도 checkout 해줄래?" 가 무슨 뜻인지

백엔드 브랜치를 프론트인 내가 왜 checkout 하냐는 의문이 있었는데, 정리하면 이렇다.

- **checkout 은 내 작업 폴더를 그 브랜치 시점의 코드로 전환하는 것** 이다. 그 작업을 내가 맡는다는 뜻이 아니라 "그 코드 상태를 로컬에서 보고 실행해 본다"는 뜻이다.
- 모노레포에서는 프론트가 백엔드 브랜치를 checkout 할 이유가 있다 — 계약(`contracts/openapi/`)이 어떻게 바뀌는지 미리 보고, 새 백엔드를 로컬에 띄워 프론트를 붙여 볼 수 있다.
- **그런데 지금은 할 필요가 없다.** `git merge-base --is-ancestor` 로 확인하니 `origin/MZ2AZ-149-검색-백엔드-보강` 의 커밋은 전부 `main` 에 이미 포함돼 있다. 브랜치와 `main` 의 diff 가 0 이라 checkout 해도 지금 코드와 같다. 머지 전에 나온 요청이었거나 머지된 것을 모르고 한 말로 보인다.

## 4. 바젤 문답 — 착수 3단계가 각각 무엇인지

팀 모두 Bazel 이 처음이라, 착수 전에 개념을 물어 정리했다. 답변은 Claude(sonnet 서브에이전트)가 실제 파일(`MODULE.bazel`, `tools/just/scaffold.just`, `tools/scripts/new-module.sh`, 계획서 §5)을 읽고 작성했다.

### 4-1. MODULE.bazel 이 뭐 하는 파일인가

`package.json` 이 npm 의존성을, `build.gradle` 이 Gradle 의존성을 선언하듯, `MODULE.bazel` 은 저장소가 쓰는 **외부 의존성을 선언하는 유일한 곳** 이다 (`MODULE.bazel:3`). 이 저장소는 "쓸 언어의 규칙만, 필요해지는 시점에" 넣는 원칙이라(`MODULE.bazel:8-9`), 지금은 Java(Spring)용 규칙만 켜져 있고 Swift·Kotlin 규칙은 적어만 두고 꺼져 있다.

### 4-2. "Apple 블록"과 "활성화"의 실체

Apple 블록은 파일 맨 아래(228~244줄)에 **주석으로** 대기하고 있는 다섯 줄이다.

```python
# Swift — iOS 앱 (apps/<name>-ios/), 공유 라이브러리 (libs/swift/):
#   bazel_dep(name = "apple_support", version = "2.8.0")
#   bazel_dep(name = "rules_swift", version = "3.6.1")
#   bazel_dep(name = "rules_apple", version = "4.5.3")
#   bazel_dep(name = "rules_swift_package_manager", version = "0.34.0")
```

`bazel_dep` 은 "이 규칙 패키지를 쓰겠다"는 선언으로, npm `dependencies` 항목 하나와 역할이 같다. **"활성화"는 true/false 플래그를 바꾸는 것이 아니라 줄 앞의 `#` 을 지우는 것** 이다. 주석인 동안 Bazel 에게 그 줄은 존재하지 않는다.

활성화하지 않으면: Swift 를 컴파일할 규칙 자체가 없어서 `swift_library`·`ios_application` 같은 타깃을 BUILD 파일에 적을 수조차 없다.

활성화하면: 다음 빌드 때 Bazel 이 룰셋들을 내려받는다. 부작용이 하나 있는데 `MODULE.bazel:239-244` 가 실측으로 적어 뒀다 — `apple_support` 를 선언하기만 해도 Bazel 이 iOS 타깃 유무와 무관하게 모든 로컬 액션 전에 Xcode 버전을 확인하고, 정식 Xcode 없이 Command Line Tools 만 있으면 그 확인이 실패해 **저장소 전체 빌드가 FATAL 크래시로 죽는다** (`DottedVersion` 파싱 실패). 그래서 계획서가 "팀 공지 먼저"를 걸어 뒀던 것이고, §3 대로 이 관문은 이미 통과다.

후속 절차: `#` 을 푼 뒤 `just deps-update`(내부는 `bazel mod tidy`)로 잠금 파일 `MODULE.bazel.lock` 을 갱신하고, **lock 파일 diff 를 같은 커밋에 넣는다.**

### 4-3. `just new-app-ios scenetrip-ios` 가 하는 일

`just` 는 명령어 모음집(Makefile 의 사촌)이고, 이 저장소의 규칙은 "bazel 을 직접 치지 말고 항상 just 레시피를 거친다"이다. `new-app-ios` 레시피(`tools/just/scaffold.just`)는 내부적으로 `./tools/scripts/new-module.sh app scenetrip-ios swift` 를 부른다.

1. 이름 검사(kebab-case)와 조합(app + swift) 검사
2. `apps/scenetrip-ios/` 아래 `src/` · `tests/` · `deploy/` 생성
3. 템플릿 렌더링 — `README.md`(빈 뼈대) · `BUILD.bazel`(`filegroup` 만 있는 자리표시자)
4. 빈 폴더에 `.gitkeep`, 끝나면 "다음 할 일 3가지" 출력

즉 **폴더 구조와 뼈대를 균일하게 찍어 주는 명령** 이지 동작하는 앱을 만들어 주지 않는다. 실제 Swift 타깃은 손으로 채운다.

### 4-4. `target_compatible_with = ["@platforms//os:macos"]` 가 하는 일

Bazel 의 "타깃"은 빌드 가능한 단위 하나하나다 — 라이브러리 하나, 바이너리 하나, 테스트 하나가 각각 타깃이다. 이 선언을 타깃에 붙이면 "이 타깃은 macOS 에서만 지어진다"를 코드에 적는 것이 되고, 리눅스 CI 러너가 `bazel test //...`(저장소 전체)를 돌릴 때 Bazel 이 호환되지 않는 타깃을 **에러 없이 자동으로 건너뛴다.**

이게 없으면 리눅스 러너가 iOS 타깃을 빌드하려다 실패해 CI 전체가 빨개진다. 계획서 §5-3 의 표현대로 이것은 검사 회피가 아니라 **"이 타깃의 실행 환경 제약을 코드에 적는 것"** 이다. Android 타깃에는 붙이지 않는다 — 리눅스에서도 지어지므로 붙이면 오히려 기존 ubuntu 잡의 검사 범위에서 빠진다.

## 5. 지라 MCP 를 이 맥에도 등록했다

3번 로그 §2 에서 지라 MCP 를 등록했는데, **이 맥의 `claude mcp list` 에는 atlassian 이 없었다.** `--scope user` 등록은 그 기기의 `~/.claude.json` 에 쓰이는 것이라 **기기 단위** 다 — 한 맥에서 등록해도 다른 맥에는 없다.

같은 명령으로 이 맥에도 등록하고 브라우저 인증까지 마쳤다.

```bash
claude mcp add --transport http --scope user \
  atlassian https://mcp.atlassian.com/v1/mcp/authv2
```

3번 로그 §2 의 함정 그대로, 등록·인증해도 진행 중인 세션에는 도구가 바로 보이지 않는다 — MCP 도구 목록은 세션 시작 때 읽히므로 다음 세션부터 쓸 수 있다.
