## 1. pull 이 막혔다 — 내 미커밋 파일 때문

권호가 올린 커밋을 받으려는데 git 이 거부했다.

```
error: Your local changes to the following files would be overwritten by merge:
	docs/project/plans/README.md
```

저장소가 깨진 것이 아니라 **안전장치가 작동한 것** 이다. 어제 계획서를 쓰면서 계획 인덱스(`docs/project/plans/README.md`)의 표에 한 줄을 추가해 두고 커밋하지 않았는데, 권호가 올린 커밋 중 하나도 **같은 표, 같은 줄** 에 자기 항목을 추가했다. git 은 머지하면 내 미커밋 변경이 사라지는 상황을 감지하면 멈춘다.

해결은 세 단계다.

```bash
git stash push -m "설명" <파일>   # 내 변경을 잠시 치워 둔다
git pull --ff-only                # 원격을 받는다
git stash pop                     # 내 변경을 다시 얹는다
```

`stash pop` 에서 예상대로 그 한 줄이 충돌했고, 두 줄을 다 살리는 쪽으로 손으로 풀었다.

> [!tip] 미커밋 변경을 오래 들고 있지 않는다
> 이 문제의 근본 원인은 계획서를 쓰고 하루 동안 커밋하지 않은 것이다. 팀이 같은 파일을 건드리는 저장소에서는 작업 단위가 끝날 때마다 브랜치에 커밋해 두는 편이 낫다.

## 2. 지라를 Claude Code 에 연결했다

지금까지 Claude 는 지라를 볼 수 없었다. 그래서 티켓 내용을 물으면 "확인할 수 없다"고 답했다.

원인은 단순했다 — **한 번도 등록한 적이 없었다.** 연결이 끊긴 것이 아니라 처음부터 없었다.

```bash
claude mcp add --transport http --scope user \
  atlassian https://mcp.atlassian.com/v1/mcp/authv2
```

MCP(Model Context Protocol, AI 도구가 외부 서비스에 붙는 표준 규약) 서버로 아틀라시안 공식 원격 서버를 등록했다. 등록 후 `/mcp` 명령에서 **Authenticate** 를 눌러 브라우저로 아틀라시안 로그인을 하면 붙는다.

주의할 점 두 가지가 있었다.

| 함정 | 내용 |
| --- | --- |
| 옛 주소는 죽었다 | `https://mcp.atlassian.com/v1/sse` 는 **2026년 6월 30일에 지원 종료** 됐다. 검색하면 아직 이 주소가 많이 나온다 |
| 등록 직후에는 안 보인다 | MCP 서버 목록은 세션이 시작될 때 한 번 읽는다. 등록한 뒤 `claude --continue` 로 세션을 다시 열어야 목록에 나타난다 |

이 맥에는 Node 가 깔려 있지 않다(`npx` 없음). npm 기반 MCP 서버는 못 쓰므로, 이렇게 HTTP 로 직접 붙는 원격 서버가 오히려 맞았다.

## 3. MZ2AZ-148 이 ADR 과 어긋나 있었다

지라를 읽자마자 문제가 보였다. **MZ2AZ-148 「목업 기반 프론트 구현 (Flutter)」** 의 본문 "확정된 전제"에 이렇게 적혀 있었다.

> - 프론트: Flutter (Dart)
> - 지도: 네이버 지도 SDK (Flutter 포팅 패키지)

8/3 스프린트 회의 기준이라 당시에는 맞았지만, 8/4 에 [[02_2026-08-05_검색탭 개발]] §10 에서 발견한 ADR 0002 가 이것을 뒤집었다.

**중요한 것은 이게 새로 내릴 결정이 아니었다는 점이다.** 권호가 이미 **MZ2AZ-183 「문서·스캐폴딩을 실제 기술 스택(Java/Swift/Kotlin/Python)에 맞게 정정」** 을 만들어 완료 처리해 뒀다. 본문에 "실제 스택(백엔드 Java/Spring Boot, **iOS Swift, Android Kotlin**, AI 에이전트 Python)과 어긋나 있던 것을 정정"이라고 적혀 있다.

즉 팀 스택은 이미 정정됐는데 **148 과 그 서브태스크만 따라오지 못한 상태** 였다. 보드가 결정을 반영하지 못하고 있었던 것이다.

## 5. 계획서를 쓰고 PR 을 냈다

저장소 규칙(CLAUDE.md §3)은 모듈 둘 이상에 걸치거나 100줄을 넘는 변경에 **코드보다 계획서를 먼저** 쓰라고 한다. iOS·Android 두 앱에 Bazel·CI 까지 걸리므로 해당한다.

문서만 바뀌고 코드·계약·빌드 설정은 건드리지 않았다.

### 브랜치·커밋 규칙이 어제 바뀌어 있었다

권호가 8/6 새벽에 `AGENTS.md` §7.2~7.3 을 고쳤다(커밋 `990d1a3`). 어제 로그 §11 에 적어 둔 것과 다르다.

| | 어제 로그 §11 | **현재 규칙** |
| --- | --- | --- |
| 브랜치 | JIRA 티켓 키 | **스토리 또는 작업 키** — 서브태스크 키는 안 된다 |
| 커밋 | JIRA 티켓 키 | **그 변경이 실제로 속한 서브태스크 키** |

근거는 "브랜치가 곧 PR 이고 PR 이 리뷰 단위" 라는 것이다. 서브태스크마다 브랜치를 만들면 리뷰가 잘게 쪼개지고 보드에서 스토리 진척이 안 보인다. 그래서 이번 PR 은 이렇게 했다.

```
브랜치  MZ2AZ-148-목업-기반-프론트-구현      ← 스토리 키
커밋    docs: ... (MZ2AZ-159)                ← 서브태스크 키
PR 제목 [MZ2AZ-148] 검색 탭 네이티브 구현 계획
```

## 6. 어제 "빈 곳"이라고 적은 것을 권호가 이미 메웠다

어제 §5 정정 블록에 **"진짜 빈 곳은 하나뿐이다 — `GET /places` 에 인물 조건이 없다"** 고 적고, `personId` 파라미터를 추가해 달라고 요청할 생각이었다. 오늘 다시 확인하니 **이미 해결돼 있었다.**

권호가 커밋 `499c5d1`(MZ2AZ-167)에서 고쳤는데, 방식이 내 예상과 달랐다. `personId` 를 추가하는 대신 **`q` 의 검색 폭 자체를 넓혔다.**

```
작품 설명  → place_content → 장소
인물 이름  → content_cast → place_content → 장소
```

명세의 `q` 설명도 바뀌었다.

> 장소명·별칭·장소 설명·등장 작품의 제목·별칭·**설명·출연진 이름** 을 함께 검색

**이 방식이 내가 제안하려던 것보다 낫다.** `personId` 를 받았다면 프론트가 "이름을 직접 쳤다"와 "자동완성에서 인물을 골랐다"를 구분해 호출을 갈라야 했다. `q` 를 넓히면 작품 탭과 장소 탭이 **같은 파라미터에 같은 문자열** 을 받는다. iOS 와 Android 에서 같은 모양의 코드가 되므로 두 앱이 갈릴 자리가 하나 줄었다.

권호가 커밋 메시지에 붙인 근거가 내가 §3-2 에 쓴 것과 같은 얘기였다 — "한쪽 탭에 걸리는 것은 다른 탭에도 걸려야 한다. 결과의 종류만 다를 뿐 질문은 하나다."

검증도 서버 쪽에서 끝나 있다. `공유`·`김고은`·`도깨비` 셋 다 작품 탭 1건 · 장소 탭 3건으로 함께 채워진다.

> [!warning] 내가 확인을 잘못했다
> 오늘 오전에도 "빈틈이 그대로 남아 있다"고 판단했는데 틀렸다. 파라미터 이름 줄만 훑어 `personId` 가 없는 것을 보고 결론을 내렸고, `q` 의 **설명문** 이 바뀐 것을 놓쳤다. 계약서를 볼 때는 파라미터 목록만이 아니라 각 파라미터가 무엇에 걸리는지까지 읽어야 한다.

## 7. 오늘 정한 것

### 지원 언어 — MVP1 은 한국어 + 영어

일본어는 이번 범위가 아니지만 구조는 언어 추가를 전제로 짠다.

이 결정으로 **어제까지 감수 사항이던 것이 해결해야 할 항목으로 바뀌었다.** 서버의 `place_i18n` 에는 `ko` 만 있고 `place_alias` 는 비어 있다. 그래서 `Bukchon Hanok Village` 같은 **장소명을 영어로 치면 찾지 못한다.** 외국인 대상 앱에 영어가 확정 범위라면 넘어갈 수 없다. 권호와 상의할 항목이다.

(작품명·배우명은 영어로 걸린다. §6 의 확장 덕에 `Goblin` 을 치면 도깨비 촬영지가 나온다.)

### 카테고리 칩 — 목록과 지도를 둘 다 좁힌다. 카메라는 그대로

어제 §6 에서 "칩은 목록만 좁히고 지도는 건드리지 않는다"고 정했는데 **뒤집었다.** 실제 숫자를 보고 바꿨다.

`도깨비` 촬영지는 58곳이고 그중 음식점·카페는 12곳이다.

| | 목록만 좁힘 (어제) | 둘 다 좁힘 (오늘 확정) |
| --- | --- | --- |
| 목록 | 12곳 | 12곳 |
| 지도 핀 | **58개** | 12개 |

목록에 없는 핀 46개가 지도에 남으면, 그 핀을 눌렀을 때 목록에 없는 장소가 열린다. **"목록과 지도가 다른 얘기를 하는" 상태가 핀이 줄어드는 것보다 더 혼란스럽다** 고 판단했다. 카카오맵·네이버지도도 같은 방식이라 사용자 관습에도 맞는다.

카메라를 옮기지 않는 이유는 칩을 껐다 켤 때 원래 보던 위치를 잃지 않게 하기 위해서다.

### 그런데 칩 자체를 아직 만들 수 없다

권호에게 물어보니 `place_type` 에 **아무것도 해 두지 않았다** 고 한다(본인도 "2개만 뒀다"고 잘못 알고 있었다). 확인해 보니 이렇다.

- DB 의 `place.type` 은 제약 없는 `TEXT` 다. Enum 도 CHECK 도 없다.
- 시드 README: **"`place_type` 이 한국어 라벨 37종. 코드 매핑표가 아직 없다. 값 그대로 넣는다"**
- 계약서 `PlaceSummary.type`: **"37종의 자유 문자열이라 필터 값으로 쓰기에 적합하지 않다 — 칩으로 묶는 매핑은 데이터 정제 후에 정한다"**
- 같은 장소가 행마다 다른 타입으로 수집된 경우도 있다 (일월수목원 = `자연` · `공원`)

프로토타입은 37종을 4묶음으로 접는 매핑표를 **앱 안에** 들고 있다. 그대로 옮기면 같은 표가 iOS 와 Android 에 **두 벌로 복제되고**, 고치려면 앱을 다시 배포해야 한다. 저장소의 `apps/README.md` 가 금지하는 형태다 — "두 앱이 같은 규칙을 지켜야 한다면 공유하는 것은 코드가 아니라 `contracts/` 의 정의다."

**그래서 1차 이식에서는 칩을 만들지 않는다.** 규칙만 지금 못 박아 둔다. 나중에 iOS 와 Android 가 각자 정하면 두 앱이 갈리기 때문이다.

### 앱 모듈 이름과 순서

- `apps/scenetrip-ios/` · `apps/scenetrip-android/` — `MODULE.bazel` 의 `apps/<name>-ios/` 규칙과 `services/scene-api` 의 명명을 따랐다.
- **iOS 를 먼저 만든다.** 준비 비용만 보면 Android 가 가볍지만, iOS 의 준비 작업이 **팀 전체를 멈춰 세우는 종류** 라서다. `apple_support` 를 선언하는 순간 정식 Xcode 가 없는 맥에서는 저장소 전체 빌드가 깨지므로 세 명이 각자 10~15GB 를 받아야 하고, 그때까지 `just check` 가 도는지 아무도 확신할 수 없다. 이 불확실성은 미룬다고 줄지 않는다.

## 8. `just check` 와 `just ci` 는 다르다

PR 을 내면서 게이트를 확인했다. 저장소에 두 명령이 있는데 역할이 다르다.

```
check: fmt-check lint build test
ci:    gen-check fmt-check lint build test test-integration
       ^^^^^^^^^                          ^^^^^^^^^^^^^^^^
```

`ci` = `check` + 앞에 `gen-check` + 뒤에 `test-integration`. 그 외에는 같다.

`check` 가 도는 테스트는 **빠른 레인만** 이다 (`--test_tag_filters=-integration,-e2e,-slow,-manual`).

**규칙은 `just check` 만 요구한다.** `AGENTS.md` 의 Definition of Done 에 `just check` 만 있고, `ci` 는 "exactly what CI runs"·"CI 재현" 으로만 설명된다. 로컬과 CI 가 같은 명령을 돌리는 구조라서, `ci` 는 CI 가 왜 빨간지 재현하고 싶을 때 쓰는 도구지 매번 통과시켜야 하는 관문이 아니다.

**팀 규칙대로 `just check` 만 돌린다.**

| 무엇 | 문제 |
| --- | --- |
| `just ci-security` | 스크립트가 미구현인데 CI 잡은 초록으로 통과한다. 저장소가 공개로 바뀌었으므로 실제 시크릿 탐지가 필요하다 |
| 통합 테스트 0개 | `just ci` 가 "일치하는 테스트 대상이 없습니다" 경고를 내고도 통과한다. 나중에 태그를 잘못 달면 한 건도 안 돌았는데 초록으로 보인다 |
| `gen-check` | `just gen` 뒤 `git diff --exit-code` 로 판정해서, **작업 트리가 지저분하기만 해도 실패한다.** 생성물인지 아닌지 구분하지 않는다 |

`lint.sh` 는 같은 상황(도구가 없으면 검사 못 함)을 `die` 로 막고 있다. 주석에 이렇게 적혀 있다 — "검사해서 통과한 것과 아예 검사하지 않은 것은 다르다." 저장소 안에서 기준이 엇갈린다.

## 9. Swift 린터·포매터는 지금 설정하지 않는다

배선은 이미 다 돼 있고 엄격하다. `tools/scripts/lint.sh`·`format.sh` 에 Swift 절이 쓰여 있어 **`.swift` 파일이 하나라도 생기는 순간 자동으로 켜진다.**

| 명령 | `swiftformat` 이 없을 때 |
| --- | --- |
| `just fmt` | 경고만 하고 넘어간다 (고쳐 주는 편의 명령이라) |
| `just fmt-check` · `just check` · CI | **실패한다** |

그래서 첫 Swift 파일을 만들기 전에 `brew install swiftformat swiftlint` 가 필요하다. 빠뜨리면 커밋 직전에 게이트가 막는다.

없는 것은 규칙 설정 파일(`.swiftlint.yml`·`.swiftformat`)인데 **지금 만들지 않는다.** 빈 프로젝트에 먼저 쓰면 무엇을 켜고 끌지 모르는 채로 남의 기본값을 베끼게 된다. 화면을 몇 개 옮긴 뒤 **실제로 나온 경고를 근거로** 쓴다. `MODULE.bazel` 이 Apple 규칙을 "첫 iOS 모듈이 들어올 때 결정한다"로 미뤄 둔 것과 같은 판단이다.

승길이 말한 "장기적인 위험 요소를 잡는 도구"(정적 분석)는 이 저장소에 **아직 전 언어에 없다.** `.bazelrc` 가 "`tools/bazel/defs/` 에 린트 애스펙트를 추가하면" 이라고 자리만 비워 뒀고, Java 도 `google_checks.xml`(스타일)뿐이다. §8 의 표와 함께 권호와 볼 항목이다.
