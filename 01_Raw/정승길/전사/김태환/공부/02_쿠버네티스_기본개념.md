# 2. 쿠버네티스 기본 개념

> 컨테이너([[01_컨테이너와_도커]])를 이해했다면 이제 "컨테이너가 많아졌을 때"의 문제다.

## 쿠버네티스가 푸는 문제

컨테이너 하나는 `docker run` 으로 띄우면 된다. 그런데 실제 서비스는 이렇다.

- 백엔드 3개, 프론트 1개, AI 에이전트 2개, DB 1개 → 컨테이너 7개
- 트래픽이 몰리면 백엔드를 3개로 늘려야 함
- 컨테이너 하나가 죽으면 자동으로 다시 띄워야 함
- 새 버전을 무중단으로 교체해야 함
- 컨테이너끼리 서로를 찾아야 하는데 IP가 계속 바뀜

이걸 사람이 손으로 하는 건 불가능하다. **쿠버네티스(K8s)는 이 관리를 대신하는
"컨테이너 오케스트레이터"** 다.

> K8s는 Kubernetes의 줄임말. K와 s 사이에 글자가 8개라서.

## 핵심 사고방식 — 선언적(Declarative)

쿠버네티스를 이해하는 열쇠다. **명령하지 않고 상태를 선언한다.**

```
명령형 (docker)          "컨테이너를 3개 띄워라"
선언형 (kubernetes)      "컨테이너가 항상 3개 있어야 한다"
```

차이가 뭐냐면, 선언형에서는 **하나가 죽으면 쿠버네티스가 알아서 새로 띄운다.**
"항상 3개"라는 약속을 지키려고 계속 감시하기 때문이다.

```
원하는 상태(desired state)  ←──┐
        ↕ 비교               │ 컨트롤러가 무한 반복
실제 상태(actual state)   ────┘
```

이 반복을 **reconciliation loop(조정 루프)** 라고 한다. 쿠버네티스의 거의 모든
기능이 이 구조로 되어 있다. 그래서 YAML 파일에 "원하는 모습"을 쓰고
`kubectl apply` 로 던져주는 게 기본 사용법이다.

## 구성 요소 — 위에서부터

### Cluster (클러스터)

쿠버네티스 전체 한 덩어리. 여러 대의 머신(노드)으로 이루어진다.

```
클러스터
├── 컨트롤 플레인 (두뇌)
│   ├── API Server      모든 명령이 들어오는 입구. kubectl이 여기로 요청
│   ├── Scheduler       새 Pod를 어느 노드에 놓을지 결정
│   ├── Controller      원하는 상태 ↔ 실제 상태를 맞추는 조정 루프
│   └── etcd            클러스터의 모든 상태를 저장하는 DB
└── 노드 (일꾼)
    └── 실제 컨테이너가 도는 곳
```

SceneTrip 로컬 클러스터는 **노드가 1개** 다(`scenetrip-control-plane`). 로컬에서
검증할 건 노드 간 분산이 아니라 애플리케이션 동작이라서. 노드를 늘리면 이미지를
노드마다 적재해야 하고 메모리만 더 든다.

### Pod (파드) — 배포의 최소 단위

**쿠버네티스는 컨테이너를 직접 다루지 않는다. Pod를 다룬다.**

Pod는 컨테이너 1개 이상을 감싼 껍데기다. 같은 Pod 안의 컨테이너들은 IP와 저장소를
공유한다(같은 방에 사는 룸메이트). 보통은 **Pod 하나에 컨테이너 하나** 다.

```
Pod
├── IP 주소를 하나 가짐 (10.244.0.5 같은 클러스터 내부 IP)
├── 컨테이너 (보통 1개)
└── 볼륨 (필요하면)
```

> [!warning] Pod는 일회용이다
> Pod는 죽고, 다시 만들어지고, 다른 노드로 옮겨간다. **그때마다 IP가 바뀐다.**
> 그래서 Pod IP로 직접 통신하면 안 되고, 뒤에 나올 Service를 써야 한다.

**Pod의 상태** — `kubectl get pods` 로 볼 때 자주 보는 것들:

| 상태 | 의미 |
| --- | --- |
| `Running` | 정상 동작 중 |
| `Pending` | 아직 배치 못 함 — 리소스 부족이거나 볼륨 대기 |
| `ContainerCreating` | 이미지 받고 컨테이너 만드는 중 |
| `Completed` | 할 일 하고 정상 종료 (Job은 이게 정상) |
| `CrashLoopBackOff` | 켜자마자 죽고를 반복 — **앱 오류. 로그를 봐야 함** |
| `ImagePullBackOff` | 이미지를 못 받아옴 — 이름 오타나 인증 문제 |

### ReplicaSet → Deployment

Pod를 직접 만들지 않는다. **Deployment를 만들면 Deployment가 Pod를 관리한다.**

```
Deployment  ("v2 이미지로 3개 유지해줘")
  └── ReplicaSet  ("3개 유지")
        ├── Pod
        ├── Pod
        └── Pod
```

- **ReplicaSet**: Pod 개수를 유지. 하나 죽으면 새로 만듦
- **Deployment**: ReplicaSet을 관리 + **롤링 업데이트·롤백** 담당

새 버전 배포 시 Deployment는 새 ReplicaSet을 만들고 Pod를 하나씩 교체한다.
그래서 무중단 배포가 된다. 문제가 생기면 `kubectl rollout undo` 로 되돌린다.

### StatefulSet — 상태가 있는 앱용

DB처럼 "누가 누구인지"가 중요한 앱에 쓴다. Deployment와 달리:

- Pod 이름이 고정된다 (`signoz-0`, `postgres-0` — 뒤에 순번이 붙음)
- Pod마다 전용 저장소가 붙는다
- 순서대로 뜨고 순서대로 죽는다

SigNoz의 ClickHouse, Zookeeper, PostgreSQL이 전부 StatefulSet이다.

### Service — 고정된 접근점

Pod의 IP는 계속 바뀐다. **Service는 Pod 집합 앞에 붙는 고정 주소** 다.

```
[ 다른 Pod ] → Service (고정 이름·IP) → Pod A / Pod B / Pod C
                                        ↑ 죽고 새로 생겨도 Service는 그대로
```

Service는 뒤의 Pod들에 트래픽을 분산(로드밸런싱)까지 한다.

**Service 종류** — 이게 자주 헷갈린다.

| 종류 | 접근 범위 | 설명 |
| --- | --- | --- |
| **ClusterIP** | 클러스터 내부만 | 기본값. 밖에서 접근 불가 |
| **NodePort** | 노드의 포트로 외부 노출 | 노드 IP:30000~32767 |
| **LoadBalancer** | 클라우드 LB 통해 노출 | AWS면 ELB가 붙음. 로컬엔 없음 |

SigNoz UI가 기본 ClusterIP라 밖에서 안 보인다. 그래서 SceneTrip은 NodePort
서비스를 따로 만들어 붙였다(`platform/kubernetes/signoz/ui-nodeport.yaml`).
자세히는 [[03_kind와_로컬클러스터]].

### Namespace (네임스페이스)

클러스터 안을 논리적으로 나누는 구획. 폴더 같은 것.

```
클러스터 "scenetrip"
├── namespace: scenetrip     우리 서비스·앱·에이전트
├── namespace: signoz        관측성 도구
└── namespace: kube-system   쿠버네티스 자체 부품
```

이름이 같아도 네임스페이스가 다르면 다른 리소스다. 명령할 때 `-n <이름>` 으로
지정하고, 안 쓰면 `default` 를 본다. **"분명 배포했는데 안 보인다"의 절반은
네임스페이스를 안 지정한 것이다.**

```bash
kubectl get pods -n signoz          # signoz 네임스페이스만
kubectl get pods -A                 # 전체 네임스페이스
```

### ConfigMap / Secret — 설정 분리

설정값을 이미지에 박아 넣으면 환경마다 이미지를 다시 만들어야 한다. 그래서 밖으로 뺀다.

| | 용도 |
| --- | --- |
| **ConfigMap** | 일반 설정 (DB 주소, 로그 레벨, 기능 플래그) |
| **Secret** | 민감 정보 (비밀번호, API 키, 토큰) |

> [!danger] Secret은 암호화가 아니다
> 기본 Secret은 base64 **인코딩** 일 뿐 암호화가 아니다. 누구나 디코딩할 수 있다.
> **Secret 원문을 Git에 커밋하면 안 된다.** 실수로 올렸다면 파일 삭제로 끝내지 말고
> 즉시 담당자에게 알리고 키를 폐기·재발급해야 한다.

### PV / PVC — 데이터 저장소

컨테이너는 지우면 데이터가 사라진다. 지켜야 할 데이터는 볼륨에 둔다.

- **PV (PersistentVolume)**: 실제 저장 공간
- **PVC (PersistentVolumeClaim)**: "10GB 주세요"라는 **요청서**
- **StorageClass**: 저장소를 자동으로 만들어주는 방식

앱은 PVC만 요청하면 되고, 실제 디스크는 알아서 붙는다. kind는 `standard`
스토리지클래스가 기본으로 있어서 자동 연결된다.

SigNoz가 PVC 18GiB를 잡는다 — Zookeeper 8Gi + PostgreSQL 10Gi.

## kubectl — 클러스터와 대화하는 도구

모든 명령은 API Server로 간다. 형태가 일정하다.

```bash
kubectl <동작> <리소스종류> <이름> [옵션]

kubectl get pods                    # 조회
kubectl describe pod my-pod         # 상세 (하단 Events가 핵심)
kubectl logs my-pod                 # 로그
kubectl logs -f my-pod              # 로그 실시간
kubectl apply -f manifest.yaml      # YAML 적용
kubectl delete pod my-pod           # 삭제
kubectl exec -it my-pod -- /bin/sh  # 컨테이너 안으로 들어가기
```

**문제가 생기면 순서는 항상 이것이다:**
`get` 으로 상태 확인 → `describe` 로 Events 확인 → `logs` 로 앱 오류 확인.

### Context (컨텍스트) — 가장 위험한 개념

**하나의 kubectl로 여러 클러스터를 조작한다.** 로컬 kind도, 운영 EKS도 같은 명령어다.
지금 어디를 보고 있는지가 "컨텍스트"다.

```bash
kubectl config current-context      # 지금 어디? → kind-scenetrip
kubectl config get-contexts         # 전체 목록
kubectl config use-context kind-scenetrip   # 전환
```

> [!danger] 삭제 명령 전에는 반드시 컨텍스트를 확인할 것
> `kubectl delete`, `helm uninstall`, `kubectl apply`, `kubectl scale` 을 운영
> 클러스터에서 실수로 실행하면 서비스가 죽는다. 습관을 이렇게 들일 것:
> ```bash
> kubectl config current-context   # kind-scenetrip 확인
> kubectl get nodes                # 노드 확인
> # 그 다음에 변경 명령
> ```

> [!note] 이름이 헷갈리는 부분
> - 클러스터 이름: `scenetrip`
> - 컨텍스트 이름: `kind-scenetrip` ← kind가 `kind-` 접두사를 붙임
> - 노드 이름: `scenetrip-control-plane`
> 셋 다 다르다.

## YAML 매니페스트 — 실제로 어떻게 생겼나

```yaml
apiVersion: apps/v1        # 이 리소스의 API 버전
kind: Deployment           # 무엇을 만들 것인가
metadata:
  name: scene-api          # 이름
  namespace: scenetrip     # 어느 네임스페이스에
spec:                      # 원하는 상태(desired state)
  replicas: 1              # Pod 몇 개
  selector:
    matchLabels:
      app: scene-api       # 이 라벨을 가진 Pod를 내 것으로 관리
  template:                # Pod를 어떻게 만들지
    metadata:
      labels:
        app: scene-api     # 위 selector와 일치해야 함
    spec:
      containers:
        - name: scene-api
          image: scene-api:dev
          ports:
            - containerPort: 8080
```

`kind`, `metadata`, `spec` 구조는 모든 리소스가 똑같다. **라벨(label)** 로 서로를
연결한다는 게 포인트 — Service도 라벨로 Pod를 찾는다.
