### 1. 윤리 / 법 관점

**Q.** 블로그·유튜브·SNS에서 촬영지 정보를 크롤링하는 게 저작권·이용약관 위반 아닌가요?
**A.** 사실(촬영지 위치·작품명 같은 정보 자체)은 저작권 보호 대상이 아닙니다. 저희는 원문 텍스트·이미지를 그대로 저장·재배포하지 않고, 위치·작품 매핑 같은 '사실 데이터'만 추출해 자체 DB로 정규화합니다. 또한 robots.txt와 각 플랫폼 약관을 준수하고, 공공데이터·관광공사·지자체 공식 자료를 1차 출처로 우선합니다.

**Q.** 외국인 사용자가 주 타겟이면 GDPR 등 해외 개인정보보호법 대응은요?
**A.** 초기 MVP는 국내 운영·국내 서버 중심이지만, 글로벌 사용자를 받는 순간 GDPR 적용 가능성을 인지하고 있습니다. 대응으로 ① 위치·계정 정보는 명시적 동의 기반 최소 수집, ② 처리 목적 고지 및 삭제·열람 요청 절차 마련, ③ 위치 데이터는 추천 연산 후 즉시 폐기/익명화하는 설계를 적용합니다.

**Q.** 실시간 GPS 위치를 계속 수집하는데 개인정보 최소수집·동의 원칙에 맞습니까?
**A.** 위치는 '방한 중 현장 기능을 켤 때만' 사용자 동의 후 수집하며, 상시 추적이 아닙니다. 추천에 쓰고 나면 좌표 원본은 저장하지 않고 결과만 캐시합니다. 구성도상 ElastiCache에 세션 단위로만 두고 만료시킵니다.

**Q.** 사유지나 개인 가게가 '촬영지'로 노출돼 사생활 침해·영업방해가 생기면요?
**A.** 운영자 검수 단계에서 개인 주거지·비공개 장소는 노출 제외 정책을 적용하고, 정확 주소 대신 근접 지점/공개 접근 가능 여부를 표기합니다. 또한 점주·소유자의 삭제·정정 요청 대응 채널을 두어, 신고 시 즉시 비공개 처리합니다.

**Q.** 잘못된 정보(폐업·통제구역·위험지역)를 추천해 사고가 나면 법적 책임은?
**A.** 신뢰도 점수와 '최신 갱신일'을 함께 표기하고, 운영시간·개방 여부는 가능한 한 공식 API로 실시간 검증합니다. 약관에 정보 제공 서비스로서의 면책과 '현장 상황 우선 확인' 안내를 명시하고, 검증 Agent 루프 자체가 허위 정보 사전 차단 장치입니다.

## p2

**Q.** 유튜브 영상 임베딩, 저작권 문제 없나요?
**A.** 영상 원본을 저장·재배포하지 않고 공식 채널 영상만 공식 임베드 플레이어로 연결합니다(p.10 명시). 이는 유튜브가 허용하는 표준 임베드 방식이라 저작권 위험이 낮습니다.

**Q.** 배우 이름·작품명으로 검색·노출하는 게 초상권/퍼블리시티권 침해 아닌가요?
**A.** 작품명·배우명은 사실 정보(어느 작품/배우가 어디서 촬영)로서 식별·검색 용도로만 쓰고, 배우 사진을 상업적 광고에 무단 사용하지 않습니다. 인물 이미지가 필요하면 공식·라이선스 소스만 사용합니다.

**Q.** 사용자 제보(UGC) 사진에 타인 얼굴·차량번호 등이 찍히면요?
**A.** 제보는 운영자 검수를 거치며, 얼굴·번호판 등 개인 식별 정보가 포함된 사진은 블러 처리 또는 반려합니다. 제보 시 권리·저작권 동의를 받고, 신고 기반 사후 삭제 절차를 둡니다.

**Q.** 특정 동네에 외국인이 몰려 오버투어리즘·주민 피해가 생기면요?
**A.** 오히려 저희 BM은 서울 쏠림을 부산·경주 등으로 분산하는 방향입니다(p.11). 민감 지역은 방문 가이드라인(소음·시간대 매너)을 함께 노출하고, 지자체 협력 모델에서 주민 수용성을 함께 설계합니다.

**Q.** AI 추천의 할루시네이션·편향으로 없는 성지를 추천하면요?
**A.** 그래서 추천 전 데이터 단계에서 검증 Agent가 좌표 실존을 확인합니다. 추천 결과는 검증된 DB 안에서만 나오도록 RAG를 그라운딩해, LLM이 DB 밖 장소를 '지어내지' 못하게 막습니다.

**Q.** 미성년 사용자 데이터 처리는요?
**A.** 위치·결제 기능은 성인/동의 기반으로 제한하고, 연령 확인 절차와 미성년자 보호 정책을 약관에 반영합니다.

**Q.** 단기 구독 결제에서 해외 결제·환불·소비자 분쟁은?
**A.** 글로벌 결제는 검증된 PG(앱스토어 인앱결제 등)를 통해 처리해 환불·분쟁 절차를 플랫폼 표준에 위임하고, 청약철회·환불 정책을 다국어로 고지합니다.

### 2. 비즈니스 관점

**Q.** SOM 100만 명(SAM의 30%)은 근거가 약한데, 어떻게 산출했나요?
**A.** 인정합니다, 현재는 목표치입니다. 다만 SAM(한류가 방한 계기인 331만) 중 ① 콘텐츠 성지 방문 의향층, ② 앱 사용 친화적 Z세대·개인 여행객(p.3 기사 'Z세대·나홀로 여행객 다수') 비중을 좁혀가는 방식으로 정규과정에서 세분화하겠습니다. 보수적으로는 SOM을 단계별(1년차 10만 → 3년차 100만)로 재설정할 계획입니다.

**Q.** 왜 외국인이 돈을 내나요? 구글맵·네이버지도는 무료인데요.
**A.** 무료 지도는 '주소를 알 때'는 강하지만, '어느 작품의 어느 장면 → 실제 위치 → 동선'을 연결해주지 못합니다. 저희가 파는 건 지도가 아니라 '성지 동선 설계 시간 절약'입니다. 그래서 탐색·저장은 무료로 풀고, 방한 중 현장 실시간 기능만 단기 구독으로 받습니다. 며칠 쓰는 여행자에게 소액 단기권은 지불 저항이 낮습니다.

**Q.** 기존 무료/거대 플랫폼(트립닷컴, 구글) 대비 방어막(moat)은?
**A.** 두 가지입니다. ① K-콘텐츠×촬영지 매핑 데이터는 일반 지도 플랫폼이 안 가진 자산이고, ② 사용자 검증 커뮤니티가 데이터를 계속 키우는 네트워크 효과를 만듭니다. 멘토 의견(p.12)도 '사용자가 직접 핀을 채워 데이터가 자라는 구조'를 진입장벽으로 평가했습니다.

**Q.** 이미 DUCPIC·Triple 등 경쟁사가 있는데 후발주자 진입이 가능한가요?
**A.** 경쟁사들은 콘텐츠 다양성·커뮤니티·여정 추천 중 일부만 강합니다(p.6 표). 저희는 '콘텐츠 폭 + 커뮤니티 + 여정 추천'을 동시에 묶은 빈 포지션을 노립니다. 또 기존 강자가 광고·중개 모델에 머무는 동안 데이터·IP 직접 연계라는 다른 BM을 파겠습니다.

## p3

**Q.** p.6 표에서 콘텐츠 다양성을 ▲로 표시했는데, 초기엔 데이터가 적지 않나요?
**A.** 맞습니다. 그 ▲는 '목표 포지션'입니다. 초기엔 서울·부산·경주 + 인기 작품 집중으로 깊이 있게 시작하고, 검증 파이프라인으로 빠르게 확장합니다. 발표 자료에서는 이 부분을 '목표/현재'로 구분 표기하겠습니다.

**Q.** CAC vs LTV는요? 인플루언서 마케팅 비용 대비 단기 구독 수익이 남나요?
**A.** 초기 유저 확보는 인플루언서·바이럴로 CAC를 낮추되, 핵심은 무료 탐색으로 대량 유입 → 방한 시 일부 전환하는 깔때기입니다. 단기 구독 단가는 낮지만 한계비용도 낮아, B2B(지자체·여행사) 라인이 수익의 안정축이 됩니다.

**Q.** B2B 지자체 모델은 영업 사이클이 길고 예산 의존적인데요?
**A.** 인지하고 있습니다. 그래서 B2B는 수익 다변화 옵션이지 단기 생존선이 아닙니다. 6개월 안엔 B2C MVP·데이터 자산 확보에 집중하고, B2B는 축적된 방문·검색 데이터를 무기로 정규과정 이후 단계적으로 접근합니다.

**Q.** 커뮤니티가 비어 있으면(콜드스타트) 가치가 없는데요?
**A.** 초기엔 운영팀이 시드 루트·검증 데이터를 직접 채워(콘텐츠 마케팅 겸) 빈 화면을 없애고, 인플루언서를 핵심 초기 사용자로 유치합니다. 즉 커뮤니티 의존 기능은 데이터가 일정 임계치를 넘은 뒤 노출합니다.

**Q.** K-콘텐츠 유행이 식으면 서비스도 죽는 것 아닌가요?
**A.** 특정 작품은 식어도 'K-콘텐츠 성지순례'라는 행동 자체는 누적되며, 식은 작품의 촬영지 데이터도 '레거시 성지'로 자산화됩니다. 신작이 계속 나오는 한 파이프라인이 데이터를 자동 갱신하므로 단일 작품 리스크는 분산됩니다.

**Q.** 6개월 SW마에스트로가 끝난 뒤 지속가능성·투자 계획은?
**A.** 6개월 산출물(앱·DB·검증 파이프라인)은 그 자체가 투자/창업 자산입니다. 정규과정 중 부산 관광객 설문(멘토 합의, p.12)으로 pain point를 검증해 PMF 데이터를 확보하고, 이를 근거로 후속 사업화/투자 라운드를 준비합니다.

**Q.** 단순히 '여행 추천 앱'이 또 하나 나오는 것 아닌가요? 한 줄 차별점은?
**A.** '추천해주는 앱이 아니라, 사용자가 콘텐츠 시청 맥락 위에 핀을 찍어 데이터가 스스로 자라는 앱'입니다. 멘토(p.12)도 트리플·구글트립과 '명확히 결이 다르다'고 평가했습니다.

**Q.** 유료 전환율은 어느 정도로 가정하나요?
**A.** 현재는 가정 단계라 보수적으로 잡고, 정규과정 설문·MVP 베타 데이터로 실제 전환율을 측정해 모델을 보정하겠습니다. 숫자를 지어내기보다 검증으로 채우는 게 맞다고 봅니다.

### 3. 기술 / 구현 가능성 관점

**Q.** p.7 구성도가 EKS·Bedrock·OpenSearch·PostGIS·EventBridge까지 너무 복잡합니다. 3명이 6개월에 가능?
**A.** 솔직히 구성도는 '최종 목표 아키텍처'이고, MVP는 핵심만 떼어 단순화합니다. 6개월 MVP는 ① PostGIS DB, ② RAG 검색, ③ 위치 추천, ④ Flutter 앱으로 좁히고, 멀티 AZ·고가용성 같은 운영 고도화는 후속 단계로 분리합니다. 인프라 멘토(방한민) 지원도 이 부분입니다.

**Q.** RAG로 촬영지 데이터 정확도를 어떻게 보장하나요?
**A.** RAG는 검증된 자체 DB에만 그라운딩합니다. LLM이 외부 지식으로 장소를 지어내지 못하게 막고, 답변에 출처·신뢰도 점수를 함께 제시합니다. 부정확 추출은 검증 Agent 루프와 운영자 검수 큐로 거릅니다.

## p4

**Q.** (핵심) 영상에서 장소를 추출·매핑하는 게 진짜 난제인데, 어떻게 자동화하나요?
**A.** 가장 어려운 부분 맞습니다. 그래서 영상 프레임 자동 인식에 처음부터 올인하지 않습니다. 1차는 자막·메타데이터·블로그·기사·공식 자료에서 '작품-장소' 텍스트 단서를 LLM으로 추출(p.7 'LLM Extraction')하고, 검증 Agent가 지오코딩으로 좌표 실존을 확인합니다. 영상 비전 기반 매핑은 데이터가 쌓인 뒤 고도화 과제로 둡니다. 즉 '쉬운 신호부터 + 사람 검수 + 사용자 제보'의 3중 보강입니다.

**Q.** 위치기반 실시간 추천의 지연시간·정확도는 감당되나요?
**A.** 추천 후보군은 사전 인덱싱(PostGIS 공간 인덱스 + Redis 캐시)으로 좁혀두고, 실시간엔 가벼운 랭킹만 수행해 지연을 낮춥니다. LLM 호출은 일정 설계 같은 비실시간 영역에 배치합니다.

**Q.** 검증 Agent가 LLM으로 LLM 출력을 검증하는데, 그게 신뢰할 수 있나요?
**A.** Agent는 'LLM 의견'이 아니라 객관적 체크(지오코딩 좌표 존재, 중복 병합, 운영시간 API 대조)로 점수를 매깁니다. 신뢰도 미달은 재검증 루프, 3회 실패는 사람 검수로 강제 이관(p.8)되므로 자동화가 틀려도 안전망이 있습니다.

**Q.** 경량 로컬 모델(Qwen, Haiku)로 정제 품질이 충분한가요?
**A.** 정제·분류 같은 반복 작업은 경량 모델로 비용을 낮추고, 품질이 중요한 단계만 상위 모델을 선택적으로 호출하는 모델 라우팅을 씁니다. 평가지표(김태환 담당)로 모델별 품질을 측정해 임계치 미달이면 상위 모델로 승격합니다.

**Q.** 초기 촬영지 DB 콜드스타트 — 출시 시점에 몇 개나 채울 수 있나요?
**A.** 6~7월 데이터 구축 기간에 서울·부산·경주 + 인기 작품 우선으로 좁혀, 깊이 있는 시드 데이터를 확보합니다. 공공데이터·관광공사·지자체 자료 + 파이프라인 자동 수집 + 운영자 검수로 채우고, 출시 후엔 사용자 제보로 증식합니다. (발표 때 목표 건수를 숫자로 말하면 더 강함)

**Q.** PostGIS 지오코딩이 한국 주소 체계에서 정확한가요?
**A.** 한국 주소는 Kakao/구글/OSM 지오코딩을 병행하고(p.7 External APIs), 결과 좌표는 검증 Agent가 교차 확인합니다. 도로명/지번 혼용은 정규화 단계에서 처리합니다.

**Q.** Flutter + SpringBoot + EKS + Bedrock... 스택이 너무 넓어 학습곡선이 큰데요?
**A.** 그래서 역할을 명확히 분리했습니다(p.8). 각자 주력 스택에 집중하고, MVP에선 익숙한 핵심 스택부터 가동합니다. 멘토 3인이 AI·인프라·기획을 각각 보조해 학습 리스크를 분산합니다.

**Q.** 추천·검색 품질을 어떻게 정량 평가하나요?
**A.** 평가지표 설계가 팀 역할에 명시돼 있습니다(김태환). 검색은 정확도/재현율·관련성, 추천은 채택률·동선 효율 같은 지표로 측정하고, 검증 데이터셋을 구축해 회귀 테스트합니다.

**Q.** 다국어(영어 질의 ↔ 한국어 데이터) 처리는요?
**A.** 작품·장소는 다국어 별칭 테이블로 매핑하고, LLM이 질의를 정규화해 한국어 DB와 연결합니다. UI는 다국어 인터페이스로 설계합니다(p.9).

**Q.** 사용자 증가 시 LLM API 비용이 폭증하지 않나요?
**A.** 무거운 LLM 연산(데이터 정제·일정 설계)은 실시간이 아닌 배치/사전 생성으로 돌리고 결과를 캐싱합니다. 실시간 경로엔 LLM 호출을 최소화하고 경량 모델·룰 기반을 우선합니다. → 리소스 Q2와 연결.

**Q.** 코드 품질·리뷰 문화는 어떻게 유지하나요?
**A.** Github PR 리뷰 + JUnit 테스트 + Github Action CI로 머지 전 검증을 강제합니다(p.7).

**A.** 콜드스타트와 데이터 품질을 통제하기 위한 의도적 제한입니다. 검증 파이프라인이 검증되면 같은 방식으로 지역을 자동 확장할 수 있어, '좁게 시작해 넓게 복제'하는 전략입니다.

**Q.** 서비스명 SceneTrip과 앱 화면 '성지순례'가 다른데요?
**A.** SceneTrip은 글로벌 브랜드명, '성지순례'는 한국어 사용자 대상 표기입니다. (발표 전 둘의 관계를 한 줄로 정리하는 걸 권장 — 심사위원이 일관성으로 물을 수 있음)

**Q.** 성공을 무엇으로 측정하나요? 핵심 KPI는?
**A.** 1순위는 검증된 촬영지 데이터 수와 정확도(신뢰도 점수), 2순위는 활성 사용자·루트 공유 수, 3순위는 추천 채택률·동선 효율입니다. 매출은 후행 지표로 봅니다.

**Q.** 앱 다운로드 장벽이 있는데 왜 웹이 아니라 앱인가요?
**A.** 실시간 GPS 위치 기반 현장 추천이 핵심 가치라 앱이 적합합니다. 다만 여행 전 탐색·랜딩은 웹으로 진입 장벽을 낮춰 앱 설치를 유도하는 투-트랙입니다(p.10).

**Q.** 데이터 라이선싱·IP 직접 연계 같은 멘토 제안 BM은 검토했나요?
**A.** 정문창 멘토 제안(p.12)대로, 광고·중개 답습을 피하고 콘텐츠 IP·로컬 사업자 직접 연결, 방문 데이터 라이선싱을 차별화 BM 후보로 함께 발굴할 계획입니다.

**Q.** 한 문장으로, 가장 자신 있는 차별점은?
**A.** '사용자가 콘텐츠 시청 맥락 위에 직접 핀을 채워 데이터가 스스로 자라고, AI 검증 루프가 허위 성지를 거르는 구조' — 단순 추천 서비스로는 만들 수 없는 진입장벽입니다.

**Q.** 왜 지금(timing)인가요?
**A.** K-콘텐츠 흥행으로 방한·성지순례 수요가 역대 최고이고(p.3), 동시에 위치 기반 LLM Agent·RAG 기술이 실용 수준에 도달했습니다. 수요와 기술이 처음으로 맞물린 시점입니다.

**Q.** 만약 거대 플랫폼이 이 기능을 베끼면요?
**A.** 그들이 못 가진 건 K-콘텐츠×촬영지 검증 데이터와 팬덤 커뮤니티 자산입니다. 기능은 베껴도 데이터 선순환은 시간을 들여야 하므로, 저희가 먼저 그 자산을 쌓는 게 방어입니다.

**Q.** 이 프로젝트에서 AI가 '필수'인가요, 아니면 '있어 보이려고' 넣은 건가요?
**A.** 필수입니다. ① 파편화된 비정형 데이터를 정제·매핑하고, ② 좌표·중복·신뢰도를 자동 검증하고, ③ 위치·취향 기반으로 동선을 설계하는 것 — 세 가지 모두 규칙 기반으론 불가능하고 LLM/RAG/Agent가 핵심 동력입니다.
