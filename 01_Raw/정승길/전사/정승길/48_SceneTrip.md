## 1. 프로젝트 개요

- **SceneTrip**: 한국 K-콘텐츠(드라마·영화) **촬영지(장면) 기반 여행 코스 앱**. 외국인 팬 대상.
- 소속: **AI·SW마에스트로 17기 부산센터, 팀50 (팀명 mz2az)**.
- 계보: 애니메이션 성지순례 아이디어 → 평가 피드백 후 **보완 방향 2차 기획 수정안 제출**(완전 피벗 아님) → SceneTrip으로 확정.
- 핵심 논리: **외국인은 한국 지리는 몰라도 콘텐츠는 안다** → 콘텐츠(장면)가 내비게이션 역할을 한다.
- 팀 구성: **권호 = 백엔드, 태환 = 데이터/AI, 승길 = 프론트** (프론트는 AI 코딩으로 빨리 끝내고 데이터/AI 서브 커버 권장).

## 3. 핵심 컨셉과 차별화

- 기능 3축: ① 흩어진 K-콘텐츠 촬영지 정보 통합 ② 코스 추천/제작 ③ 커뮤니티(루트 공유).
- 평가위원 지적(극복 대상): 특출 기능 부재 / 대형 여행앱 대비 차별성 / BM 불확실 / 데이터 수집·일정 불명확.
- **차별화 = "경로의 유기적 연결" + NotebookLM식 LLM 플래너**: 탐색 단계에서 픽한 플레이스 풀을 소스로, LLM이 대화로 코스를 짜주고 조정까지 (경로 최적화가 자연스럽게 녹아듦, 몰랐던 콘텐츠 추천 가능).
- 사용자 시나리오(멘토 시연 확정): 앱 실행 → (선호도 조사는 후순위) → 카테고리(MVP1은 드라마만) → 작품 선택 → **장면 리스트** → 장면 클릭 → **"담기"** → 마이코스에서 순서 조정 + 계획 입력 = **나만의 코스**.
- **다국어 지원은 필수**이며 처음부터 설계에 반영 (로케일 코드가 데이터 PK 단위부터 들어가는 구조. 나중에 추가는 대공사).
- BM 참고: 구독 대신 **패스**(1일/3일/1주) 용어. 코스 유료화는 재검토 항목(유명해진 루트는 유료 의미 퇴색). 크라우드소싱은 BM이 아니라 **오픈 후 유입+콘텐츠 확장용 마케팅 요소**.
- 벤치마킹: **Visit Seoul** (카테고리 → 큐레이션 코스 → 플레이스 → 픽 흐름).

## 4. 콘텐츠 모델 (7/24 화이트보드에서 명시화)

원자 단위 = **장면(Scene) + 장소(Place)**. 경로 순으로 꿰면 코스, 회차 순으로 꿰면 작품별 장면 모음.

| 엔티티 | 속성 |
|---|---|
| **장면** | 영상 이미지, 메타 정보, 장면 설명, 포스터 API |
| **장소** | 실제 장소 이미지(구글 API 대표), 메타 정보, 리뷰(이미지·user), POI 정보 |
| **코스** | ① 순번 ② 설명(여행 계획), 작품 관련 설명(같은 장소라도 어느 장면·순번인지) |
| **커뮤니티** | 게시판 |
| **유저** | 찜 → DB |

- 관계: **장소:장면 = 1:N**. 장면→코스 사이를 **LLM이 "축약"**(흩어진 정보 → 콘텐츠화).
- DB 형태(RDB vs 그래프)는 의사결정 대상. 다이어그램: 루트의 `SceneTrip MVP1 모델.excalidraw` 와 `SceneTrip MVP1 모델.drawio.svg`.

### 화면·인터랙션 결정 (7/24 보드 하단)

1. **홈 카테고리는 2갈래: 테마별 검색 + 장소별 카테고리**
   - **테마별 검색**: 테마(영화 등)를 고르면 작품 목록 → 작품 선택 시 그 작품의 성지(장소) 목록 → 선택해서 **코스 장바구니에 담기**.
   - **장소별 카테고리**: 특정 장소 목록이 나오고 검색 가능 → 장소를 먼저 선택하는 흐름이므로 **바로 장바구니에 담기** 가능.
2. **코스 버튼과 활성화 버튼 분리** (기존엔 코스 버튼 안에 활성화가 같이 있었음 → 분리하고 활성화 버튼은 작게 오른쪽 배치)
   - **활성화 버튼**: 이용자가 **실제 한국에 와서** 누르는 현지 안내용. 누르면 해당 코스가 **바로 지도에 표시**된다.
   - **코스 버튼만** 누르면: 해외에서 여행 계획을 세울 때 보는 **정적 지도** 제공.
   - **홈에서 보여주는 지도는 동적** 형태.
   - (보드 메모 "코스만 눌리면 / 동적·정적 / 현지 활성화 팝업"은 전부 이 결정을 가리킴 — 미결 없음)

## 5. 데이터 파이프라인 & LLM 전략

- 결합할 3정보: ① 영화/드라마 콘텐츠 ② 플레이스(관광공사 등 공공데이터) ③ 사용자 후기(소셜). **이미 결합된 소스는 없음 → 우리가 연결**.
- 이원화: **크롤링(원천→로우 적재)** 은 LLM 불필요, 바이브 코딩으로 자동화 / **연결·메타 생성**은 LLM (클로드 코드로 핑퐁 매핑 후 "스킬로 만들어줘" → 스킬 반복 실행).
- 크롤링 신뢰도 점수 부여, 미달 시 운영진 직접 검증. 최근 인기작 우선(옛날 것 배제), MVP1은 OTT 인기작 ~20개.
- LLM 활용 포인트 2가지: ① 콘텐츠 생성(내부 자동화 — 서비스 아님) ② **서비스 내 플래너 어시스턴트(매력 포인트, 더 중요)**.
- 모델 전략: 내부 파이프라인은 오픈웨이트로 비용 최적화, 사용자 대면 플래너는 상용 LLM(하이쿠급이면 충분하다는 언급). API 비용은 전략적 결정 필요(BYOK vs 월 무료 한도).
- **LLM 어시스턴트용 널리지 베이스 별도 설계 필요**: 표시용 콘텐츠 모델만으로는 부족 → 영화·위치의 풍부한 텍스트를 벡터 DB(RAG)로 제공하는 컨텍스트 엔지니어링.
- 장소 사진: 구글 API로 수급(최신성 애매). 저작권은 일단 보류하되 **크롤링 시 출처 기록**, 변호사 멘토링 1회 필요.
