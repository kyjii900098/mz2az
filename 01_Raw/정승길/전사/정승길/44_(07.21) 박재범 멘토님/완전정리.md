## 한눈에 보기 (TL;DR)

- 멘토님의 핵심 지적: **"사용자가 이 서비스를 어떻게 쓰는지에 대한 시나리오(스토리)가 없다."** 화면 목업은 있지만 콘텐츠 수집 → 제공 → 사용자의 시간 흐름이 이어지는 그림이 없음.
- 멘토님이 즉석에서 **콘텐츠 모델링(장면+플레이스+코스) → 데이터 파이프라인 → 사용자 시나리오 → MVP 1/2/3 로드맵**까지 설계 시연을 해줌.
- 차별화 포인트 제안: 사용자가 직접 플랜을 짜는 대신 **NotebookLM 방식의 LLM 플래너 어시스턴트**가 코스를 짜주게 하라.
- 실행 지침: 계획부터 세우지 말고 **각자 파트를 먼저 손대서 개발 속도 감을 잡은 뒤**, 앞으로 한 달을 **3일 단위 블록 12개**로 쪼갠 계획에 합의하라. MVP1 목표는 8/21~22.
- 회의 후 팀 결론: "명시화가 안 된 게 너무 많다"는 자각. **금요일까지 각자 본인 메인 파트의 MVP1 기술 계획을 만들어오고**, 금요일 오프라인에서 화면 하나하나 결정 + 로드맵 명시화.

## 1. 도입 — 근황 공유와 일정 (00:00~08:00)

- 6월 초 첫 멘토링 이후 처음 만남. 그간의 경과 업데이트 요청.
- 팀: 완전 피벗이 아니라 **보완 방향으로 2차 기획 수정안 제출** 완료. 애니메이션 성지순례 → **한국 K-콘텐츠(영화·드라마) 촬영지 여행 루트 추천 앱**으로 방향 전환(SceneTrip).
- 전담 멘토들이 거의 매주(주 1~2회) 봐주고 있는 상황이라, 박재범 멘토님 오프라인(부산) 일정은 고정하지 않고 **다음 달 중후반에 다시 조율**하기로. 필요할 때 온라인으로 요청 (멘토님은 저녁 시간 대체로 가능).

## 2. 기존 기획 리뷰 — 발표 내용과 평가 피드백 (08:00~12:00)

**팀이 발표했던 기획**:
- 팬덤 대상: 작품명/배우명 검색 → 촬영지를 지도에서 확인, 여행 코스 추천 + 본인 코스 제작.
- 챗봇: 현재 위치 기반 다음 장소·맛집 추천.
- 기능 3축: ① 흩어진 K-콘텐츠 촬영지 정보를 한데 모음(외국인의 정보 접근성 해소) ② 여행 일정 추천 ③ 커뮤니티(루트 공유).
- BM: "구독" → **패스**(1일/3일/1주)로 용어 교체. 패스 구매 시 챗봇·추천 기능 제공.

**평가위원 피드백**(기획 완성도/아이디어 우수성/기술 개발 가능성/기대 효과 4개 분류):
- 우리만의 특출한 기능이 안 보인다 (커뮤니티를 더 강조해 보완).
- 모두투어 등 대형 여행앱이 K-콘텐츠 카테고리 하나 넣으면 뭐가 다른가.
- BM 구조가 확실하지 않다.
- 데이터 수집 방법·추진 일정이 명확하지 않다.

## 3. 데이터 확보 — 세 가지 정보의 결합 (12:00~19:00)

- 팀 계획: 공공데이터(영화 관련은 꽤 있음) 활용 + 크롤링. 크롤링에 **신뢰도 점수**를 부여해 한계점 미달이면 운영진이 직접 검증 (장소가 지금도 영업 중인지 등).
- 멘토님 정리: **① 영화/드라마 콘텐츠 ② 플레이스(관광지) ③ 사용자 후기(소셜)** — 이 세 가지가 결합돼야 정보가 풍부해진다.
  - 이미 결합된 소스가 있는가? → **없다. 따로 수집해서 우리가 연결해야 한다** (팀 확인). 그렇다면 세 정보를 자동으로 믹스·연결하는 데이터(연결 DB, 널리지 그래프든 뭐든)가 필요.
- 시의성: 오래된 콘텐츠보다 **최근 인기 콘텐츠**("김부장" 같은 핫한 것)가 빨리 반영되는 구조가 필요. 팀도 옛날 것은 배제, MVP는 인기작 몇 개로 시작 후 고도화 방침.
- K-콘텐츠 범위: 드라마 촬영지뿐 아니라 공연(BTS 등)일 수도 있음 → **카테고리 범위를 갈라 구색을 갖춰야** 한다. 플랫폼 내 사용자 수보다 **방문지 코스가 얼마나 다양하게 많으냐**가 사용자 유입을 결정.
- 앱 내 대중교통 길찾기: 그것만으로 별도의 앱이 될 만한 **엄청 큰 기능**이니 주의. 기술 난이도를 낮추는 절충안 필요 (팀도 인지).

## 4. BM·코스 유료화·초기 콘텐츠 전략 (19:00~28:00)

- 코스 판매: 초반엔 팀이 만든 코스 무료 제공, 유/무료 전환은 작성자 선택. 단, **유명해진 루트는 유료의 의미가 없어진다**는 점은 더 생각해봐야 (멘토 지적, 팀도 수긍).
- 크라우드소싱의 위치: 사람이 만드는 것이고 소싱 비용이 드는 것 → 당장의 BM이 아니라 **서비스 오픈 후 사용자 유입 + 콘텐츠 확장을 동시에 노리는 마케팅 요소**로 봐야 한다. (팀도 장기 BM으로 본 것이며 초반 수익화 목적 아님을 확인.)
- **Visit Seoul 벤치마킹**: K-팝/드라마/푸드 카테고리 + 큐레이션된 코스 콘텐츠가 이미 잘 되어 있음. 우리도 카테고리를 정하고 콘텐츠를 미리 만들어놔야 하는데, 그걸 누가 어떻게 만드느냐(초기 데이터 생성 전략)가 관건.
- 초기 콘텐츠 생성 방법 비교: ① 사람이 블로그 쓰듯 직접 ② 크롤링+전처리(RPA식) ③ **LLM 에이전트를 스킬로 만들어 자동화** — 콘텐츠에 큐레이터의 '말'(내레이션)이 들어가야 하므로 **LLM이 적절**.
- 멘토님이 제안한 큰 그림:
  - **MVP1**: OTT(넷플릭스·웨이브 등) 최근 인기작 20개를 정해 **LLM 에이전트로 콘텐츠를 만들어 플랫폼에 담는다** (우리가 만들어 놓는 단계).
  - **MVP2**: 오픈 후 확산 방향(K-공연? K-팝? K-뷰티?)을 정하고 **크라우드소싱에 비용을 걸어** 사용자와 콘텐츠를 동시에 확보.

## 5. 콘텐츠 모델링 — 장면 + 플레이스 = 원자 단위 (28:00~36:00)

- 팀의 "장면 지도": 케데헌이면 그 작품에 나온 장소들을 검색 없이 한 번에 제공하는 것. 각 지점은 (장면 사진 + 실제 장소 사진 + 설명) 수준 = **스토리가 아니라 정보**. 경로가 스토리가 된다는 입장.
- 멘토님의 모델링 정리:
  - **코스 = 여행지의 시퀀셜한 트라젝토리, 하나의 에피소드**. 에피소드의 스텝 = 장면(씬) + 방문지(플레이스).
  - **콘텐츠의 원자 단위 = 장면 + 플레이스**. 이를 **경로 순으로** 꿰면 코스가 되고, **회차(시간) 순으로** 꿰면 "케데헌 장면 모음" 같은 콘텐츠가 된다.
- 사용자 제작 콘텐츠는 자유 형식이 최선이지만, **우리가 기본으로 만들어낼 콘텐츠는 파이프라인 구축 → 정보 형태로 모델링 → 프로세스 자동화**를 설계해놔야 한다. (팀에 그려놓은 파이프라인이 있는지 물었으나 → 없음.)

## 6. 목업 리뷰와 핵심 지적 — "사용자 시나리오가 없다" (36:00~48:00)

- 팀 목업 설명: 홈=지도+카테고리(K-드라마/K-팝) → 인기작 목록 → 작품 클릭 시 촬영지 핀 표시 → 핀 클릭 시 간략 정보+사진(또는 공식 유튜브 임베드; 저작권 이슈로 논의 필요) → 핀을 담아 러프하게 코스 구성, 커뮤니티에서 본인 코스 글쓰기 지원. 코스 탭 화면 시안 3종.
- 멘토님 지적:
  - 이대로면 "네이버 지도와 뭐가 다른가"로 보인다 (평가 피드백과 동일한 지점).
  - 첫 화면에서 내 위치 기반 지도만 뜨면 **사용자가 뭘 해야 할지 모른다**.
  - 제목이 "장면에서 출발하는"이면, 콘텐츠와 장면이 쫙 펼쳐지고 거기서 집어 출발해 코스를 만들어 나가는 경험이 기대된다.
  - 결국 Visit Seoul 같은 화면 흐름(카테고리 → 큐레이션 코스 → 플레이스 → 픽)이 나와야 하고, 팀이 말한 **"경로의 유기적 연결"이 바로 차별화 포인트**이니 그걸 시나리오로 보여줘야 한다.
  - **"어떻게 콘텐츠를 모으고, 어떻게 사용자에게 제공하고, 사용자는 어떤 시간 흐름으로 서비스를 이용하는가"에 대한 그림(서비스 시나리오)이 없다.** → 팀: 없습니다. → 멘토님이 직접 그려서 시연 (아래 7).

## 7. 멘토님의 설계 시연 (48:00~1:01:00)

### 7-1. 콘텐츠 모델 (3개 엔티티)
| 엔티티 | 구성 |
|---|---|
| **드라마 장면(Scene)** | 영상 컷 이미지 + 대사 등 메타 정보 |
| **플레이스(Place)** | 이미지 + 설명 + 위치 정보 |
| **코스(Course)** | 순번 + (장면↔플레이스 링크) + 사용자의 여행 계획 메모 |

- 장면 : 플레이스 = 1:1 또는 1:N 매칭 관계. 연결은 링크 필드든 별도 릴레이션 테이블이든 하기 나름.
- DB 형태도 의사결정 대상: 단순 시퀀스면 RDB, 여러 작품의 장면을 넘나들며 엮는 걸 살리려면 노드-링크(그래프) 구조도 고려.

### 7-2. 데이터 파이프라인
- 데이터 원천: ① 관광공사 여행지 ② 영화 정보(영화진흥원 등) ③ 기타 공공데이터포털.
- **에이전트(LLM)를 하나 만들어** 영화에서 출발 → 장면 생성 → 관광공사 여행지에 매핑 → 링크 생성 → DB 적재. "콘텐츠 추출"을 에이전트가 실행하면 장면·여행지·링크가 만들어지는 구조.
- 코스는 초기엔 우리가 미리 만들어 둔다 (100~300개 규모 언급).

### 7-3. 사용자 시나리오 (페르소나 흐름)
1. 앱 실행 → **선호도 조사** (밸런스 게임식 질문 1~2개 통과하면 선호도 저장)
2. 카테고리 표시 (MVP는 드라마만; 팝은 이후)
3. 작품 선택 (무빙, 연애세포 등) → 그 작품의 **장면 리스트**가 쭉 표시
4. 장면 클릭 → 장면+위치 상세 → **"담기"** → 내 코스 후보에 1번, 2번… 누적
5. 탐색이 끝나면 **마이코스** 탭 → 담아둔 항목이 순서 흐름/목록으로 표시 → 빼고 넣고 순서 조정 + 나만의 계획 입력 → 저장 = **나만의 코스 생성**
6. 다시 앱에 들어오면 내가 만든 코스가 홈에 뜸
- 탐색(2~4)과 플랜(5)은 다른 단계다. **코스를 만드는 것이 곧 나의 여행 플랜의 목적.**
- 외국인은 한국 지리는 몰라도 **콘텐츠는 안다** → 콘텐츠가 내비게이션 역할을 하게 하는 게 이 서비스의 논리.

## 8. MVP 로드맵 프레임 (1:01:00~1:07:00)

> 설계 = 별 게 아니다. 데이터(엔티티·속성·타입·확보 방법)와 기능의 범위를 **데이터/기능 두 관점**에서 MVP별로 식별하면 그게 로드맵이다.

| | 데이터 | 기능 | 시점(안) |
|---|---|---|---|
| **MVP1 — 장면·코스 구성, 여행 플랜 수립** | 드라마만, 우리가 자동 생성한 콘텐츠만 | 앱 메인, 장면 탐색, 마이코스 (선호도 조사는 부차적 → 나중) | **8월 말 (8/21~22 팀 목표)** |
| **MVP2 — 개인화 추천** | 드라마+영화, 크라우드소싱으로 사용자 코스 확보 | 선호도 질문 + 개인화 추천, 마케팅/사용자 유입 | 9월 말 |
| **MVP3 — 여행 계획 최적화** | — | 지도 내비게이션, 경로 순서 최적화(동선 정리) | 이후 |

- 남은 기간 동안 **한 달 사이클 스프린트를 약 3회** 돌릴 수 있다 (중간에 실사용자 모집·마케팅 포함).

## 9. 다국어 지원과 문서화 (1:07:00~1:10:30)

- 외국인 대상이 목표라면 **다국어 지원은 필수** — "이거 안 하면 우리나라 사람용 앱일 뿐."
- **처음부터 설계에 반영해야 한다**: 데이터 콘텐츠부터 로케일 코드(KR/EN/CN…)가 모든 PK에 들어가 쌍으로 만들어지고, 앱은 사용자 세션 로케일에 따라 메시지를 DB에서 읽어오는 구조. 나중에 추가하려면 엄청난 일. 영어까지만 할지 등 **범위 자체가 중요한 의사결정**.
- 이런 것들을 **설계서 형태로 노션 등에 문서화**해두면 멘토링 때도 "우리 MVP 계획·사용자 시나리오·콘텐츠 모델링은 이겁니다"로 소통이 되고, 팀원 간 오해도 사라진다. **설계 문서 = 의사결정이자 의사소통 수단.**

## 10. 휴식 중 팀 내부 대화 (1:15:46~1:23:50)

- "박재범 멘토님은 우리 상황을 모르는데도 보자마자 시나리오→데이터→LLM까지 다 나왔다. 우리가 설명을 못 한다는 게 말이 안 된다. **우리가 그만큼 깊게 생각을 안 해봤다는 것**" — 팀원들끼리 먼저 이야기해야겠다는 자각.
- 성지 지도까지는 명확했는데 **'코스'가 들어오면서 어려워졌다**는 진단 (코스를 어떻게 구성할 것인가).
- 코스 담기(장바구니) 시나리오 재확인: 작품을 넘나들며(무빙→케데헌) 장소 핀을 담으면 그 사람만의 취향 코스가 되고, 이는 커뮤니티 추천으로도 이어질 수 있다. 단발성 여행이라는 반론도 있었으나, 담는 대상은 작품이 아니라 **장소 핀**임을 정리.
- "장소 클릭 → 내 코스에 넣기 버튼" 등 지금까지 한 번씩 다 나왔던 얘기인데 **정리(명시화)가 안 돼서 흐름으로 잇지 못하고 있다** → 시나리오 문서가 필요. 코스 유료화도 재검토 필요.

## 11. LLM 차별화 아이디어 — NotebookLM식 플래너 (1:23:52~1:32:00)

- 멘토님이 쉬는 시간에 떠올린 제안: **구글 NotebookLM**(잘 구현된 RAG 서비스; 소스를 주면 할루시네이션 없는 답변, 마인드맵·보고서·슬라이드·퀴즈 생성) 데모 시연.
- 적용: 사용자가 탐색 단계에서 픽해둔 플레이스 풀을 '소스'로 삼아, **LLM에게 "이런 취향인데 여행 코스 만들어줘"라고 하면 코스가 생성되고, 말로 조정까지 되는 UI** (소스 / LLM 대화 / 콘텐츠의 3분할을 UI에 녹이기).
- 효과:
  - 사용자가 플랜을 직접 짜는 게 아니라 **LLM이 플래너 역할** → 경로 **최적화가 자연스럽게 녹아든다** (한국 지리를 모르는 외국인이 플랜을 짤 수 있겠나라는 우려 해소).
  - LLM이 "너 이건 모르는 것 같은데 요즘 여기가 핫해"라고 **몰랐던 콘텐츠 추천**까지 가능 → 차별화 지적을 상당히 극복.
- 비용 질문(팀): 사용자가 코스를 계속 만들면 API 비용은? → **LLM 전략의 문제**. 사용자가 자기 API 키를 넣게 하면(BYOK) 비용은 사용자 부담이지만 키 없는 사람은 못 쓰는 문제 → 월 무료 한도 등, 반은 비즈니스·반은 유입 문제로 **전략적 결정** 필요. (모바일 앱에서의 입력 불편은 음성 프롬프트 등 추가 고민.)

## 12. LLM 활용 포인트와 모델 전략 (1:35:00~1:41:00)

- LLM 활용 포인트는 두 가지로 구분하라:
  1. **데이터 수집·구축(콘텐츠 생성)** — 사용자에게 드러나지 않는 내부 자동화. **개발 업무 자동화이지 서비스가 아니다.**
  2. **서비스 내 어시스턴트(여행 플랜 지원)** — 사용자가 느끼는 스마트한 팩터. **여기가 매력 포인트라 오히려 더 중요.**
- 모델 전략:
  - 내부 파이프라인(한글 여행지-장면 매핑 정도)은 **오픈웨이트 모델**로 충분 → 비용 최적화.
  - 사용자 대면 품질이 중요한 플래너는 **상용 LLM** (여행 플랜 수준이면 클로드 하이쿠로도 충분하다는 언급).
  - 모델 선택·API 정책·사용자 제공 한도는 비용 폭탄 위험까지 감안해 전략적으로 결정.
- 지역 커버리지: 지역 구분을 따로 할 필요 없이 **인기 작품 위주로 가면 범위가 자연스럽게 갈라진다** (국내 K-콘텐츠 전제는 OK).

## 13. 역할 분담과 데이터 엔지니어링 실행법 (1:41:00~1:49:30)

- 역할: **권호=백엔드, 프론트=참석자(발화자), 태환=데이터/AI**. 프론트는 AI 코딩으로 빨리 끝나니 **데이터/AI를 서브로 같이 커버**하는 것 권장.
- 데이터 엔지니어링 이원화:
  - **크롤링(원천 → 로우 데이터 적재)**: LLM 불필요, 파이프라인 코드로 자동화. 바이브 코딩으로 가능한 영역.
  - **연결·메타정보 생성**: LLM 활용. **클로드 코드에서 핑퐁으로 매핑 작업을 한 번 해본 뒤 "지금까지 나랑 한 걸 스킬로 만들어줘" 하면 스킬화** → 이후엔 스킬만 돌리면 됨.
  - 콘텐츠 저장용 데이터 테이블만 잘 만들어두고, 적재는 LLM에게 시키면 된다.
- **LLM 어시스턴트용 널리지 베이스 추가 설계 필요**: 서비스 표시용 콘텐츠 모델(이미지+대사+위치)만으로는 LLM이 플랜을 짜기에 지식이 부족할 수 있다 → 영화·위치에 대한 풍부한 텍스트를 **벡터 DB(RAG) 형태**로 주는 컨텍스트 엔지니어링 관점을 추가하라.

## 14. 멘토님의 오늘 정리 — 5가지 (WebEx로 전달, 1:47:00~1:50:00)

1. **MVP 계획 수립** — 앞으로 1개월은 구체적 계획, 그 이후는 로드맵 수준의 대략 계획.
2. **데이터 엔지니어링**(크롤링을 통한 원천 콘텐츠 확보) + **콘텐츠 모델링**(장면·위치·코스 정의와 LLM 매핑·콘텐츠화).
3. **사용자 시나리오** — 외국인의 정보 부족·접근성 고려 → LLM 기반 플래너 어시스턴스 필요.
4. **LLM 어시스턴스를 위한 지식 정보(널리지 베이스) 추가 모델링.**
5. **전체 서비스의 LLM 활용 포인트**(콘텐츠 생성 + 여행 플랜 지원)와 **상용 vs 오픈웨이트 사용 전략.**

## 15. 실행 지침 (1:50:00~1:59:15)

- **손을 대보지 않고 짠 계획은 부정확하다.** 각자 파트를 빨리 개발해보고 "바이브 코딩으로 이 정도면 얼마 걸린다"는 **속도 감**을 먼저 잡아라. (예: 케데헌 1편으로 파이프라인 전체를 돌려보니 3일 → 그러면 드라마 20편이 아니라 50편 가능한지/10편으로 줄일지 판단 가능. 범위와 시간은 트레이드오프.)
- 클로드에게 크롤링 엔지니어링을 먼저 만들게 해서 돌려보고, 그 결과를 LLM 콘텐츠화까지 해봐야 "몇 개를 언제까지"가 정확해진다.
- 프론트 디자인: 고민보다 **벤치마킹이 빠르다**. https://getdesign.md/#find-skills 에서 디자인 md를 받아 클로드에 주거나, 마음에 드는 화면 캡처만 줘도 그 스타일로 잘 만들어준다. 컨셉만 잡으면 나머지는 AI가 금방.
- **계획 단위: 3일 블록.** 4주 = 12블록. 각자 계획을 세워 셋이 합의하라. 주 단위는 너무 러프하고 5일은 너무 크다.
- **한 달(시간)을 사수하고 범위를 조절하라.** 범위가 좀 줄어도 한 달 안에 끝내는 것이 목표. 첫 스프린트라 시행착오는 당연하고, 끝나면 속도 경험이 생겨 다음 계획이 정확해진다.
- 오늘 내용을 소화해 **설계서 초안**으로 만들고 살을 붙여나갈 것.

## 16. 회의 후 팀 회고 (1:59:50~2:24:49)

**소감**
- 태환: 목업 등 우리끼리 다 짠 건데 설명을 못 했다고 모르는 건가 싶다. 개발하며 정해갈 수 있는 부분이라 **크게 공감은 안 됐다**. 다만 구체적 플로우차트가 안 짜여진 것엔 동감.
- 권호: 도움 된 부분 = **경각심**. "팩트는 우리가 명시화 안 된 게 너무 많다", 특히 **코스**에 물음표가 많았다. 다만 AI 활용 방안(플랜 등)은 우리도 이미 생각했던 것. 챗봇 형태로 넣을지 플래너로 넣을지는 생각해봐야.
- 프론트 담당: 처음엔 기대 안 했는데, **한 달 이상 한 우리보다 처음 본 멘토님이 더 잘 설명하는 건 말이 안 된다** → 우리가 깊게 생각 안 한 것. 이분에게 주기적으로 "검사받는" 방식이 좋겠다 (전체를 봐주는 멘토가 없었음: 정문창=창업/BM, 김상규=팀 운영(지라·LLM 위키), 방한민=인프라 → **워크플로우·흐름을 잡아주는 부분이 오늘 채워짐**).
- 멘토링 태도 반성: 우리가 너무 수동적이었다. **매번 우리가 해간 것 + 궁금한 것(물음표)을 명시화해서 가져가야** 한다. 명시화된 문서가 있으면 매번 앞부분 설명 30분이 절약된다. 설문 관련 질문도 준비해서 물어볼 것.

**결정·논의 사항**
- 기획은 러프하게는 끝났고, **기획을 디테일하게 만드는 것 = 명시화**. 정문창 멘토님이 기술을 봐줄 것이라는 기대에 너무 의존하지 말고 우리가 먼저 잡고 가야 한다 (8/9? 전까지 아무것도 안 잡고 가면 안 됨).
- 장소 사진: 구글 API로 장소 사진 수급 가능하나 최신성이 애매(남산타워 2025.5월 사진 등). **일단 저작권은 생각하지 말고 쓸 수 있는 이미지를 넣되, 크롤링 시 출처를 함께 남기고**, 이미지 재생성 등은 나중에 해결. 변호사 멘토링 1회는 꼭 필요.
- 목업: 바로 툴로 만들기 전에 **손으로 먼저 그려서** 다 같이 결정 (AI가 대충 그려도 잘 만들어주니까). 기존 목업의 좋은 부분(지도 위로 올리는 정보 시트, 장바구니 담기)은 유지.
- 3일 단위 스프린트는 지라(Jira)에 반영 검토. 회의실 못 잡을 때를 대비해 포터블 모니터를 사물함에 비치.
