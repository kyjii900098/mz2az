## 2. 해야 할 일 (Action Items)

### 2-1. 데이터 수집 — 전원

- **대상**: K-콘텐츠 전반. 유명 드라마 / 영화 / OTT / K-POP 관련 장소 / 예능(런닝맨 등).
  - 일단 K-콘텐츠를 **다 넣고 나중에 필터링** 하는 방향.
- **방식**: 확정된 컬럼(스키마)을 **AI에게 던져서 수집** → 빈 칸은 각자 눈으로 확인해 수동 보완.
  - 근거: AI는 정해진 컬럼 안에서만 동작하므로, 컬럼을 먼저 확정해야 재수집을 피할 수 있다.
- **포맷**: **CSV** (어떤 DB로든 넣기 편하므로).
- **마감**: 화요일(7/28)~수요일(7/29) 안에 각자 모아오기.
- **규칙**: 모으다가 컬럼이 더 필요하다고 판단되면 **모이기 전에 미리 카톡으로 공유** (회의 시간 절약 목적).
- **참고 소스**: 한국문화정보원 영상 촬영지 데이터, 소상공인시장진흥공단 공공데이터.

### 2-2. 스키마 확정 — 내일(7/28)까지

- 컬럼명은 **영문으로** 통일 (한글 X). 한 사람이 기준안을 만들어 공유.
- **확정된 컬럼 후보**

  | 컬럼 | 비고 |
  |---|---|
  | 장소 이름 | 필수 |
  | 작품명 | |
  | 작품 별칭 | "별그대" 같은 검색용 별칭. 여러 개 필요 → 별도 테이블 검토 |
  | 작품 카테고리 | |
  | 장소 타입/카테고리 | 한국문화정보원 데이터가 미디어/장소 타입으로 나눠둔 걸 보고 추가 |
  | 좌표 (위도/경도 분리) | **소수점 5~6자리**. 5째 자리 = 약 1m 차이. 검색 결과에 나온 자릿수를 임의로 자르지 않음 |
  | 주소 | 좌표와 별개 |
  | 관련 인물 | 배우·주연 우선, 감독은 후순위. 일단 자연어 문장으로 넣고 나중에 분리 |

  | 작품 관련 설명 | **몇 화 몇 신인지** 포함. AI가 잘 못 하는 영역 → 수동 보완 필요 |
  | 마지막 업데이트 | |

- **보류**: 장소 자체에 대한 설명 → **별도 테이블** 로 분리. 장소:작품 = 1:N 이라 같은 장소가 중복 저장되는 문제 때문. 장소 목록이 확정된 뒤 수집.
- **영업시간**: 일단 적어는 두되, **MVP1에서는 빼는 쪽으로 결론** (3-4 참조).

- **1차 MVP 목표일 = 8/29** ("넉넉하게 29일").
- **중간발표 = 9/18~19** → 9/14 주는 발표 준비에 사용.
- 8/15(광복절) 등 빨간 날엔 모이지 않음.
- 전반적으로 **"생각보다 빠듯하다"** 는 인식이 공유됨.

### 3-2. MVP 범위

- **MVP1 = 검색 + 지도 + 루트(코스) + 로그인 + 커뮤니티 + 마이페이지**.
  - 9월 중간발표에서 MVP1을 발표해야 하므로 커뮤니티·마이페이지까지 포함해야 함.
- **MVP1 = "여행 전" 시나리오 / MVP2 = "여행 중" 시나리오** 로 구분.
- **루트 생성은 초기엔 수작업(손으로)**. AI(LLM) 자동 생성은 그 다음 고도화 단계.
  - "일단 루트만 만들었다면 그다음 고도화를 AI로."
- **이미지 검색 기능은 하지 않음**.
- 앱 배포(구글 플레이/앱스토어) 심사는 커뮤니티 구현 **이후** 단계에 배치. 심사에 시간이 걸리고, 결과물이 있어야 등록이 가능하기 때문.

### 3-3. 로그인

- **자체 회원가입 없이 소셜 로그인(OAuth)만** 사용 — 그게 훨씬 쉬움.
- 단, OAuth는 **심사 과정** 이 있고 **민감한 정보를 요구할수록 심사가 빡빡해짐**. 통과 못 할 가능성도 있음.

### 3-4. 데이터 / DB 전략

- 데이터는 **이번에 한 번 제대로 모아놓고 그걸로 계속 감** (지속적 재수집 아님).
#### 음식점/카페 전략

> [!check] **확정** — 수동으로 초기 데이터를 구축한다
> 1. 팀이 **작품별 경로를 직접 만들면서** 그 경로상의 식당/카페를 **2~3개씩만 수동 큐레이션**.
> 2. 상세 정보는 **네이버/카카오맵 링크로 외부 연결**.
> 3. 우리 DB에는 **상호명 + 위경도 + 링크** 정도만 저장.
>
> 근거: 우리 앱 사용자는 **성지 근처를 다니는 사람** 이지 전국을 도는 사람이 아님. "성지 100개 × 각 3개면 충분".
> 부수 효과: 외부 API 호출이 사실상 필요 없어지고, 업데이트 부담도 사라짐.
> 원문: *"이건 확실한 확정인데 … 유명한 것들은 수작업으로"* (02:24:18)

> [!note] MVP1 범위 밖
> 전수 DB(소상공인시장진흥공단 등)를 넣고 **API로 "있다/없다"만 표시**하는 방식은 회의에서 거론됐으나 **이번 MVP에서는 하지 않는다.** 초기 데이터는 위 수동 구축으로 간다.

- **카카오/네이버 API 응답을 DB에 저장하거나 캐싱하는 것은 운영정책 위반.**
  - 응답 속도 개선 목적의 1시간 캐싱조차 쿼터 절감으로 판단되어 반려된 사례가 있음.
  - 카카오 로컬 API는 장소 고유 ID를 제공하지만 저장은 불가.
  - 확정안(수동 구축)대로 가면 **API 호출 자체가 거의 필요 없어져** 이 제약이 문제되지 않는다.
- **영업시간은 넣지 않기로** — "책임져야 할 부분이 너무 많아진다".
- 복합키(이름 + 좌표) 논의 결론: **키 설계는 지금 고민하지 않아도 됨.** 트리 인덱스면 검색 비용은 로그이고, 컬럼 2개를 묶어 하나의 고유키로 쓰는 건 흔한 방식이라 성능 문제 없음.
  - 남은 리스크: 좌표는 **점주가 핀 위치(입구 등)를 바꾸면 변할 수 있음**.
- **데이터 축적 자체가 해자(경쟁 우위)** 라는 인식 공유 — 특히 **외국인 리뷰** DB.
- 사용자가 직접 장소를 등록하는 기능은 **가능성만 열어두는 부가 기능**.
  - **(2026-07-28 갱신)** 검색/지도 화면의 **사용자 제보 기능** 으로 구체화되어 계획에 포함됨 (2-3 참조). "가능성만" 단계는 지났음.

### 3-5. 다국어

- **다국어 지원 확정.** 단순 번역이 아니라 **처음부터 구조를 그렇게 짜야 함** (글자 길이가 달라 프론트 레이아웃에 영향).
- 대상 언어: **한국어 + 영어 + 일본어** 를 기본으로, 번체 중국어(대만) 검토 중.
- **중국 본토는 제외** — Google Play 사용 불가.
- 대만은 표준중국어를 쓰되 **번체 표기**. 영어 지수가 한국보다 낮다는 정보도 확인됨.

### 3-6. 벤치마킹 / 저작권

- **K-Spot**: UI가 답답함. 저작권 회피하려고 포스터를 이상하게 처리. AI로 대충 만든 티가 나고 홍보도 안 하는 듯. → 우리는 **DB를 제대로 구축해서 차별화**.
- **트리플**: 결국 **수동으로 노가다** 해서 데이터를 채웠음. 사진은 페이스북 등에서 가져오되 **출처를 남기는** 방식. 사용자 리뷰가 쌓임.
- 우리도 **출처 표기 방식** 을 검토.
- 콜드스타트 인식 공유: 초기에 뭔가 있어야 사람들이 쓰므로, **초기 데이터를 직접 채워놓고 홍보는 나중에**.
- **UI/UX에 신경 써야 함.** 사용법을 몰라도 쓸 수 있을 만큼 직관적으로. MVP1 이후 UX/프론트 전문가에게 연락 검토.
