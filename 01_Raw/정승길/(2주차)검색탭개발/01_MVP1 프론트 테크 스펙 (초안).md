# MVP1 프론트 테크 스펙 (초안)

> [!info] 이 문서의 위상
> 이번 스프린트(8/3~8/7)에서 Flutter로 **무엇을, 어떤 데이터로, 어디까지** 만드는지 정한다.
> **회의 결정이 정본이고, 목업([[목업_작품검색.html]])은 참고 자료다.** 목업은 AI로 빠르게 만든 시안이라 팀 의사를 100% 반영한 화면이 아니며, 색·디자인·UI/UX는 구현하면서 더 낫게 바꿔도 된다. 목업 기능의 전체 목록은 [[MZ2AZ-116 작품검색 목업 기능 명세]] 에 있으니 이 문서는 1:1로 다시 적지 않는다.
> 티켓 번호가 나오면 이 문서는 JiraDocs로 옮긴다.

## 2. 화면 사양 (작품검색 탭)

### 2-1. 지도

- **네이버 지도 SDK** (Flutter 포팅 패키지, 후보: `flutter_naver_map`). 클라이언트 ID 발급 필요 — §6 미결.
- 첫 진입: 서울 중심, 인기 핀만 표시. 중심 좌표·줌 레벨은 구현하며 잡는다 (8/3 회의).
- 인기 기준: V6의 `famous_rank` (작품 단위) → 상위 작품의 촬영지를 우선 노출. 장소 단위 인기도는 백엔드 `popularity_score` 가 생기면 교체.
- 핀 탭 → 촬영지 상세로 이동. 포커스 애니메이션 등 연출은 구현 재량.
- 지도가 한국 밖으로 벗어났을 때 처리는 **팀 미결** (8/3 회의 Open Issue #2) — 일단 아무 처리 없이 두고 결정을 기다린다.

### 2-2. 검색

- 검색창은 **화면 상단 고정** (7/27 회의).
- **자동완성**: 영어 입력 기준. 매칭 대상 = `title` + `title_aliases` (세미콜론 분리값 각각). DB 조회는 단순 단어 매칭 (RAG 아님, 8/3 회의).
- 백엔드 API가 나오기 전에는 V6 목데이터로 프론트 안에서 자동완성을 구현하고, API가 나오면 호출로 교체한다 (§5 API 계약).

### 2-3. 작품 목록 / 작품 상세

- 작품 카드: 포스터(`poster_url`) · 제목 · `방송사 · 연도 · 장르`(`title_network`/`title_year`/`title_genre`) · 촬영지 N곳(행 카운트).
- "등록 장면 수" 지표는 넣지 않는다 — 촬영지는 넣고 등록 장면은 count로 대신한다 (8/3 승길 메모). 루트 N개 지표도 범위 밖.
- 작품 상세: 포스터, 메타, 촬영지 리스트(번호 = 지도 핀 연동). 줄거리는 V6에 없으므로 생략하거나 이후 추가.

### 2-4. 장소 목록 / 촬영지 상세

- 장소 카드: 씬 이미지(`scene_image_url`) · 장소명(`place_name`) · 카테고리(`place_type`) · 장면 설명 일부.
- 촬영지 상세: 대표 이미지(`place_image_url`) · 장소명 · 주소(`place_address`) · **장면 설명(`scene_description`, 문장형)** · 출연진(`title_cast`) · 네이버 지도 링크(`place_naver_url`) · 장바구니 저장 버튼.
- 한 장소에 여러 작품이 있는 경우(예: 녹사평 일대) 작품별 장면 설명을 나란히 보여준다.

### 2-5. 장바구니

- 담기 / 중복 시 안내 / 목록 보기까지. 저장은 **로컬 저장소** (로그인 없음). 루트 생성 버튼은 만들지 않는다.

> [!question] 확인 필요 — 카테고리 최종안은 태환 액션 아이템("카테고리 구분")과 합쳐 팀에서 확정한다. 이 임시안은 화면을 돌리기 위한 것.

> [!warning] 8/6 갱신 — 이 임시안은 프로토타입에서만 쓴다
> 위 매핑표는 **Flutter 프로토타입 안에 그대로 구현돼 있다.** 그런데 네이티브로 옮길 때는 이 표를 가져가지 않기로 했다.
>
> **서버는 아직 아무것도 묶어 두지 않았다.** 권호에게 확인한 결과와 저장소 기록이 일치한다.
>
> - DB 의 `place.type` 은 제약 없는 `TEXT` 다. Enum 도 CHECK 도 없다.
> - 시드 README: "`place_type` 이 한국어 라벨 37종. 코드 매핑표가 아직 없다. **값 그대로 넣는다**"
> - 계약서 `PlaceSummary.type`: "37종의 자유 문자열이라 **필터 값으로 쓰기에 적합하지 않다** — 칩으로 묶는 매핑은 데이터 정제 후에 정한다"
> - 같은 장소가 행마다 다른 타입으로 수집된 경우도 있다 (일월수목원 = `자연` · `공원`)
>
> 매핑표를 앱이 들면 **같은 표가 iOS 와 Android 에 두 벌로 복제되고**, 고치려면 앱을 다시 배포해야 한다. 저장소의 `apps/README.md` 가 금지하는 형태다 — "두 앱이 같은 규칙을 지켜야 한다면 공유하는 것은 코드가 아니라 `contracts/` 의 정의다."
>
> **그래서 1차 이식에서는 칩을 만들지 않는다.** 다만 칩이 생겼을 때의 동작 규칙은 지금 확정해 뒀다 — **목록과 지도를 둘 다 좁히고 카메라는 옮기지 않는다.** 나중에 두 앱이 각자 정하면 갈리기 때문이다. 경위는 [[03_2026-08-06_지라 정리와 네이티브 전환]] §7 에 있다.

## 5. API 계약 — 권호에게 요청할 목록 (프론트 필요 기준)

프론트는 아래 6개가 있으면 목데이터를 걷어낼 수 있다. 응답 필드는 §3 매핑 기준. DBML([[MZ2AZ-111 SceneTrip DB 스키마 (DBML)]])이 참고 정본.

| # | API | 요청 | 응답 핵심 |
| --- | --- | --- | --- |
| 1 | 작품 자동완성 | 부분 문자열(영어) | 작품 id·제목·별칭 매칭 목록 |
| 2 | 작품 검색 | 검색어 | 작품 카드 목록 (메타 + 촬영지 수) |
| 3 | 작품별 촬영지 목록 | 작품 id | 촬영지 목록 (좌표·장면 설명 포함) |
| 4 | 뷰포트 촬영지 검색 | 지도 영역(BBox) + 상한 N | 영역 내 촬영지, 인기순 상위 N |
| 5 | 촬영지 상세 | 장소 id | 상세 + 그 장소의 작품·장면들 |
| 6 | 인기 촬영지 (첫 화면용) | 상한 N | 인기순 상위 N 촬영지 |

- 장바구니는 MVP1에서 로컬 저장이므로 API 불요 (로그인 후 `saved_place` 로 이관).
- 자동완성은 프론트에서도 연계 구현이 필요하므로 응답 형태를 **먼저** 맞추자 (8/3 회의에서 승길에게 백엔드 스펙 사전 확인이 걸려 있음).

> [!done] 8/6 갱신 — 이 6개는 전부 만들어졌다
> 이 표는 **내가 요청하려던 목록** 이고, 권호가 실제로 만든 계약(`contracts/openapi/scene-api-v1.yaml`)이 정본이다. 8/6 기준으로 6개 요구가 모두 충족돼 있고, 구현도 머지됐다(PR #10 · #11).
>
> | 이 표의 요청 | 실제 엔드포인트 |
> | --- | --- |
> | 1 작품 자동완성 | `GET /search/suggestions` — 장소·작품·**인물** 을 `type` 으로 구분해 함께 준다. 요청한 것보다 넓다 |
> | 2 작품 검색 | `GET /contents?q=` — 제목·별칭·설명·**인물 이름** 에 걸린다 |
> | 3 작품별 촬영지 목록 | `GET /places?contentId=` · `GET /contents/{id}/places` |
> | 4 뷰포트 촬영지 검색 | `GET /places?bbox=` (+ `limit`) |
> | 5 촬영지 상세 | `GET /places/{id}` |
> | 6 인기 촬영지 | `GET /places?sort=popularity&limit=` |
>
> **요청 목록에 없었는데 계약에 있는 것** 도 둘 있다 — `GET /contents?personId=`(인물을 정확히 지목), 그리고 `GET /places?q=` 가 **출연진 이름까지** 훑는 것(MZ2AZ-167). 후자가 없으면 배우를 검색했을 때 장소 탭이 빈다.
>
> **남은 빈 곳은 하나다 — 장소명의 영어 표기.** `place_i18n` 에 `ko` 만 있고 `place_alias` 는 비어 있어서 `Bukchon Hanok Village` 로는 찾지 못한다. 작품명·배우명은 영어로 걸리므로 `Goblin` 은 된다. MVP1 지원 언어에 영어가 확정되면서(§6) 이것이 감수 사항에서 **해결해야 할 항목** 으로 바뀌었다. 권호와 상의 중이다.

> 아래 표는 **8/3 회의 시점의 선택** 이며 프레임워크·지도·상태 관리 행은 더 이상 유효하지 않다.
> 8/4 에 권호가 [ADR 0002](https://github.com/mz2az/SceneTrip/blob/main/docs/architecture/adr/0002-product-stack-spring-python-native-mobile.md)(status: accepted, 커밋 `64cb637`, MZ2AZ-157)를 저장소에 넣으면서
> **크로스 플랫폼 프레임워크(Flutter · React Native)를 쓰지 않는다** 가 확정됐다.
> 이유는 유지보수되는 Bazel 규칙이 없어 저장소 제1법칙("Bazel 이 모든 것을 빌드한다")과 충돌한다는 것이다.
> 8/5 에 승길이 이 결정을 따르기로 하고, Flutter 로 만든 검색 탭은 **프로토타입으로 남기고 네이티브로 다시 만든다.**
> 경위는 [[02_2026-08-05_검색탭 개발]] §10 에 있다.

> [!info] 8/6 갱신 — 범위가 iOS 전용에서 **iOS + Android** 로 넓어졌고 이름이 확정됐다
> 지라 티켓 MZ2AZ-148 의 제목이 「목업 기반 프론트 구현 **(iOS Swift · Android Kotlin)**」 으로 바뀌었고,
> 완료 처리했던 서브태스크 5개를 진행 중으로 되돌렸다. 저장소 계획서도 함께 올렸다
> (PR [#13](https://github.com/mz2az/SceneTrip/pull/13), `docs/project/plans/mobile-native-search-tab.md`).
> 상세는 [[03_2026-08-06_지라 정리와 네이티브 전환]] 참고.

| 항목 | 선택 | 비고 |
| --- | --- | --- |
| ~~프레임워크~~ | ~~Flutter 3.44 / Dart~~ → **iOS 네이티브(Swift) + Android 네이티브(Kotlin)** | 8/3 회의는 Flutter 였으나 8/4 ADR 0002 로 뒤집혔다 |
| 만드는 순서 | **iOS 먼저**, Android 는 그 다음 | 준비 비용은 Android 가 가볍지만, iOS 는 `apple_support` 선언만으로 **Xcode 없는 맥의 저장소 전체 빌드를 깨뜨려** 팀 전체가 걸린다. 그 불확실성은 미룬다고 줄지 않는다 |
| 프로토타입 위치 | `~/workspace/mobile` (Flutter, 모노레포 밖) | 화면·검색 규칙의 참고본으로 남긴다. 모노레포에 넣지 않는다 |
| 앱 모듈 이름 | `SceneTrip/apps/scenetrip-ios/` · `apps/scenetrip-android/` | `MODULE.bazel` 의 `apps/<name>-ios/` 규칙과 `services/scene-api` 의 명명을 따랐다. 8/6 확정 |
| 지도 | 네이버 지도 **iOS SDK · Android SDK 를 각각 직접** | ~~`flutter_naver_map`~~. 그 패키지가 감싸던 것과 같은 SDK 다. **클라이언트 ID 발급 필요 (팀 미결)** |
| 지원 언어 | **MVP1 = 한국어 + 영어.** 일본어는 이후 | 8/6 확정. 구조는 언어 추가를 전제로 짠다. §5 의 "장소명 영어 표기" 항목이 여기서 나온다 |
| 이미지 | 전부 URL 로딩 | 8/3 회의 — 로컬 단계부터 링크 방식. ~~`cached_network_image`~~ 는 Dart 패키지라 플랫폼별 대응물을 쓴다 |
| ~~상태 관리~~ | ~~Provider 또는 Riverpod~~ | Dart 패키지라 해당 없음. iOS 는 SwiftUI 기본 상태 관리로 시작한다 |
| 실행 대상 | iOS 시뮬레이터 → 이후 Android 에뮬레이터 | 웹(Chrome)은 Flutter 프로토타입에서만 되던 것이라 빠진다 |
| API 클라이언트 | **손으로 쓰지 않는다.** `contracts/` 에서 생성한다 | 저장소 CLAUDE.md §5. 생성기는 `swift5`(iOS) · `kotlin`(Android) |
| 디자인 | 목업 색·레이아웃에 구속되지 않음. UI/UX 개선 재량 | 이 문서 상단 위상 참조 |
