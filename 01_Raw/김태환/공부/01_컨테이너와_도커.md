# 1. 컨테이너와 도커

> 모든 것의 출발점. 여기가 흔들리면 쿠버네티스는 절대 이해할 수 없다.

## 컨테이너가 푸는 문제

프로그램 하나를 돌리려면 그 프로그램만으론 안 된다. 특정 버전의 런타임(JDK 21,
Python 3.12), 라이브러리, 환경변수, OS 설정이 다 맞아야 한다.

그래서 이런 일이 생긴다.

- 내 맥에선 되는데 팀원 맥에선 안 됨 (JDK 버전이 다름)
- 로컬에선 되는데 서버에선 안 됨 (라이브러리가 없음)
- 서버에 A 프로젝트를 깔았더니 B 프로젝트가 깨짐 (같은 라이브러리의 다른 버전이 필요)

**컨테이너는 프로그램과 그것이 필요로 하는 모든 것을 하나로 묶어 격리한다.**
어디서 실행하든 안이 똑같으므로 결과도 똑같다.

## 컨테이너 vs 가상머신(VM)

둘 다 격리를 하지만 무게가 다르다.

```
가상머신                          컨테이너
─────────────────────            ─────────────────────
[ 내 앱 ]                        [ 내 앱 ]
[ 라이브러리 ]                    [ 라이브러리 ]
[ 게스트 OS 전체 ]  ← 무거움      (호스트 커널을 공유)  ← 가벼움
[ 하이퍼바이저 ]                  [ 컨테이너 런타임 ]
[ 호스트 OS ]                    [ 호스트 OS ]
```

VM은 OS를 통째로 하나 더 띄운다 — 부팅에 수십 초, 메모리 수 GB. 컨테이너는
호스트의 커널을 공유하고 프로세스만 격리한다 — 기동 1초 미만, 메모리 수십 MB.

> [!note] 맥에서는 사실 VM이 하나 껴 있다
> 컨테이너는 리눅스 커널 기능이라 macOS에선 그냥 못 돈다. Docker Desktop이
> 뒤에서 리눅스 VM을 하나 띄우고 그 안에서 컨테이너를 돌린다. 그래서 맥의
> Docker가 리눅스보다 느리고 메모리를 따로 할당해야 한다.

## 이미지와 컨테이너 — 가장 중요한 구분

이 둘을 헷갈리면 계속 헤맨다.

| | 이미지(Image) | 컨테이너(Container) |
| --- | --- | --- |
| 무엇 | 실행에 필요한 파일·설정의 **읽기 전용 스냅샷** | 이미지를 **실행한 상태** |
| 비유 | 클래스, 설계도, 붕어빵 틀 | 인스턴스, 건물, 붕어빵 |
| 개수 | 이미지 1개로 | 컨테이너를 100개 만들 수 있다 |
| 변경 | 안 됨 (불변) | 안에서 파일을 만들 수 있지만 **지우면 사라짐** |

```bash
docker image ls        # 이미지 목록 (설계도)
docker ps              # 실행 중인 컨테이너 목록 (실체)
docker ps -a           # 멈춘 것까지 전부
```

**컨테이너는 일회용이다.** 안에서 만든 데이터는 컨테이너를 지우면 없어진다.
데이터베이스처럼 데이터를 지켜야 하면 별도의 저장소(볼륨)를 붙여야 한다 —
쿠버네티스에선 이게 PVC다. [[02_쿠버네티스_기본개념]] 참고.

## 태그 — 이미지의 버전 이름

```
scene-api:dev
└─ 이름 ─┘ └태그┘
```

태그를 안 쓰면 `latest` 가 붙는다. SceneTrip은 로컬에서 `:dev` 태그를 고정해서
쓴다 — 매번 태그를 바꾸면 옛 이미지만 쌓이기 때문이다.

## Dockerfile — 이미지 만드는 레시피

```dockerfile
FROM eclipse-temurin:21-jre     # 베이스 이미지 (JRE 21이 깔린 리눅스)
WORKDIR /app                     # 작업 디렉터리
COPY build/libs/app.jar app.jar  # 내 파일 복사
EXPOSE 8080                      # 이 포트를 쓴다고 표시
ENTRYPOINT ["java","-jar","app.jar"]  # 컨테이너 시작 시 실행할 명령
```

각 줄이 **레이어** 를 하나씩 만들고, 레이어는 캐시된다. 그래서 변하지 않는 것
(의존성 설치)을 위에, 자주 변하는 것(내 소스코드)을 아래에 둬야 빌드가 빠르다.
순서를 거꾸로 하면 소스 한 줄 고칠 때마다 의존성을 전부 다시 받는다.

```bash
docker build -t scene-api:dev services/scene-api
#             └── 이름:태그 ──┘ └─ Dockerfile이 있는 경로 ─┘
```

## 레지스트리 — 이미지 보관소

이미지를 올려두고 받아가는 저장소. Git에서의 GitHub 같은 것.

| 레지스트리 | 용도 |
| --- | --- |
| Docker Hub | 공개 이미지 (nginx, postgres 등) |
| AWS ECR | 우리 팀 이미지 (배포용) |

`docker run nginx` 를 하면 로컬에 없을 때 Docker Hub에서 자동으로 받아온다.

## SceneTrip에서 알아야 할 것

**Docker Desktop은 컨테이너 런타임으로만 쓴다.** Docker Desktop 설정에 Kubernetes
항목이 있지만 **켜지 않는다.** SceneTrip은 kind를 쓰기 때문이다. 켜두면 클러스터가
둘이 되어 어디에 배포했는지 헷갈리고 메모리도 두 배로 먹는다.
자세히는 [[03_kind와_로컬클러스터]].

**리소스 할당** — Docker Desktop → Settings → Resources에서 조정한다.
16GB 이상 장비 기준 권장값: CPU 4, Memory 6~8GB, Swap 1~2GB, Disk 40GB 이상.

## 자주 만나는 오류

| 오류 | 원인 | 해결 |
| --- | --- | --- |
| `docker: command not found` | Docker Desktop 미설치 | `brew install --cask docker-desktop` |
| `Cannot connect to the Docker daemon` | **Docker Desktop 앱이 안 켜져 있음** | 앱 실행 후 재시도 |
| `exec format error` | 이미지 아키텍처 불일치 (arm64 vs amd64) | `docker buildx build --platform linux/amd64` |

> [!warning] Apple Silicon 주의
> 맥북(arm64)에서 빌드하면 arm64 이미지가 나온다. AWS EKS 노드가 amd64면
> **로컬에선 되는데 EKS에서만 죽는다.** `--platform` 을 지정해서 빌드해야 한다.
